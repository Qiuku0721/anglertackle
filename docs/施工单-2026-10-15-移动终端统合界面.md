## §1 为什么用"发指令"做路由（最省、最不易错）

每个模块**已经有**自己的请求通道（`CodexRequestPayload` / `GuideRequestPayload` /
`RankRequestPayload` / `CookbookRequestPayload` …），服务端收到就推快照、客户端收到就开界面。
所以终端点一下，**只要客户端发一条对应的 `/atl` 指令**即可：

```java
// TerminalScreen 里，点某个模块：
this.minecraft.player.connection.sendCommand("atl quest");   // 委托
this.minecraft.player.connection.sendCommand("atl codex");   // 图鉴
// …mail / shop / league / contest / ach …
```

**好处**：① 不新增任何载荷；② 权限口径**自动**沿用既有指令（`ach` 无门槛、`grant` 要 OP ✓）；
③ 以后加模块 = 表里加一行 ✓。

⚠ 唯一要注意：`sendCommand` 是**客户端**发的，服务端会当普通玩家指令执行 —— 所以
**终端里只能列"玩家自己能开的"模块**（`/atl coins`、`/atl repair` 这类 OP 指令**不要列**）。

## §2 入口（用户抱怨的是"分散在物品上"，所以入口要少而固定）

1. **按键**（推荐主入口）：默认 `V`（或 `J`），可在原版"按键设置"里改 ——
   需要 `ClientSetup` 注册 `KeyMapping` + `ClientEvents` 里 `while (key.consumeClick()) mc.setScreen(new TerminalScreen())`。
   ⚠ `docs/41` 里没有定过键位，**先问用户一句**再定死。
2. **指令**：`/atl terminal`（无门槛）—— 与 `/atl ach` 同一套 `lit(...)` ✔。
3. **（可选）单个物品**：如果要"一个物品当遥控器"，就复用现有某个物品（例如邮箱物）右键开终端，
   **不要新造物品**（要贴图、要配方、要进商店，成本高且违背"入口少"的初衷）。
