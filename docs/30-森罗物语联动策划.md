# 30 · 森罗物语（Kaleidoscope）联动策划与制作规划

> 📌 **开工必读** —— 本文件是《垂纶》策划族的一员。动手前先读 `docs/CONVENTIONS.md`（协作规则 + 每轮自我暗示）与 `docs/接力.md`（接手须知）；项目记忆只认 `docs/` 下的文件。

> **用户原话（2026-10-03）**
> 第一轮："我想实现的是森罗物语的类似物品可以替代合成，比如森罗的油可以替代我们的鱼油，
> 以及我们的食物可以用森罗的方式合成，比如把红烧鱼的材料放入炒锅，可以用他们的炒制方式制作出来，
> 同时不改变他们 mod 的任何内容，但让我们能够适配。先出策划和制作规划。"
>
> 第二轮（补充要求）："就比如借他们的砧板，森罗在切菜时用菜刀在砧板切，我的设想是在他们的砧板上
> 可以实现和我们这里工作台处理完整鱼成肉块的流程，而且还可以实现我们有的『根据重量获得更多成品』。
> 砧板上再放上我们 mod 的鱼肉块用菜刀切，可以直接合成鱼丸。根据不同菜单类型确认他们在森罗制作的流程，
> 并且在森罗需要用碗盛饭，我希望如此制作的物品在使用后像森罗那样返还碗。厨具不新增，直接用他们的，
> 但不加森罗也可以用我们已经有的方式合成。你可以通过制作扩展包实现这些内容，但无论如何不能动原来
> 森罗 mod 的哪怕一行代码。"
>
> 本文件是这一层的**唯一真源**。落地后由 `tools/check-kaleidoscope-compat.js` 守着（§7）。

## 1. 目标（拆成 6 条可验收的）

| # | 目标 | 方向 |
|---|---|---|
| **G1** | 相似物品替代合成：森罗「油脂」顶我们的「鱼油」、国味「盐」顶我们的「盐」 | 我们 → 接受他们的 |
| **G2** | 他们的机器/配方接受我们的东西（鱼进他们的锅、我们的刀上他们的砧板） | 他们 → 接受我们的 |
| **G3** | **在他们的砧板上跑我们工作台的切鱼流程**（整鱼 → 鱼块，**按重量出块**） | 我们 → 借他们的砧板 |
| **G4** | 在砧板上用我们的鱼块切出**鱼丸** | 同上 |
| **G5** | 我们的菜用他们的厨具做（炒锅/汤锅/蒸笼…），**碗装、吃完返还碗** | 我们 → 借他们的厨具 |
| **G6** | **厨具不新增**；**不装森罗时一切照旧** | 约束 |
| **红线** | **不改森罗 mod 的任何一行代码/资源**（他们的 jar 一个字节都不碰） | 约束 |

## 2. 事实：他们的接口（2026-10-03 逐个扒出来，不是猜）

装的 4 个 jar：`厨房 1.4.1` / `国味 1.1.11` / `酒馆 1.2.0` / `兼容 2.9.7`。

### 2.1 厨具与配方类型

| 类型 | 条数 | 字段（实读） | 语义 |
|---|---|---|---|
| `pot` | 190 | `ingredients[]` + `result{count,id}` | 炒锅：一批材料 → 一批成品 |
| `stockpot` | 65 | `carrier[]` + `ingredients[]` + `result` | 汤锅 |
| `flex_stockpot` / `flex_pot` | 29 / 28 | `carrier{item}` + `ingredients[]` + `result` | 容错版（配方基本只用 `c:` 标签） |
| `chopping_board` | 17 | `ingredient` + **`cut_count`** + **`model_id`** + `result` | 砧板：切 N 刀 |
| `millstone` | 86 | — | 石磨 |
| `teapot` / `steamer` | 7 / 5 | `ingredient` + `result` | 茶壶 / 蒸笼 |

> ⚠ 所有 `result` 都是**静态 `ItemStack`**（id+count）—— 纯数据面改不了产物。

### 2.2 他们的标签（我们能"塞东西进去"的官方接口）

- **`c:raw_fishes`** = `#c:foods/raw_cod` + `#c:foods/raw_salmon` + `#c:foods/tropical_fish`
  → **6 条配方直接吃它**（海鲜味噌汤 ×2、仰望星空派 ×2、油泼鱼）。
- 其它：`c:foods/raw_*`、`c:foods/cooked_*`、`c:eggs`、`c:flour`、`c:dough(s)`、`c:grain/rice`、`c:crops/*`…
- 他们自己命名空间下**被代码读取**的标签：

| 标签 | 谁读 | 意义 |
|---|---|---|
| `kaleidoscope_cookery:kitchen_knife` | `ChoppingBoardBlock(Entity)` | **砧板认"手里的刀"** → 我们的鱼刀挂进去就能切 |
| `ingredient_container` | `PotBlock` / `StockpotBlock` | 什么算容器 |
| `ingredient_blocklist` | `PotBlockEntity` / `StockpotBlockEntity` | 什么不能进锅（**不要动**） |
| `bucket_container` | `ItemUtils` | 桶类容器 |
| `oil` | 没有 class 读（留给数据包/别的模组） | 语义声明 |

### 2.3 ⭐ 他们的 **API 包**（决定性的发现）

`com.github.ysbbbbbb.kaleidoscopecookery.api.*` —— **官方留给别的模组的钩子**：

| API | 内容 | 我们能拿它做什么 |
|---|---|---|
| `api/item/IHasContainer` | `Item getContainerItem()` + `returnContainerToEntity(...)` | **碗返还**的官方契约 |
| `api/blockentity/IChoppingBoard` | `onPutItem` / `onCutItem` / `onTakeOut` / `playParticlesSound` | 驱动他们的砧板：放料、切、取出、**放他们的音效粒子** |
| `ChoppingBoardBlockEntity`（public） | 另加 `getModelId` / `getMaxCutCount` / `getCurrentCutCount` / `getCurrentCutStack` | 读砧板当前状态 |
| `api/blockentity/IPot` + `PotBlockEntity`（public） | `onPlaceOil` / `addIngredient` / `removeIngredient` / `onShovelHit` / `takeOutProduct` / **`getInputs()`** | 读锅里有什么 → 出锅时替换成**带数据**的菜 |
| `api/blockentity/ISteamer` | `placeFood` / `takeFood` | 蒸笼同上 |
| `api/blockentity/IStockpot` / `IMillstone` / `ITeapot` / `IShawarmaSpit` / `IKitchenwareRacks` | 各自的公开操作 | 同上 |
| `api/event/StockpotMatchRecipeEvent`(**Pre/Post**) | **`getInput()` + `setOutput(RecipeHolder<StockpotRecipe>)`** | 汤锅匹配配方时**直接换掉产物** |
| `api/event/MillstoneMatchRecipeEvent`(Pre/Post) | 同上形态 | 石磨 |
| `api/event/RecipeItemEvent`(CheckItem/DeductItem) | 他们的「菜谱纸」扣料 | 暂不需要 |
| `crafting/recipe/StockpotRecipe` | **public record + 公开构造器**，字段含 `ItemStack result`（**完整栈，可带组件**） | 我们自己 new 一个配方对象塞回去 |
| `crafting/container/StockpotInput` | `extends SimpleInput`（拿得到 `List<ItemStack>`） | 从输入读出鱼的**鱼种/档位/重量** |

**结论：只要写一个"扩展包"（编译期只依赖他们的 API，运行期可选），"接管产物"这条路全通** ——
砧板、炒锅、汤锅、蒸笼都能出**带我们数据组件**的菜，而他们的 jar 一个字节都不用改。

### 2.4 我们这边的现状（要改造的地方）

| 位置 | 现状 | 影响 |
|---|---|---|
| `DishRecipe.Need`（Java） | `mat(() -> ModItems.FISH_OIL.get())` **写死物品** | 没法接受替代物（G1） |
| 我们的物品标签 | 只有 `#anglertackle:fishes`，**一个 `c:` 都没有** | 他们的机器看不见我们的鱼（G2） |
| 无数据菜 | `DishItem` 没有 `FISH_CHUNK` 时按"无数据"处理（tooltip 已能说清） | 需要定"默认档"口径（§4.2） |

## 3. 架构：主 jar + **扩展包**

```
anglertackle-1.3.0.jar              主 jar：不引用他们的任何类（无编译依赖）
  ├─ data/c/tags/item/…             标签互认（required:false 可选条目）
  ├─ data/anglertackle/recipe/kaleidoscope/…   兼容配方（mod_loaded 条件）
  └─ 我们自己的逻辑：替代标签、无数据菜口径、碗装物品（原版 usingConvertsTo）

anglertackle-kaleidoscope-1.0.0.jar  扩展包：compileOnly 依赖他们的 API，可选安装
  ├─ 砧板接管（G3/G4）
  ├─ 炒锅/蒸笼出锅接管（G5 数据保真）
  ├─ 汤锅/石磨 MatchRecipeEvent（G5 数据保真）
  └─ 碗装物品的 IHasContainer 实现（与他们的 carrier 流程对齐）
```

- **他们的 jar 不入库**：扩展包构建时从 `libs/kaleidoscope_cookery.jar` 读（开发者手动放，
  `.gitignore` 掉），缺失时**跳过扩展包编译**（主 jar 不受影响）。
- **卸掉森罗**：扩展包整包不加载（`neoforge.mods.toml` 里声明依赖他们 +
  配方文件带 `neoforge:mod_loaded` 条件）→ 我们的原路径（工作台/炉子）完全照旧 ✓ G6。
- **他们的 jar 只读**：构建前记录 sha256，跑完再比一次（证明我们没写过他们的文件）。

## 4. 逐条设计

### 4.1 G1 替代合成（标签 + `required:false`）

我们把"写死的物品"换成**自己命名空间的标签**，里面同时列我们的物品与他们的对应物：

```json
// data/anglertackle/tags/item/cooking_oil.json
{ "values": [ "anglertackle:fish_oil",
              { "id": "kaleidoscope_cookery:oil", "required": false } ] }
```

> ⚙️ `required: false` 是**原版 1.21 原生支持**的（`TagLoader.EntryWithSource` / `build()` 那条路）：
> 没装森罗时这个条目**不会**让整个标签加载失败、也不报错 —— 不需要条件标签、不用写两套文件。

- 改 `DishRecipe.Need`：`mat(Supplier<Item>)` → 接受 tag/Ingredient（10 道菜全部受益）。
- 替代关系表（⚙️ 初版，可加行）：

| 我们的 | 标签 | 他们的对应物（可选条目） |
|---|---|---|
| 鱼油 | `anglertackle:cooking_oil` | 厨房 `kaleidoscope_cookery:oil`（油脂） |
| 盐 | `anglertackle:salt` | 国味 `kaleidoscope_chinesefood:salt`（盐） |
| 鱼刀 | `anglertackle:kitchen_knife` | 厨房 `*_kitchen_knife`（菜刀） |
| 熟鱼块 | `anglertackle:cooked_fish_chunk` | —（他们无可比物） |
| 酱油 / 芥末 | 暂空位 | 他们没有（国味只到盐） |

- 反向（G2）：往**他们的标签**里加我们的物品（data 包**合并**，不是覆盖）：

| 文件 | 内容 | 收益 |
|---|---|---|
| `data/c/tags/item/raw_fishes.json` | `#anglertackle:fishes` | **他们那 6 条配方立刻能用我们的 28 条鱼** |
| `data/kaleidoscope_cookery/tags/item/kitchen_knife.json` | `anglertackle:fish_knife` | **我们的鱼刀能上他们的砧板** |
| `data/kaleidoscope_cookery/tags/item/oil.json` | `anglertackle:fish_oil` | 语义声明（他们暂未读） |
| `data/c/tags/item/foods/cooked_fish.json` | 熟鱼块/熏鱼/炭烤鱼 | 通用"熟鱼"标签 |

> ⚠ **不许**把我们的鱼挂进 `c:foods/raw_salmon|raw_cod|tropical_fish`（那是"这条是鲑鱼/鳕鱼"，
> 挂进去等于让"鲑鱼刺身"配方接受鲫鱼 —— 语义错、也骗玩家）。

### 4.2 无数据菜的口径（**已定案：按鱼的档位**）

**有了 §2.3 的接管手段之后**，砧板/炒锅/汤锅/蒸笼这四条主路径都能出**带数据**的菜 ✓，
"无数据菜"只剩两种情况：① 没装扩展包只装了主 jar 的兼容配方；② 他们未来新增的厨具。

**口径（用户 2026-10-03 拍板："根据鱼档次决定"）**：

| 情况 | 规则 |
|---|---|
| **能读到输入鱼**（扩展包接管的砧板/炒锅/汤锅/蒸笼 —— 正常路径） | 产物带**那条鱼的真实数据**（鱼种 + 档位 + 重量），效果与饱食度**按它的真实档位**结算 |
| 读不到输入（主 jar 的静态兜底配方、创造模式直拿的无数据菜） | ⚙️ 最后兜底 = 按**优质档（tier 2）**结算，tooltip 写明"此做法按优质档结算"；若你希望改成别的档（例如白档 0）说一声 |

> 也就是说：**"一口价"这件事被 API 消掉了** —— 只要走扩展包接管，档位就是真实的；
> "按优质档"只剩"完全没有来源信息"时的兜底，不再影响正常玩法。

### 4.3 G3/G4 在他们的砧板上跑我们的切鱼流程

**放料让他们的代码做**（他们的模型/动画/`model_id` 都照旧），**只在"切"这一步接管**：

```
玩家拿整鱼右键砧板      → 他们处理（onPutItem）✓ 我们不动
玩家拿我们的鱼刀右键    → PlayerInteractEvent.RightClickBlock（可取消，先于方块 use 触发）
                        ① 判定：板上是我们的整鱼/鱼块，手里是我们的鱼刀
                        ② 我们按**重量**算块数（复用 CuttingRecipe 的公式与常量）
                        ③ 调他们的 playParticlesSound()（他们的音效与粒子 ✓）
                        ④ 调他们的 onTakeOut() 清板（鱼回到玩家/掉落）
                        ⑤ 把算好的鱼块（**带 FISH_CHUNK 数据**）交给玩家
```

- 鱼块 → 鱼丸：同一条路，②换成鱼丸的产出规则（可做"1 块 → 4 颗"之类的定案数值）。
- **没装扩展包时**：主 jar 里仍有一条**静态**的 `chopping_board` 配方（固定块数、无数据），
  保证"只装主 jar + 森罗"也能切，只是不如接管版精确 ✓ 两条并存、行为差异写进界面文案。
- 他们的原配方（切他们的食材）**完全不受影响** —— 我们只在自己物品的组合上取消事件。

### 4.4 G5 用他们的厨具做我们的菜（逐厨具流程 + 碗）

| 我们的菜 | 厨具 | 在他们那的流程 | 碗 |
|---|---|---|---|
| 红烧鱼 / 香煎鱼 / 油炸鱼块 / 整条油炸 | 炒锅 `pot` / `flex_pot` | 放油 → 放料 → 炒（自动）→ 铲出 | 不需要 |
| 鱼丸 | 炒锅 `pot`（或砧板，见 G4） | 同上 | 不需要 |
| 鱼汤 / 奶白鱼汤 / 慢炖鱼 | 汤锅 `stockpot` / `flex_stockpot` | 放料 → 加水/汤底 → 煮 → 用**碗**盛 | **需要碗** |
| 清蒸鱼 | 蒸笼 `steamer` | 放料 → 蒸 | 不需要 |
| 刺身 | 砧板 `chopping_board` | 整鱼上板 → 切 | 不需要 |
| 熏鱼 / 炭烤鱼 | 不做（与我们的炉线重叠，收益低） | — | — |

**数据保真**（扩展包内实现，全部走他们的公开 API/事件）：

- **汤锅**：`StockpotMatchRecipeEvent.Pre/Post` → 从 `input` 读出鱼 → 我们 new 一个
  `StockpotRecipe(ingredients, soupBase, 我们的带数据结果, time, carrier, visuals)` → `setOutput(...)`
  （`StockpotRecipe` 是 public record、`result` 是完整 `ItemStack` ✓ 可带组件）。
- **炒锅**：在"铲出"那一步读 `PotBlockEntity.getInputs()` → 把产物替换成带数据的菜。
- **蒸笼**：`ISteamer.takeFood` 那一侧同理。
- **砧板**：§4.3。

**碗返还（G5 的后半句）**：我们的"碗装版"物品用**原版**机制即可 ——
`Item.Properties.usingConvertsTo(Items.BOWL)` / `craftRemainder(Items.BOWL)`（和原版蘑菇煲同款）✓。
若要与他们的 `carrier` 流程完全对齐（比如汤锅要求玩家手持碗），扩展包里再实现他们的
`IHasContainer`（`getContainerItem()` 返回碗）✓ —— 两条都行，⚙️ 我建议**先做原版机制**（不依赖他们的版本）。

### 4.5 G6 不装森罗时照旧

- 主 jar：标签用 `required:false`；兼容配方带 `neoforge:conditions` + `mod_loaded`。
- 扩展包：整包声明依赖森罗 → 不装就不加载（连类都不进 JVM）。
- 验收：装/不装两次 `runServer`，配方数与体检结果必须一致（除兼容面）。

## 7. 守门：`check-kaleidoscope-compat.js` 断言

1. **不越界**：我们的 data 下**不存在** `data/kaleidoscope_cookery/recipe/**`。
2. **可选条目**：所有引用他们物品 id 的标签条目必须带 `"required": false`。
3. **条件加载**：所有 `kaleidoscope_cookery:*` 类型的兼容配方必须带 `neoforge:mod_loaded`。
4. **替代不丢原件**：每个替代标签里必须**仍然包含我们自己的原物品**。

放文件；从替代标签删掉我们自己的鱼油；把鲫鱼挂进 `raw_salmon`；在主 jar 里 import 他们的类。

## 13. 插手边界（1.5.1 定稿，用户报的锅盖事故换来的）

**事故**：用户 2026-10-04 报"点击汤锅可以取下锅盖，硬是拿下来一个物品却发现方块上还有"、
"蒸笼 shift+右键开关笼盖，一放我们的鱼右键无论如何都把蒸笼破坏"。

**原因**：扩展包原来是"只要锅里有我们的成品就取消他们的右键、由我代跑
`takeOutProduct`/`takeFood`"。可同一个右键在他们那里还兼着**锅盖/笼盖**的开关 ——
被我们取消之后，物品到手了、**方块状态却没更新**（锅盖还在），状态机也跟着乱。

**因此定死三条边界**（`StockpotTakeover` / `PotTakeover` / `SteamerTakeover` 各守一条）：

| 方块 | **才接管**（三条同时成立） | **一定不碰** |
|---|---|---|
| 汤锅 | ① 手里拿着**碗**（我们配方的 carrier）② 状态 == `IStockpot.FINISHED` ③ 成品是我们的菜 | 空手（取锅盖）、拿水桶/生料、任何其它物品 |
| 炒锅 | ① 手里拿**碗**或他们的**锅铲**（`TagMod.KITCHEN_SHOVEL`）② 状态 == `IPot.FINISHED` ③ 成品是我们的菜 | 放油、放料、空手、其它物品 |
| 蒸笼 | ① **不潜行**（潜行=开关笼盖）② **空手** ③ 笼里确实有"熟了"的一格（`getCookingProgress() >= getCookingTime()`，用他们公开数组） | shift+右键（笼盖）、放料、还没熟的右键 |

**另一条教训**：状态判断一律用他们的 **API 常量**（`IStockpot.FINISHED`/`IPot.FINISHED`），
不许写死数字 —— 我上一版把汤锅"煮好"写成 `status != 2`，而 `IStockpot` 里 FINISHED 是 **3**，
于是抢错了时机。

## 12. 1.4.1–1.4.2：汤底、生料、以及"数据为什么会丢"（用户实机反馈）

### 12.0 数据丢失的真根因（1.4.2 才修对，值得单独记）

用户："通过森罗制作的食物似乎失去了原来的数据，至少奶白鱼汤没给效果。"

他们的 `StockpotBlockEntity.setRecipe(Level)` 顺序（javap 逐条读的）：

```
StockpotInput input = getInput();
post(Pre)                    ← 只有这里能改结果：Pre.getOutput() != null 就 applyRecipe 并 **return**
if (非flex 命中) applyRecipe(...)
post(Post)                   ← 已经晚了：flex 还没匹配
if (flex 命中) applyRecipe(...)   ← **最后落地的永远是这一条**
```

我们的兼容配方全是 `flex_stockpot`（汤底自由），所以：
· 1.4.0/1.4.1 挂在 **Post** 上 —— 那时 flex 还没匹配，改了也白改；
· **Pre 里 `getOutput()` 是空的**（还没匹配），所以"读现成的再改"同样不通。
✅ 正确做法：**在 Pre 里用他们的 RecipeManager 自己匹配一遍**
（`ModRecipes.FLEX_STOCKPOT_RECIPE` + `StockpotInput`），照抄配方只换 result，再 `setOutput(...)`。

### 12.0.1 ⚠ 1.4.2 的崩溃（用户实机报的）与修法

```
java.lang.ClassCastException: FlexStockpotRecipe cannot be cast to StockpotRecipe
  at StockpotTakeover.onPre(StockpotTakeover.java:68)
  at StockpotBlockEntity.setRecipe → tick → 服务端崩
```

**原因**：`FlexStockpotRecipe` **不是** `StockpotRecipe` 的子类 —— 两者都
`implements BaseRecipe<StockpotInput>`、都继承 `java.lang.Record`，只是**凑巧字段一样**
（ingredients / soupBase / result / time / carrier / visuals）。我按"flex 是 stockpot 的子类"写了强转。

**修法**（两条都要，缺一不可）：
1. 两个类型**分别 instanceof 分支**取字段，再拼一个 `StockpotRecipe` 交给他们；
2. 汤锅/炒锅两个处理器**整体包 try/catch** —— 它们跑在**他们的方块实体 tick / 交互路径**上，
   兼容层再出错也只能退化成"这道菜没数据"，绝不允许把玩家的世界弄崩。

**炒锅**（`pot`/`flex_pot`）**没有**任何匹配/成品事件（`api/event` 只有 Stockpot / Millstone /
RecipeItem / SickleHarvest），所以改配方这条路不通 —— 改成卡**出锅那一下**：
`PotBlockEntity.getStatus()==FINISHED` + 成品是我们的菜 + 锅里有我们的鱼 → 取消交互 →
调他们的 `takeOutProduct`（玩家先拿到无数据的那份）→ **等量收回** → 给带数据的那份。
收不回来就什么都不额外给（宁可玩家拿到无数据的一份，也不给复制口子）。

**用户原话**："他们的汤锅有汤底这一属性，我对着我们的配料表，使用熟鱼块加鱼油，以水为汤底，
却只能做出森罗物语里默认没有配方的烹饪产出 —— 谜之炖菜。……比如都用锅煮饭了，那必然是用生肉。"

**病根**：1.3.1 那版把 `minecraft:water_bucket` 写成了**配料**，而他们的汤锅把水放在**汤底槽**
（`StockpotInput.getSoupBase()`，独立于 `ingredients`）→ 配料永远匹配不上 → 落到他们的兜底菜"谜之炖菜"。
（他们的 `flex_stockpot` 配方 JSON 只有 `type` / `ingredients` / `result` 三个键 ——
不写汤底，所以**任何**汤底都能用，包括水 ✓）

**改法**（13 条兼容配方）：
- 汤锅 6 条：**删掉水桶配料**；鱼汤/奶白鱼汤/慢炖鱼各有"**生**块"与"熟块"两条 ——
  生料是"锅煮饭用生肉"的正路，熟料那条保留（用户已经试过熟块加鱼油，不能让他白试）。
- 炒锅 6 条：主料一律换成**生**料（`anglertackle:raw_fish_chunk` / 整鱼），锅负责把它做熟（**配方里不写鱼油** —— 他们的炒锅在放料前有独立的"放油"流程 `IPot.onPlaceOil`，再要就是收两次油）：
  ⚠ **炒锅配方里不写鱼油**：他们的炒锅在放料**之前**有一个独立的"放油"流程
  （`IPot.onPlaceOil`），配方再要鱼油等于收两次油（用户 2026-10-04 指出）。酱油/盐/面粉/糖保留。
  香煎鱼 = 生块+盐；油炸鱼块 = 生块+面粉；红烧鱼 = 生块+酱油+糖；
  鱼丸 = 生块+面粉（**1:1**，与砧板那条一致）；整条油炸 = 整鱼+面粉；
  **清蒸鱼 = 整鱼+姜+酱油**（原来是"熟块+水桶"，水桶是照抄工作台配方的错 —— 蒸的是整条鱼）。
- 砧板 1 条：静态兜底（`cut_count: 4` → 刺身），装了扩展包时走 `BoardTakeover` 的按重量切块。

⚠ 口径提醒：**工作台**那条线仍用熟块（`docs/25` 的三级流程），森罗厨具这条线用生料 ——
两条线的原料不同是**故意的**（锅会做熟，工作台不会）。
