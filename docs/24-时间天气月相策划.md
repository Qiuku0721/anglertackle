## 0. 一句话设计（v2）

> **每个受影响的"组"（时段组 / 天气组 / 月相组），其归一化后的总占比最多提升 10 个百分点；
> 组内每条鱼乘同一个倍率 k（k 由池子反解得出，不写死）。月相组的预算另有口径：
> 金红爆率总提升 ≤ 5 点、紫爆率 ≤ 15 点。**
>
> 三条约束全部是**上界**：池子组成决定实际能吃到几点，但**永远不可能超过**。

**用户给的两个算例（照抄，作为口径基准）**：

| 池子 | 变化 | 说明 |
|---|---|---|
| 2 种鱼各 **50%**，其中 1 种受加成 | **40 / 60** | 受加成那条 50% → 60% |
| 4 种鱼各 **25%**，其中 2 种受加成 | **20 / 20 / 30 / 30** | 受加成那两条各 25% → 30% |

两个算例背后的规则是同一条：**受加成组的总占比恰好 +10 个百分点，且组内每条鱼乘同一个倍率**。
反解出来的倍率是 `k = 1.5`（不是 1.2，见 §4.1 的核对）。

## 1. v1 错在哪：倍率 vs 占比

| | v1（被否） | v2（本版） |
|---|---|---|
| 表达方式 | "活跃时段的鱼权重 **×1.60**" | "活跃时段的鱼**总占比最多 +10 个百分点**" |
| 实际效果取决于 | 池子组成**未知** —— 若那条鱼本来就占 40%，×1.6 会让它冲到 57% | **有确定的上界**：无论池子怎么组成，占比提升不超过 10 个百分点 |
| 玩家感知 | "某条鱼突然到处都是" | "这个时段它明显更常见了，但还是老样子钓鱼" |
| 可验证性 | 只能验证"倍率写对了" | 可以**离线模拟验证上界**（跑 2 万竿统计占比） |

**关键差别**：倍率是**相对量**，占比是**绝对量**。同一个 ×1.60：
鱼占 5% 时只加到 7.8%（+2.8 点，温和）；鱼占 **40%** 时加到 **57%**（+17 点，失控）。
v1 的错就在于"把控制权交给了池子组成"，而池子组成又随竿/饵/窝/水体变化 ——
所以同一个倍率在两种配置下的体感完全不同。占比上限把这件事按死了。

## 2. 三条硬约束（用户指定，不再讨论）

| # | 维度 | 约束 | 口径 |
|---|---|---|---|
| **C1** | **时间** | 受时段加成的鱼，**归一化后总占比最多 +10 个百分点**；组内每条同倍率 | `p'(时段组) − p(时段组) ≤ 0.10` |
| **C2** | **天气** | 同上，**最多 +10 个百分点** | `p'(天气组) − p(天气组) ≤ 0.10` |
| **C3** | **月相** | 所有金红鱼吃到的**爆率总提升 ≤ 5 个百分点**；所有紫鱼 **≤ 15 个百分点** | 详见 §4.3（均摊口径 ⏳） |

**关于"是不是减权"（v1 的表述我改一下）**：
v2 的做法是**只把受加成鱼的权重乘 k**，不受加成鱼的权重**一个都不动**；
它们占比从 50% 掉到 40%，是**归一化的必然结果**（分母被抬大了），
不是"被打压"——**池子里没有任何一条鱼的权重被乘上小于 1 的数**。
这个区分很重要：它保证"换个时段来钓鱼，收获不会变差，只是鱼的构成不同"。

> 反过来说，v1 里那些"×0.45 / ×0.60"的惩罚项是**真的减权**，已经全部删除。

## 4. 实现：三条约束怎么解

### 4.1 时间与天气（C1 / C2）—— 反解倍率，不写死

代码库里**已经有这个套路**：`FishSpecies.buildPool(...)` 里的 `hvTargetPct`
就是把"金+红"这一组的总占比精确拉到目标值，用的公式是
`k = p·other / ((1−p)·hv) `。v2 沿用同一个思路，只是**目标值改成"当前占比 + 10 点，且封顶"**：

```java
/** 把 inGroup 命中的那组鱼的**归一化总占比**抬到 min(当前占比 + deltaPct, capPct)。 */
static boolean applyShareCap(List<FishSpecies> kept, List<Double> w, IntPredicate inGroup,
                             double deltaPct, double capPct) {
    double total = sum(w);
    double g = sum of w where inGroup;
    if (g <= 0) return true;                       // 这条鱼都不在池子里 → 本维度无事可做
    if (total - g <= 0) return true;               // 全在这一组 → 占比恒 100%，抬不了
    double p = g / total;
    double target = Math.min(p + deltaPct, capPct);
    if (target <= p) return true;                  // 已到顶 → 封住（这是"上界"，不是失败）
    double k = (target * (total - g)) / ((1 - target) * g);
    for (i where inGroup) w[i] *= k;              // ⚠ 只乘这一组；其余鱼**一个都不动**
    return Math.abs(share(w, inGroup) - target) < 1e-9;
}
```

**核对用户的算例**（脚本 `build/_check-k.js` 实测，不是手算 —— 跑它就是复现下面这两行）：

| 池子 | 受加成组原占比 p | 反解出的 k | 归一化后 | 与用户给的一致？ |
|---|---|---|---|---|
| 2 种各 50%，1 种受加成 | 50% | **1.5** | 60.00% / 40.00% → **40/60** | ✅ 完全一致 |
| 4 种各 25%，2 种受加成 | 50% | **1.5** | 30/30/20/20 → **20/20/30/30** | ✅ 完全一致 |

> ⚠️ 我一开始按"每条 ×1.2"算过一遍，结果只拿到 **+4.55 点**（50% → 54.55%），
> 与你要的 40/60 差得远 —— 所以**倍率必须是反解出来的**，不能写死。
> 反过来，若写死 k=1.2：p=10% 时只 +1.76 点、p=90% 时只 +1.53 点，越极端越没感觉。

- **`target` 是"当前占比 +10 点"** —— 本来就占 25% 的那组最多升到 35%（+10 点），不是升到 10%。
- **反解 vs 写死倍率**：`k` 由池子反解 ⇒ "每条同倍率"且"组增量恒为 10 点"两件事同时成立，
  你的两个算例就都满足了。这是本方案的核心，**不要退化成固定倍率**。
- **`capPct`（封顶）**：p 很大时（比如 90%）"+10 点"会算出让组占比 100% 的 k，
  所以最后夹一层封顶（默认 `envShareCapPct = 90`，见 §10）。夹住之后增量自然变小，
  这属于"池子里本来绝大多数都是加成鱼"的极端情形，不影响常态。
- 三组（时段 / 天气 / 月相）**逐个施加**，每步都重新统计占比；最后跑收敛检查（§4.4）。

### 4.2 月相（C3）—— 分两层，先做第一层再决定第二层

月相要求的是**品质爆率**，不是鱼种占比，所以它作用在另一条链上。
需要先说清"爆率"是怎么来的（我核对过代码）：

```
一竿的品质 = ① 抽到哪种鱼（鱼种权重，buildPool）
            × ② 这条鱼有多重（rollIndividual 按体型系数采样）
            → 品质档由体重决定：tierForWeight()，区间权重表见 tierSplit()
```

`tierSplit()` 现在的取值是：**红档 2 / 金档 5 / 其余 6**（同种鱼里红档本来就只占约 1/8 的体重区间）。

**两种做法**：

| | 做法 A（鱼种级） | 做法 B（个体级） |
|---|---|---|
| 改哪 | 月相鱼的**鱼种权重**（只对带红/紫档的月相鱼加权） | 月相鱼的**档位区间权重**（`tierSplit` 在月相时临时加红/紫的份额） |
| 效果载体 | 让"镜鲤"这种鱼更容易被抽到 | 让同一条鱼的个体更容易落在高/中档 |
| 精度 | 要离线模拟才知道落在几个百分点 | 可以直接把区间权重调到目标 |
| 复杂度 | 低（复用 §4.1 的求解器） | 中（要动 `rollIndividual` 的采样路径） |
| 我建议 | **先做 A，用离线模拟量出实际增量**；达不到 +5/+15 再做 B | |

### 4.3 月相（C3）—— 用户原话与我的落地口径

> 用户原话：
> **"比如钓鱼，抽取鱼所有金红鱼加起来 5%，月相加成吃满就是各分一点，
> 所有金红鱼提升的爆率加起来不超 5%。紫爆率同理。"**

拆成三条可执行的规则：

| # | 规则 | 落地 |
|---|---|---|
| 1 | 金红鱼**合计爆率**上限 **5 点**，紫鱼合计 **15 点** | 总预算封顶 |
| 2 | 吃满时**所有金红鱼一起分**这 5 点（"各分一点"） | 组内每条**同倍率**，不是"只抬最稀有那一条" |
| 3 | 组内每条鱼分到的**相对提升一致** | 反解同一个 k（与 §4.1 同一套求解器） |

**关于"各分一点"的两种读法**（都满足"总和不超 5 点"，但效果差很多）：

| 读法 | 算法 | 若金红鱼合计 5%（5 条各 1%） | 结果 |
|---|---|---|---|
| **① 预算均摊** | 每条**各自 +1 点**（5 点 ÷ 5 条） | 各 1% → 各 2% | 合计 10%（**+5 点**，就是把预算用完） |
| **② 同倍率**（与 §4.1 一致） | 反解 k 使合计 5% → 10% | k = 2.11，各 1% → 各 2.11% | 合计 10.55%（**+5.55 点，略超**） |

⏳ **这一条要你定**（§15 #4）。我倾向 **① 预算均摊** —— 它就是你说的
"各分一点"的字面意思，而且**天然不会超预算**（每条分到的点数确定，
几条金红鱼加起来正好 5 点）：

```java
/** 月相预算均摊：给每条金红鱼各加 deltaPct/条数 个百分点（直接算进权重占比）。 */
static void applyMoonBudget(List<FishSpecies> kept, List<Double> w, IntPredicate inGroup,
                            double budgetPct) {
    int n = count of kept where inGroup;
    if (n == 0) return;
    double per = budgetPct / n;                  // 每条鱼分到的百分点
    // 把"该鱼占比 + per"换算成它的权重倍率 → 归一化后每条正好 +per 点
    for (i where inGroup) w[i] *= shareToWeightFactor(w, i, per);
}
```

**代码层面要注意的一件事**：上面算的是**鱼种权重占比**，
而你说的"金红鱼加起来 5%"很可能是**最终钓上来那条鱼是金/红的概率**（爆率）。
两者差一个系数 —— 同种鱼里红档只占约 `2/13` 的体重区间、金档约 `5/13`（见 `tierSplit()`）。
所以落地时：**先按"爆率"定预算**，用离线模拟反推需要多少权重占比增量，
再把那个增量喂给求解器。§12 的模拟脚本会把两列数都给出来（权重占比 / 实际爆率）。

**做法 A / B 的选择**（与 v1 相同，只是目标换成"爆率 +5/+15"）：

| | 做法 A（鱼种级） | 做法 B（个体级） |
|---|---|---|
| 改哪 | 月相鱼的**鱼种权重** | 月相鱼的**档位区间权重**（`tierSplit` 临时改） |
| 效果载体 | 让"镜鲤"这种鱼更容易被抽到 | 让个体更容易落在高档 |
| 精度 | 要模拟才知落到几个百分点 | 可直接调区间 |
| 复杂度 | 低（复用 §4.1 求解器） | 中（动 `rollIndividual`） |
| 我建议 | **先做 A**；模拟显示爆率吃不到 +5/+15 再做 B | |

### 4.4 三组叠加时会互相稀释 —— 用迭代收敛

时段组、天气组、月相组会**重叠**（一条鱼可能又活跃、又爱雨、又逢满月）。
逐个施加时，后一组会把前一组的占比稀释（分母又变大了）。做法：

- **最多迭代 3 轮**，每轮对三组各施加一次求解器，并检查是否都达到目标；
- 达到就停；3 轮还没全达到（极端池子）就取最后一次结果并**记一条日志**；
- ⚠ **上界永远不会被突破**：每轮 `target` 都是 `p + deltaPct` 且带封顶，
  所以迭代只影响"吃满没吃满"，**不可能超**。这是"先算目标占比、再反解倍率"
  相对"直接乘一个固定倍率"的关键好处。

## 6. 时段与月相口径（与 v1 相同，未变）

### 6.1 时段（原版刻度，一天 24000 tick = 现实 20 分钟）

| 时段 | tick 区间 | 现实时长 | 判据 |
|---|---|---|---|
| **清晨 Dawn** | 23000 – 1000 | ≈2 分钟 | `t >= 23000 \|\| t < 1000` |
| **白天 Day** | 1000 – 11000 | ≈8.3 分钟 | `t >= 1000 && t < 11000` |
| **黄昏 Dusk** | 11000 – 13000 | ≈2 分钟 | `t >= 11000 && t < 13000` |
| **夜晚 Night** | 13000 – 23000 | ≈8.3 分钟 | `t >= 13000 && t < 23000` |

用 `level.getDayTime() % 24000L`（不是一直在涨的 `getGameTime()`）。
边界取"日出/日落前后"（原版日出 ≈0 / 日落 ≈12000），玩家靠天色就能判断。

### 6.2 月相

`level.getMoonPhase()` 返回 0–7，一个周期 8 个游戏日（现实约 2 小时 40 分）。
**只做两端**：满月（0）与新月（4），其余四个相位**不给任何效果**
（玩家抬头看月亮就能判断，不需要 UI 读数）。

### 9.2 改 `fishing/FishSpecies.java`

**注意**：`buildPool` 的签名已经很长（12 个参数，含 `hvTargetPct` / `habitMask` /
`habitExtraPct`）。v2 再往里塞参数会失控，所以**环境相关的三组约束单独抽一个方法**，
在 `buildPool` 的最后一步调用：

```java
/** 在习性加成之后调用；按 C1/C2 把"时段组""天气组"的占比抬到上限内。 */
static void applyEnvironment(List<FishSpecies> kept, List<Double> w, Environment env) {
    if (env == null) return;
    for (int round = 0; round < 3; round++) {          // §4.4 迭代，最多 3 轮
        boolean timeOk    = applyShareCap(kept, w, s -> env.inTimeGroup(s.id()),
                                          Tuning.envTimeDeltaPct(),    Tuning.envShareCapPct());
        boolean weatherOk = applyShareCap(kept, w, s -> env.inWeatherGroup(s.id()),
                                          Tuning.envWeatherDeltaPct(), Tuning.envShareCapPct());
        if (timeOk && weatherOk) break;
    }
}
```

**位置**：仍然放在 `FishHabits.applyBonus(...)` **之后**、取整之前 ——
即"不参与 `hvTargetPct` 求解"这条纪律不变（§2 的 C1/C2 是自己独立求解的）。

## 10. 配置项（全部进 `tools/gen-gameplay-config.js` 生成区）

新增 `[environment]` 组。**v2 的项比 v1 少很多**（没有一堆倍率了）：

| 配置键 | 默认 | 说明 |
|---|---|---|
| `environmentEnabled` | `true` | 总开关；`false` = 完全回到现在的行为 |
| `envTimeDeltaPct` | `10.0` | **C1**：时段组占比最多涨几个百分点（硬上界；50/50 → 40/60 就是这个值） |
| `envWeatherDeltaPct` | `10.0` | **C2**：天气组同理 |
| `envMoonGoldRedDeltaPct` | `5.0` | **C3**：金红爆率总预算（所有金红鱼一起分） |
| `envMoonPurpleDeltaPct` | `15.0` | **C3**：紫爆率总预算 |
| `envMoonShareMode` | `1` | **C3 的分法**：`0` = 组内同倍率，`1` = 预算均摊（§4.3，默认均摊） |
| `envShareCapPct` | `90.0` | 封顶：任何一组占比不得超过这个值（p 很大时防"算出让组占比 100% 的倍率"） |
| `biteNightCutPercent` | `10` | 夜间台钓等待减免（0 = 关） |
| `envLogToPickup` | `false` | 调试：把三组实际吃到的增量打进 `/atl rod` 输出 |

> 全部可热改（走 `Tuning`），改完 `/atl config reload` 生效。
>
> ⚠ `envShareCapPct` 定的是 **90 而不是 50**：你的算例里"2 种鱼各 50%，1 种加成"
> 会让受加成那条达到 **60%**，如果封顶写 50 就直接违背了算例。封顶只用来兜住
> "池子里几乎全是加成鱼"的极端情形。

## 14. 风险与兼容

| 风险 | 对策 |
