## 2. 悬浮显示：三行结构

以「红烧草鱼（优质）」为例：

```
红烧草鱼                       ← 名字（配方书 / JEI 里也是这个）
熟块 + 酱油 + 甘蔗红烧：硬菜（tooltip.anglertackle.braised_fish）
草鱼 · 优质                    ← 鱼种 · 材料档次
食用后获得：                    ← 当前档位**真的会给**的效果
  渔运 II · 14:00              ←（蓝色，与原版药水同一套语言键）
金/红档的鱼做的菜还会获得（档次越高时间越长）：   ← 顶级才多出来的那些
  渔运 II · 14:00              （暗灰）
```

三条规则：

1. **数字不抄策划表**：直接调 `DishEffects.grantsFor(dishId, 档位)` —— 与吃菜时**同一个函数**，
   所以"显示 6 分钟、实际 3 分钟"这种分叉在结构上不可能发生。
2. **"还会获得"只列新增的效果**，不列同一效果的高等级版本（那是**替换**不是新增，
   混在一起会让人以为能叠）。
3. **没有鱼数据**（创造模式/JEI 直拿的裸物品）时说清"效果取决于做菜用的鱼"，
   而不是显示一份不属于它的数字。

> ⚙️ 时长格式：满 1 分钟写 `m:ss`（与原版药水一致），不足 1 分钟写 `20s`。
> 短效果（速度 20s / 生命恢复 5s / 饱腹 10s）写成 `0:20` 会被误读成 20 分钟。
> 等级名用自己维护的罗马数字表（I…X），**不用**原版的 `enchantment.level.N`：
> 那是"代码里拼前缀、我们语言文件里一个键都没有"的一类，`check-lang.js` 的拼接键检查
> 会（正确地）判它"游戏里会显示成原始键名"；与其给检查器开白名单口子，不如维护十个常量。
> 效果名走原版 `MobEffect#getDisplayName()`，所以 11 个效果的中英名不用我们写。

## 3. 菜谱：三个数据来源，全是真源

| 界面上的内容 | 来源 |
|---|---|
| 这道菜能用哪些鱼 | `DishRecipe.allowedPairs()`（**配方表本身**） |
| 基础与配料（熟块 ×1 + 酱油 + 糖） | `DishRecipe.Dish#base()/baseCount()/extraItems()`（配方就是按它收料的） |
| 加工步骤 | 按 `base()` 分三种：切块→加热→合成 / 生食两步 / 整条下锅 |
| **每种配料怎么来** | **现场问客户端的配方管理器**（`getRecipeManager().getRecipes()`） |
| 吃了给什么效果、各多久 | `DishEffects.grantsFor(dishId, 档位)` |
| 回多少饱食度 | `FoodValues.dishHunger(档位)` 的六档阶梯 |

所以不会出现"菜谱说能做、实际做不出来"，也不会出现"菜谱写 8 点、吃到 6 点"，
更不会出现"界面里的酱油配方与数据包里的不一样"——**配料链是查出来的，不是抄的**。

### 2.1 12 道菜一道不少（2026-10-03 第二轮反馈）

用户："一个是菜谱不完善，12道菜只介绍10道"。

根因很具体：界面当时只遍历 `DishRecipe.Dish.values()`，而那个枚举里**只有工作台做的 10 道**。
熏鱼与炭烤鱼是**设备做的**（烟熏炉 / 营火，配方类型 `chunk_smoking` / `chunk_campfire`），
压根不属于那个枚举 —— 塞进去就得给它们造一个不存在的配方序列化器。

现在清单 = `Dish.values()`（10 道）+ `CookbookScreen.DEVICE_DISHES`（2 道）= **12**，
而且 `check-cookbook.js` 会拿它和 `ModItems` 里注册的成品菜**逐条对账**：
以后再加一道菜，菜谱里不写就红。

左侧列表也改成**两栏 6 行**：单列 12 行在矮窗口下会被 `UiLayout.rows()` 砍掉两行 ——
"少两道"正是用户看到的现象之一（他那一轮的报告里两件事叠在了一起）。

界面（`CookbookScreen`）与图鉴/指南同款：设计 400×224、按窗口现算面板尺寸、
文字一律走 `TextWidget`（本机环境下 `drawString` 是糊的，见 TextWidget 类注释）、
`isPauseScreen() = false`。左边一列 12 道菜点一下就切，右边给材料/饱食度/三档效果。
`tools/check-ui-fit.js` 已把菜谱纳入"四种窗口尺寸下都装得下"的验算。

### 3.1 为什么要走"请求 → 下发"两个包（明明内容都是静态表）

内容确实不需要同步，但**开界面这件事必须留在客户端专用类里**：
`CookbookItem` 在 common 侧，一旦在里面写 `Minecraft.getInstance().setScreen(...)`，
专用服务器加载这个物品类时就会去加载客户端类 ——
2026-10-03 本仓库正因为同类问题（对客户端类型做 `instanceof`）整个模组装不进专用服务器。
所以照抄图鉴书的形状：客户端发 `CookbookRequestPayload` → 服务端回 `CookbookPayload`
（空载）→ 由 `ClientPayloadHandlers`（`Dist.CLIENT`）开界面。
`check-cookbook.js` 有一条断言专门盯着这件事（负例 `cookbook-item-client-class`）。

## 4. 合成：一本书 + 任意熟鱼

```json
{ "type": "minecraft:crafting_shapeless",
  "ingredients": [ { "item": "minecraft:book" }, { "tag": "c:foods/cooked_fish" } ],
  "result": { "id": "anglertackle:cookbook", "count": 1 } }
```

用 NeoForge 通用标签 `#c:foods/cooked_fish`（原版熟鳕鱼/熟鲑鱼都在里面），
所以"原版任意熟鱼"成立，别的 mod 的熟鱼也顺带能用。
解锁材料由 `tools/gen-recipe-advancements.js` 从配方第一格推出来（`minecraft:book`），
不手写第二张表。

## 7. 档位文字必须带品质色（**颜色 = 品质**）

用户 2026-10-03："自查所有悬浮显示，如出现顶级鱼等该显示颜色的文本却是白色，就改一下。"

模组有一条贯穿全部界面的约定：**颜色 = 品质**（白绿蓝紫金红，见 `item/Quality.java`），
图鉴那一列一直就是这么做的。但悬浮显示是**一个个物品类各写各的**，
于是同一条约定在五个地方各自漏了一点 —— 都不报错、不崩，只是"看起来一样"：

| 位置 | 原来 | 症状 |
|---|---|---|
| `FishChunkItem` | 按 group 手写表（0 白 / 1 蓝 / 2 紫） | **绿档鱼块显示成白色**、**金红档的"顶级鱼排"显示成紫色** |
| `DishItem` | 档次段写死 `GRAY` | "顶级"和"普通"长得一模一样 |
| `FishItem` | 尺寸评级整行 `GRAY` | "纪录级"与"幼体"差 3.5 倍售价却同一个颜色 |
| `RodItem` | 档位上限那行整行 `AQUA` | 那一行的全部意义就是那个字（"金"），却和"白"一个色 |
| `ChumItem` | 自己抄了一份 `tierName`/`tierColor` 表 | 与 `Quality` 重复，迟早分叉 |

现在统一成：**档位文字一律 `Quality.of(tier).color()`**（tooltip）
/ **`Quality.of(tier).argb()`**（自绘界面，色值由 `ChatFormatting` 派生，
所以界面与 tooltip 是同一个来源），菜谱界面的"普通/优质/顶级"三档标签也照此上色。

> `Quality.argb()` 是这次新加的：界面用 int、tooltip 用 `ChatFormatting`，
> 两套颜色手抄两份必然分叉（"图鉴里金字、tooltip 里白字"），所以让 argb 从 color 派生。

守着它的是 `tools/check-tooltip-colors.js`：断言**盯着那一段组件本身的颜色**
（不是"文件里出现过 Quality"）—— 后者在"颜色改回灰色、别处还留一处 Quality.of"时会绿，
负例抓过这种漏检。
