## 3. ★ 经验 A：**永久有效**（铁律 —— 与本机、与模型都无关）

1. **新文件必须登记进 `tools/_negtest.js` 的 `FILES`。** 不登记的后果有两个，今天各发生一次：
   ① 负例改的是副本，副本里没这个文件 ⇒ **改坏了也不红**（假绿）；② 锚点预检直接报"找不到文件 X.java"
   ⇒ **整条负例阶段停摆**，而闸报的是"[负向测试未通过：存在漏检的检查脚本]"（看起来像检查器失效 ✗）。
2. **改实现要顺手改负例锚点**（`mutate` 里的 `from` 串）。锚点要挑"下一个人不会顺手改掉"的写法；
   锚点漂移的症状与上一条一模一样（都表现为"整段没跑起来"）。
3. **语言键中英成对、一次补齐**：新代码里用到的键缺一个 ⇒ `check-lang` 红；成就/委托这类
   "面板文案" 还会同时让 `check-quest` 那类检查红。
4. **新增一个 `check-*.js` 之后必须 `node tools/gen-progress.js --write`**（`docs/进度.md` 是生成物，
   表头的检查器数量由它数出来，`check-progress-doc.js` 会拿"表头 vs 磁盘真实条数"比对）。今天先红了一次。
5. **每条断言都要真的证伪过。** 今天的现场：我给"指令有没有接进 `register(...)`"写的断言只查
   "文件里有没有那串字符"，负例把调用**注释掉**之后那串字符**还在** ⇒ 断言照样通过 ⇒ 负例报"漏检"。
   改成盯**非注释行**（`/(^|\n)[ \t]*registerAchievements\(dispatcher\);/`）才真的能抓。
   **教训：断言写"存在性"时，先想"破坏者会不会把东西留在原地"。**
6. **一次只跑一条链**（构建 / 生成器 / 负例不许并发）；负例之前先跑 `node tools/_negtest.js --check-anchors`
   （0 秒、只读），别等整条闸跑四分钟才发现锚点没了。
7. **`-Filter <单条>` 不能用来跑负例**：runner 要求这一批里**至少有一棵对照组**（`expect: 0`），
   否则直接拒跑（"这批用例里一棵对照组都没有 —— 先别跑"）。这是**正确的守卫**：没有对照组就分不清
   "抓到了" 和 "检查器自己坏了"。要单验某组就用组名前缀（如 `-Filter achievement`）。

## 6. ★ 经验 D：**确认错误的答案**（试过、证伪过 —— 别再试）

1. ✗ **"`qq-mode-console` 缺 schemastery 依赖 / 从没激活过"** —— 两句话都错。它是**符号链接**到
   `Documents/dsh/qq-bridge/plugins/qq-mode-console`，而 qq-bridge 自带 `node_modules`（依赖能解析）；
   它**一直在激活**，日志（在 `qq-bridge/state/qq-mode-plugin.log`，**不在** `$DSH_HOME/state/`）显示
   每次都走到 `settings service unavailable` 后优雅退出 —— 真因是 **settings API 换代**：
   旧 `ctx.settings.register(ns, schema)` 已不存在（现为 `configure/describe/update/replace/mutate`），
   新版模型下**设置页 = 插件自己那一行的 `Config`**、`ns = patch 行 id`，且字段必须带 **`meta.volatile`**
   标记。已按此移植（patch 行 id 改成 `qq-mode`，桥零改动）。**待重启 DSH 验证。**
2. ✗ **"本地 `link:` 插件一定能解析 `@deepseek-ai/*`"** —— 取决于插件真身所在的那棵树有没有 `node_modules`。
   `$DSH_HOME\plugins\...` 下的 `link:` 插件**不会**被 pnpm 装依赖；qq-mode-console 之所以能跑，是因为它
   真身在 qq-bridge 里。
3. ✗ **"只发源码的仓库也能从 GitHub tarball 装"** —— 不可以（仓库里没有 `lib/`/`dist/`，构建要 devDependency）。
   实例：`dsh-file-review`、`@liustack/modlens`、`dsh-forge-studio` 全系列、`dsh-harness-ops`（它的真 bundle 在
   `plugins/dsh-restart-recover/` 子目录）。**改用 npm 同名包**（npm 包才带构建产物）；并且
   `install_bundle <名字>` 遇到"已装但来源不同"只会回 `restart-required` 而**不换源**，必须 `remove_bundle` 再装。
4. ✗ **DSH 的构建审批键 `onlyBuiltDependencies`** —— 它读的是 profile `pnpm-workspace.yaml` 的 **`allowBuilds`**；
   而且"待批准"的判定很特别：**值必须恰好是字符串 `set this to true or false`**，否则 `plugin_manager` 的
   `approvedBuilds` 只会回 `stale-approval`（`pendingBuilds` 恒为空）。
5. ✗ **GitHub 的 `github.com/<owner>/<repo>/archive/HEAD.tar.gz`** —— 这台机器上会被掐（21 秒超时）；
   **`codeload.github.com/<owner>/<repo>/tar.gz/HEAD` 一直通**。另外 host 进程的 PATH 里**没有 git**，
   所以 `github:owner/repo` 规格也走不通。
6. ✗ **"日志里没报错 = 插件在跑"** —— 本地 `link:` 插件既不走版本兼容闸、也不出现在 `warnings` 里。
   判定死活要看**它自己的日志文件**和它依赖的服务在不在。
