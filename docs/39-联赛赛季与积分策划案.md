## 2. 赛季与期（D1 已定）

```
期号(推送)  1 小型 → 2 中型 → 3 大型   ⇒ 都属【S1】
期号(推送)  4 小型 → 5 中型 → 6 大型   ⇒ 都属【S2】
期号(推送)  7 小型 → …                 ⇒ S3 …
```

| 项 | 规则 |
|---|---|
| **赛季号** | `S{n}`，`n = (期号 - 1) / 3 + 1`（整除，即每 3 期进一个赛季） |
| **季内三期** | **共用同一个赛季号**（所以同一赛季里"小型冠军"与"大型冠军"都叫 `S1…`，但规模词不同、不冲突 ✓） |
| **"每届/每期"** | 一次推送（一次签收窗口）为一届 ⇒ **商店限购按"届"刷新**（D11），即**一个赛季内刷新 3 次** |
| **现存实现的映射** | `LeagueData.seasonId`（全局递增）保持不变 ✓ **不重构**；赛季号由它现算（`(id-1)/3+1`）⇒ 改动最小 |

> ⚠ 三级轮转口径不变（`docs/37` §2.1：`allowConcurrent=false`）。若某服把 `allowConcurrent` 打开，
> 三期不再轮转 ⇒ **赛季号的界桩会漂**。⇒ 落地时必须**把"届序"单独计数**（见 §7 数据行），
> 不能靠 `seasonId` 推断"第几届大型" ✗。**这是本节最容易踩的坑，已列进 §8 断言。**

## 3. 联赛积分

### 3.1 产出规则（R3~R5，D4~D6 已定）

| 来源 | 分值 | 发放时机 |
|---|---|---|
| **每尾鱼基础分** | **5** | **当场**（钓上来就加） |
| 品质加成 | 白 **0** / 绿 **2** / 蓝 **5** / 紫 **10** / 金 **20** / 红 **32** | 同上 |
| ⇒ 单尾合计 | 白 5 / 绿 7 / 蓝 10 / 紫 15 / 金 25 / **红 37** | |
| 结算名次 第 1 | **1000** | **结算后**（排行榜定格） |
| 第 2 | **500** | 同上 |
| 第 3 | **300** | 同上 |
| 第 4~10 | **200** | 同上 |
| 第 11 名及以后 | **0**（但有上鱼分 ✓） | — |

- **资格**：只要**签收**过（= 参与联赛）且**在自己的 30 游戏分钟窗口内**上鱼 ⇒ **不看名次**都给分（D4）；
  未签收者、窗口外的鱼 ⇒ **不给**（沿用 `docs/37` §3.4 的计分口径，反刷）；
- **名次分**：只在**结算**时按最终名次发（D5/D6），与既有发奖流水同源、**先写键后加分**（幂等）。

## 5. 生成式称号（**D10，本轮最大的新增**）

### 5.1 需求

用户要的是：`S1大型联赛冠军`、`S1大型联赛亚军`、`S2大型联赛冠军`、`S1大型联赛纪念`、`S2大型联赛纪念`……
**每届都会产生新名字** ⇒ 静态表写不下（"不可能在预设里写几千行"）。

### 5.2 现状（读码结论，决定改造量）

| 现状 | 位置 | 影响 |
|---|---|---|
| 称号是**静态表** `Def(id, 品质, 可重复)` | `title/TitleDefs.java` | 没有"参数"概念 |
| 授予入口**唯一**：`Titles.grant()`，内部 `TitleDefs.byId(id)` **查表**，查不到就 `return false` | `title/Titles.java` | 动态 id 会**静默不授予** ✗ |
| 名称 = 语言文件 `title.anglertackle.<id>`，**逐处 `Component.translatable(nameKey(id))`** | `Titles.nameKey()` + **4 个渲染点**：`TitleScreen:186` / `AnglerCommands:674,714` / `TitleChatEvents:60` | 要做"带参数的名字"就得过这 4 处 |
| ⚠ **快照按静态表逐条发**：`TitleSnapshot.of()` 遍历 `TitleDefs.ALL` | `title/TitleSnapshot.java` | **动态实例不在 ALL 里 ⇒ 客户端根本看不到** ✗✗ **这是最容易漏的坑** |
| 玩家侧存储是 **`Set<String> owned`** + `Map counts`（×N） | `player/PlayerTitles.java` | ✅ **好消息：字符串集合天然能装多实例** |

### 5.3 设计：**模板 + 参数实例**

**① 新增 3 个"参数化模板"**（仍登记在 `TitleDefs`，仍守既有命名规则）：

| 模板 id | 名字模板 | 品质 | 授予 |
|---|---|---|---|
| `league_champ` | `S{n}{规模}联赛冠军` | 紫3 / 金4 / 红5（按规模，沿用现有 3 条冠军的颜色） | 结算名次 1 |
| `league_runnerup` | `S{n}{规模}联赛亚军` | 蓝2 / 紫3 / 金4（按规模） | 结算名次 2 |
| `league_third` | `S{n}{规模}联赛季军` | 白0 / 蓝2 / 紫3（按规模） | 结算名次 3 |
| `league_memorial` | `S{n}{规模}联赛纪念` | **金 4**（R8） | 商店 500 积分购买 |

> 品质梯度照搬既有 40 条的习惯（越稀有越高档、且与"规模"同向）：**冠 > 亚 > 季** ✓（D13）。

**② 实例 id 形如 `league_champ@S1-large`**（`@` 分隔；仓库里目前没有第二处用 `@`）：

```
模板id @ S<赛季号>-<规模>
        └─ 参数只有这两段，且都在白名单内（规模仅 small|medium|large，赛季号仅数字）
```

**③ 存储不用改**：`owned` 是 `Set<String>` ⇒ `league_champ@S1-large` 与 `league_memorial@S2-large` **天然共存** ✓（D8 的"多赛季共存"直接成立）。

**④ 授予入口改造**（唯一入口，只此一处）：`Titles.grant()` 里

```java
// 现在：TitleDefs.byId(id)  —— 查不到就 false
// 改成：先 byId(id)（老路不变），miss 时再 byInstance(id)（拆 @ → 校验模板+参数白名单）
```

**⑤ 名字渲染**：`nameKey(id)` 拆出模板后取 `title.anglertackle.<模板>`，语言文件写成**带参数**的：
`"S%s%s联赛冠军"`（`%s` 由 `Component.translatable(key, "1", "大型")` 传入）⇒ **4 个渲染点逐一过**。

**⑥ 快照补实例行**（本设计最关键的一步）：`TitleSnapshot.of()` 除遍历 `ALL` 外，**必须再把玩家 `owned` 里
"不在 ALL 里的实例 id" 追加成行**，否则客户端列表里看不到。⚠ 客户端 `TitleScreen` 的排序/分组也按 `ALL` 下标算 ⇒
实例行的排序规则要定（建议：紧跟其模板那一行之后，按赛季号升序）。

**⑦ 检查器（守"不许乱生成"）**：
- 实例 id **必须** = 已登记模板 + `@S<数字>-<规模>`，否则红；
- **源码里不许出现写死的未来赛季**（如 `league_champ@S7-large`）⇒ 负例：手写一条未来实例应当红；
- 模板命名仍守 `check-titles.js` 的三套命名数组（`NAME_TAILS` 等）；
- 语言文件与模板**一一对账**（缺 key 红）。

| 规则 | 做法 |
|---|---|
| **折叠成一行** | 同一模板（如"纪念"）**只占一行**，不铺开 |
| **优先显示本赛季** | 这一行上显示的名字是**与当前赛季相符**的那一条；没有本赛季的，退而显示**最近一季**（不倒序铺开） |
| **可展开符号** | 该行名字**右边一个可点的展开符号**（▸/▾）⇒ **点一下**才把"以前各赛季"的实例**逐条列出来**（按赛季号降序，最新在前） |
| **默认收起** | 列表默认全是收起状态 ⇒ 40 条静态称号的观感**不变** ✓（不展开就等于现在） |
| **交互=鼠标** | 展开/收起、选中、佩戴**全部用点击**（D15）；**不新增快捷键** ✓ 与现有界面的点击式交互一致 |
| **佩戴哪个** | 展开后点其中一条即佩戴该条（`equipped` 仍只存**一条** ⇒ 与现有 `equipped` 字段语义兼容 ✓） |
| **计数显示** | 折叠行右侧显示"共 N 条"（替代原来那个 ×N 的含义，但显示位置沿用 ✓） |

⚠ 落地注意：折叠 = **客户端展示层的归并**，**存储里仍是各自独立的一条**（`owned` 集合）⇒ 不引入新数据结构 ✓。

### 14.6 只读勘察补充（2026-10-13，**下一轮必须先看这一节**）

> 由探索型子代理做的**只读**勘察（符合 `AGENTS.md §一`：子代理只搜资料、不写码）。
> 下面每条都带行号，都是"不知道就会踩"的东西。

**A. 目录不是从 `RULES` 长出来的，而是从 `ModItems.java` 解析出来的** ⚠ 这是本轮最大的发现
`gen-shop-prices.js:66-101` 只认那 7 类 id（rod/line/reel/hook/lure/bait/chum 的正则）⇒
**原版物品、附魔书、称号根本产不出 `new Entry(...)`**。
⇒ 上一版 14.1 里"扩 `Entry` 字段"这条**仍然要**，但还得多一件事：**让生成器支持"非 ModItems 来源"的条目**
（或在 `ShopCatalog` 里加一份独立的 `POINTS` 表）。**这条必须先定，否则后面全是白工。**

**B. `ShopManager.buy` 的 `switch (e.kind())` 没有 `default`**（`ShopManager.java:175`）
⇒ 加了 `Kind.POINTS` 而忘了写分支：**编译不报错、不扣任何货币、直接走到发货** ⇒ **白送** ✗
（这条要写进负例：把 POINTS 分支删掉，必须红。）

**C. `give(ServerPlayer, Entry)`（:318）只会 `new ItemStack(item)`，而且硬编码 `anglertackle:` 命名空间**
⇒ 附魔书 / 固定品质鱼 / 原版物品 / 称号**都不能复用它**。
真正具备那两种能力的是：`exchangeFish`(:340) → `ShopMaterials.resultStack(Player, Exchange)`(:227，附魔在 247-261、固定鱼在 242-246)；
通用给物是 `give(ServerPlayer, ItemStack, String)`(:366)。称号走 `Titles.grant(ServerPlayer, String)`(:179，唯一入口)。
⇒ POINTS 分支要**自己写发货**（照 `exchangeFish` 的路子）。

**D. 界面不是两处，是四处**（14.3 那条要扩）
- `ShopScreen.drawEntry`(:517-549)：价格分支是 `FREE / BUY / else` ⇒ `POINTS` 会落进 `else` **被画成"兑换"** ✗；
- **`ShopScreen.TABS`(:44) 与 `TAB_RATING/TAB_SELL/TAB_REPAIR/TAB_EXCHANGE`(:47-51) 的下标要整体顺延**（加一个分类 = 多一个页签）；
- `ShopTooltipEvents` 的 `switch (entry.kind())`(:72) 也**没有 `default`** ⇒ `POINTS` 会**整段不显示价值**；
- 同文件 `find()`(:97-106) 第 99 行"命名空间不是 `anglertackle` 就 return null" ⇒ **原版物品/附魔书/称号永远没有商店 tooltip**（要用联赛商品就得放宽这条）。
- `ShopDebug.catName`(:94-103) 是**枚举 switch 表达式**，不补 `case LEAGUE` 会**编译失败**（穷尽性）。
