# 09 · 原版机制冲突与渲染优化

> 📌 **开工必读** —— 本文件是《垂纶》策划族的一员。动手前先读 `docs/CONVENTIONS.md`（协作规则 + 每轮自我暗示）与 `docs/接力.md`（接手须知）；项目记忆只认 `docs/` 下的文件。

> 起因：你指出"高级鱼线线长 70 格，但很多玩家渲染距离约 64 格以内，需要给浮漂单独做渲染优化"。
> 我核对了原版与 NeoForge 的实际机制，发现这里有**三层**独立的距离限制，比他预想的还多一层。本文档逐条给出结论与对策。

---

## 1. 三层距离限制（先搞清楚到底是哪一层在拒绝渲染）

| 层 | 机制 | 典型值 | 是否可被模组修改 | 后果 |
|---|---|---|---|---|
| **L1 · 服务端实体追踪范围** | `EntityType.Builder#clientTrackingRange(区块数)`，决定服务器把实体**同步给**哪些客户端 | 原版浮漂约 **4 区块 = 64 格**；NeoForge 默认 5 区块 = 80 格 | ✅ **可以**（注册时设定） | 超范围时客户端**根本收不到这个实体**——不是"不渲染"，是"不存在" |
| **L2 · 服务端实体激活范围 / DAB** | 实体距玩家过远时降低 tick 频率（DAB：>8 格开始降频，20 格以上最慢每 60 tick 一次）；MISC 类激活范围约 8 格 | 8 / 20 格 | ✅ 可以（请求强制 tick） | 70 格外的浮漂**可能每 3 秒才 tick 一次**，张力判定直接崩 |
| **L3 · 客户端区块视距** | 玩家设置里的渲染距离（2–32 区块） | 常见 8–12 区块（128–192 格），低配 4–6 区块（64–96 格） | ❌ **不能**（玩家设置优先） | 即使前两层都放开，**视距外仍然看不见** |

**关键结论（官方文档原文意思）**：`clientTrackingRange` **若大于客户端区块视距，则以客户端视距为准**（见 [NeoForge 官方 Entities 文档](https://docs.neoforged.net/docs/1.21.5/entities/)）。所以：

> ❌ 单靠把 `clientTrackingRange` 调到 10 区块**解决不了"玩家视距只有 4 区块"的情况**。
> ✅ 必须配合**不依赖实体的渲染兜底方案**（§4 的"幽灵鱼线"）。

## 2. 七种"顺手改原版"的冲突（我全部避开了）

| # | 直觉做法 | 会踩的坑 | 我们的做法 |
|---|---|---|---|
| 1 | 直接把原版 `FishingHook` 的 `clientTrackingRange` 改大 | `FishingHook` 的 `WATER_CHECK_RANGE`(4) / `MAX_DISTANCE_TO_BOBBER_SQ`(`public static final int = 1024`，即 32 格) 是 **`public static final` 字段**，改它等于把**所有用原版钓竿的玩家**（包括其他模组的）行为一起改了 | ✅ **完全新建 `DeltaBobberEntity`**，不碰原版 `FishingHook`。原版钓鱼竿照旧走原版逻辑，两条路互不干扰 |
| 2 | 给原版钓鱼竿挂事件实现新玩法 | 与其他钓鱼模组必然冲突；玩家分不清"这根竿是新的还是旧的" | ✅ 新的钓竿物品**独立物品**，配方独立；原版竿保持原样 |
| 3 | 在 `InputEvent.MouseButton.Pre` 里直接吃掉左键 | 玩家在钓鱼时想挖方块/攻击会被吞掉；更糟的是拦截到全局，**破坏挖掘与 PvP** | ✅ 只在**同时满足**三个条件时拦截：① 当前存在活跃钓鱼会话 ② 会话状态 ∈ `{FIGHT}` ③ 手持本模组钓竿。其他情况一律放行。且提供配置 `input.interceptAttackKey=false` 关闭 |
| 4 | 自己写一套耐久扣减 | 与"耐久""经验修补"附魔以及铁砧修复逻辑打架，可能出现耐久不扣或双倍扣 | ✅ 复用原版 `ItemStack#hurtAndBreak`（服务端），耐久/修补自动联动；自定义的"咬钩损耗"只是**调用它的一个来源** |
| 5 | 用 `Blocks.WATER` 判定水体 | 1.21 里大量水体是 `waterlogged` 状态（楼梯/栅栏/海草/脚手架），单纯判 `Blocks.WATER` 会漏判 | ✅ 同时判定 `FluidState#is(Fluids.WATER)` 与 `BlockState#getValue(WATERLOGGED)`；"含水方块"只算水深 1（不够 2 格就进浅水池） |
| 6 | 用全局 `Level#tick` 遍历所有玩家 | 与服务器性能优化/其他模组抢 tick；多人时开销线性上升 | ✅ 用 NeoForge 的 `ServerTickEvent.Post` + 只在**活跃会话表**上迭代（没有会话时零开销） |
| 7 | 让实体鱼用 `MobCategory.WATER_CREATURE` 自然刷 | 占用原版水生生物上限（5），会把鱿鱼/海豚挤掉，整合包里被骂 | ✅ 走**独立生成器**（自定义 `MobCategory` 或按区块手动管理），完全不占原版 spawn cap【开放项10：实体鱼系统开关】 |

## 3. 原版机制的**正常**依赖（这些是好事，不要对抗）

| 原版机制 | 我们的用法 |
|---|---|
| `ItemStack#hurtAndBreak` | 鱼竿耐久扣减的标准入口，自带耐久/修补附魔联动 |
| `ItemStack#isDamageableItem` / `getMaxDamage` | 鱼竿 "2000 耐久起步"就用原版耐久字段实现（而不是自定义数值） |
| `EnchantmentHelper` | 海之眷顾/饵钓的等级读取 |
| `FluidState` / `FluidTags.WATER` | 水体判定的唯一正确方式 |
| 原版音效 `entity.fishing_bobber.splash` / `.throw` | 落水/抛投音效直接复用，省一半音效工作量 |
| 原版粒子 `bubble` / `fishing` / `crit` | 窝子与水面反馈粒子 |
| `SavedData`（维度存储） | 排行榜数据持久化 |
| `AttachmentType` | 玩家数据（等级/鱼币/图鉴），设置 `copyOnDeath` |
| 原版实体剔除机制 | 会话结束后**主动交还**控制权，让浮漂按普通规则被剔除，不留常加载负担 |

## 4. 浮漂渲染优化方案（本方案核心）

### 4.1 实体注册参数（L1）

```java
// ModEntities.java
public static final Supplier<EntityType<DeltaBobberEntity>> DELTA_BOBBER =
    ENTITY_TYPES.register("delta_bobber", () -> EntityType.Builder
        .<DeltaBobberEntity>of(DeltaBobberEntity::new, MobCategory.MISC)
        .sized(0.25f, 0.25f)
        .clientTrackingRange(DeltaFishingConfig.bobberTrackingRangeChunks)  // 默认 10 区块 = 160 格
        .updateInterval(1)        // ★ 每 tick 同步（默认 3 对拉力判定太慢）
        .noSummon()               // 禁止 /summon
        .fireImmune()
        .build(ResourceKey.create(Registries.ENTITY_TYPE, rl("delta_bobber"))));
```

> `updateInterval(1)` 很关键：原版浮漂默认每 3 tick 才发一次位置更新，做**张力判定**够用，但我们要画"鱼线张力抖动"，位置更新必须每 tick。

### 4.2 强制 tick（L2）

```java
// DeltaBobberEntity.java
@Override
public void tick() {
    super.tick();
    // 会话期间：即使离玩家 70 格，也保证每 tick 都被 tick
    if (this.isInActiveSession()) {
        this.setDeltaMovement(...);   // 张力/挣扎模型推进
    }
}

// 关键：豁免"距离激活"剔除
@Override
public boolean shouldBeSaved() { return this.isInActiveSession(); }

// 向服务端声明本实体不可被"远距离降频"（NeoForge 会在实体 tick 时检查）
// 1.21.1 具体实现：在 ModEntities 注册时使用 MobCategory.MISC +
// 会话期间调用 chunkMap 的 forced-tick 请求；详见 M1 实现说明
```

**性能代价与回收**：
- 单个会话期间，服务端多 tick 1 个实体、多发 1 个实体位置包 → 开销可忽略。
- **会话结束（上鱼/断线/取消）后立即取消强制 tick**，浮漂按普通实体规则处理，3 秒内消失。
- 全局同时活跃会话上限 = 玩家数（每个玩家最多 1 个），不存在被滥用刷量的可能。

### 4.3 幽灵鱼线（L3 兜底）★ 这是解决你担忧的关键

**问题**：玩家视距只有 4 区块（64 格）、抛了 70 格 → 客户端区块根本没加载，浮漂实体即使收到了也不可见。

**方案**：把"鱼线渲染"与"实体是否存在"**解耦**。

```
                            客户端渲染优先级
                                    │
      ┌─────────────────────────────┼─────────────────────────────┐
      │                             │                             │
  距离 ≤ 视距且实体存在          实体不存在（超视距/超追踪）        距离 > 64 格
      │                             │                             │
      ▼                             ▼                             ▼
  完整渲染：                    幽灵鱼线：                     简化线型：
  · 浮漂模型 + 上下浮动          · 用会话同步包里的            · 从竿尖直接连到落点
  · 鱼线带下垂曲率                 落点坐标绘制鱼线               （不做下垂曲率）
  · 水面涟漪/水花粒子            · 线末端画一个                · 颜色仍按张力变化
  · 鱼线颜色 = 张力               "落点标记"（小圆环）           · 不做粒子
                                 · 颜色仍按张力变化
```

**实现要点**：

1. 会话同步包（`SessionSyncPayload`，每 2 tick 一发）里**始终包含落点的绝对坐标**，与实体是否存在无关。
2. 客户端 `GhostLineRenderer` 在 `RenderLevelStageEvent` 的 `AFTER_TRANSLUCENT_BLOCKS` 阶段绘制；绘制前检查"该实体是否已被客户端渲染"，避免重复画两条线。
3. 线宽与颜色：
   - 世界内实际线宽 **1.5 px**（太细看不见，太粗违和）
   - 颜色直接取张力映射表（白/黄/红/深红闪烁），**不做渐变纹理**，纯色 + 张力越高略微加亮
4. 超过 64 格自动切简化为直线（省去曲率计算，也避免远处抖动看起来像 bug）。
5. **性能**：幽灵线只是一个 `LineRenderer` 的 2 个顶点，可忽略不计。

### 4.4 鱼线曲率（视觉细节）

原版钓鱼线是"竿尖 → 浮漂"的直线，带一点随距离的弧度。我们沿用这个做法，但增加**张力对曲率的影响**：

| 张力 | 线型 |
|---|---|
| 白区（0–55） | 明显下垂弧度（松弛），中点下垂 0.35 格 |
| 黄区（55–82） | 轻微下垂，中点下垂 0.15 格 |
| 红区（82+） | 完全绷直（下垂 0），且线略微抖动（每 tick 随机偏移 ±0.01 格） |

> 这一段是"看线就知道张力"的核心——**玩家甚至可以不看 HUD**。

### 4.5 视距低于抛投距离时的体验补偿

如果玩家视距 4 区块（64 格）而抛了 70 格：

- **不阻止抛投**（阻止会让高级鱼线失去意义）
- 客户端显示落点标记 + 幽灵鱼线（能看见线和水面的标记）
- HUD 的距离数字照常更新
- **首次发生**时给一次提示：`"你的渲染距离较短，远处的浮漂只显示落点标记（设置→视频设置→渲染距离）"`
- 配置项 `render.warnShortViewDistance = true`

## 5. 其他可能被忽视的原版交互

| 场景 | 原版行为 | 我们的处理 |
|---|---|---|
| 玩家在水中抛竿 | 原版浮漂会随水流漂动 | 我们的浮漂也会随水流轻微漂移（增加真实感），但**不漂出鱼线长度限制** |
| 下雨时水面 | 原版雨滴粒子 | 复用；雨天还会在浮漂周围生成额外涟漪（配合"雨天咬钩快"的反馈） |
| 水下呼吸/溺水 | 玩家在水里憋气 | 站在水里钓鱼超过 15s 给一次"注意呼吸"提示（不强制） |
| 船/木筏上钓鱼 | 原版可行 | 支持；船上抛竿的射程 +10%（从高处抛） |
| 潜行时 | 原版降低移动速度 | 不影响钓鱼 |
| 视角切换（F5） | 第三人称 | 张力 HUD 与鱼线渲染都正常（不依赖第一人称） |
| 玩家死亡 | 物品掉落 | 渔具包设置 `copyOnDeath`（不掉落）；普通鱼获正常掉落 |
| 他人拾取浮漂 | — | 浮漂只能被主人收回；其他玩家右键无效 |
| 命令 `/kill` 浮漂 | 会移除实体 | 会话检测到实体消失 → 走"逃脱"结算 |
| 区块被卸载（服务端） | 实体停止 tick | **会话期间对浮漂所在区块请求 ticket**（加载但不强加载）；会话结束释放 |
| 与光影/优化模组（Sodium/Iris） | 可能不渲染自定义线 | 用标准 `RenderType.lines()`，Sodium 兼容；若检测到不兼容则在配置里提示 |
| 与其他钓鱼模组共存 | 双方都加钓竿 | 无共享状态、无 mixin 覆盖，可共存 |

## 6. 结论：三条必须落到代码里的硬约束

1. **绝不修改原版 `FishingHook` 的静态字段**，新玩法走独立实体 —— 这一条保证了"和原版零冲突"。
2. **浮漂的追踪范围（10 区块）与 tick 频率（每 tick）在会话期间单独设定，会话结束立刻交还** —— 既解决 70 格问题，又不留性能债。
3. **鱼线渲染不依赖实体存在**（幽灵鱼线 + 落点标记 + 超 64 格简化线型）—— 这才是在"玩家视距 4 区块"这个不可控变量下的唯一可靠方案。

> 附：`clientTrackingRange` 大于客户端视距时以视距为准，出自 NeoForge 官方文档（[Entities · NeoForged Docs](https://docs.neoforged.net/docs/1.21.5/entities/)）；
> 远处实体降频（DAB，8 格起降频 / 20 格以上每 60 tick 一次）出自第三方技术文档（[Entity (de)spawning and AI](https://github.com/vibecentralmc/wiki/blob/main/technical/entity-de-spawning-and-ai.md)），该文档描述的是特定服务端实现，原版行为相近但具体阈值可能不同 —— **M1 阶段我会写一个实测命令 `/anglertackle debug tickrate` 直接测出我们实体在不同距离下的真实 tick 频率**，用实测数据而不是文档猜测来定案。
