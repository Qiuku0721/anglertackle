## 1. 已定案的决定

| # | 决定 | 备注 |
|---|---|---|
| 1 | **钓上来给物品** | 不改现有链路（图鉴/售价/商店卖鱼/战利品表全建立在"鱼是物品"上） |
| 2 | **水族箱是容器方块**：把鱼物品放进去 → 转成实体 → 约束在箱内游动 | 实体是"鱼的展示形态" |
| 3 | **合成**：任意模组鱼 ×1 + 玻璃 ×8 → **水族箱 ×8** | 一次出 8 块，和玻璃的产出比一致 |
| 4 | 外观：**透明，方块边缘是框**；连接处**不能每个面 4 条边** | 要参考"无缝玻璃"类 mod 的做法 |
| 5 | 另有**放生台**（可选路线）：鱼进去 → 实体出现在最近的可放水域 | 给不想建缸的玩家一条路 |

## 2. 体积门槛（用户原话："格数恰好是正方体构成所需"）

| 鱼的体型 | 需要的水族箱格数 | 正方体 |
|---|---|---|
| 小型鱼 | **≥ 2** | 1×1×2（竖着两格） |
| 中型鱼 | **≥ 8** | **2×2×2** |
| 大型鱼 | **≥ 27** | **3×3×3** |

- **"格数" = 连在一起的水族箱方块数量**，不是空间体积
- **想要多种鱼同时观赏，就要更多方块** —— 即每条鱼**各自占用**一份体积，
  不是"整箱共用一个门槛"
- ⚠ 待确认：小型鱼的 2 是 `1×1×2` 还是 `2×1×1`？还是"必须构成一个长方体"？
  （8 和 27 都是正方体，2 只能是 1×1×2 的长方体，所以门槛大概是"**连通格数**"而非形状）

## 3. 技术方案

### 3.1 方块与方块实体

- `AquariumBlock extends BaseEntityBlock`，`noOcclusion()`、`isViewBlocking → false`、
  透光（类似玻璃：`propagatesSkylightDown`）
- `AquariumBlockEntity`：存
  - 箱内**实体 UUID 列表**（真鱼实体）
  - 或者：实体自己带着"我被关在哪个箱子"（见 3.4）
- 水的处理：箱内是否要**真水**？两个选项：
  - **真水**（箱内是 `minecraft:water`）：鱼能正常呼吸、能用桶捞，但方块要 `BucketPickup` 逻辑
  - **无水**（方块自称是水）：`canRandomSwim` 需要骗过 `isInWater()`
  - **建议真水**：少骗系统，`AbstractFish` 的游泳/呼吸全部照常工作

### 3.2 连接检测

用**方块状态 6 个方向布尔**，和原版玻璃板/铁栏杆同一个套路：

```java
public static final BooleanProperty NORTH, SOUTH, EAST, WEST, UP, DOWN;
```

- `getStateForPlacement`：放置时按邻居设初值
- `updateShape`：邻居变化时重算（`BlockUpdate` 里自动调）
- 判据：邻居也是同种方块（或同属一个多方块结构）

**blockstate json 用 `multipart`**：
- 一个"中心/内核"模型（永远渲染）
- 6 个方向各一个"边框"模型，**只在对应方向不连接时**渲染

这样连成一片时，内部的面不画框 → 正是用户要的"不会每个面 4 条边"。

> 这是**标准做法**（原版铁栏杆、玻璃板、栅栏都是这个思路）。
> 需要 7 个模型 json（1 核心 + 6 面框）+ 1 个 multipart blockstate。

### 3.3 体积统计（连通分量）

放置/破坏时对连通的水族箱方块做 **BFS 洪水填充**，得到：
- 连通组的总格数
- 组内所有方块坐标（用于约束鱼的游动范围）

⚠ **性能**：每次放/拆都 BFS 一次。上限可以设死（比如 BFS 超过 512 格就停止并标记"太大"），
避免玩家用几千个方块拖死服务器。

⚠ **不要在 tick 里 BFS**。只在方块变化时算，结果缓存进 `AquariumBlockEntity`。

### 3.4 实体约束

鱼实体每 tick 需要知道"我能游到哪"。两种做法：

| 做法 | 优点 | 缺点 |
|---|---|---|
| **A. 鱼自己找家**：实体存 `home`（连通的方块集合包围盒），用"限制在家附近"的 AI 目标 | 我已经在 `FishermanEntity` 上写过这个模式（`StrollNearHomeGoal`） | 包围盒是**长方体**，L 形水箱里鱼会游进"空气"（其实没方块的地方） |
| **B. 逐 tick 检查所在方块**：鱼每 tick 确认脚下/所在格是水族箱方块，不是就往回推 | 精确，能处理任意形状 | 每 tick 一次方块查询 × N 条鱼 |

**建议 B 的简化版**：鱼每 **10 tick** 检查一次所在位置；不在箱内就把速度朝最近的水族箱方块推。
配合 A 的包围盒做粗筛，开销可以接受。

**游动范围**还要和"占用体积"挂钩：每条鱼占用 N 格，箱子的**有效容量 = 总格数 / 每条鱼的门槛**。
超了就不让再放。

### 3.5 放生台

- `ReleasePlatformBlock`：右键放入鱼物品 → 转成实体
- 实体生成位置：**距离放生台最近的 2×2×2 水域**
  - 搜法：以放生台为中心向外做螺旋搜索，找到第一个满足"2×2×2 全是水"的位置
  - 找不到 → 提示玩家"附近没有足够的水"
- 用途：不想建缸的玩家也能把鱼变成实体

## 5. 已知难点与取舍

### ① 无缝边框的关键在 blockstate，不在贴图

很多人第一反应是把边框画进贴图，然后靠"连接时换贴图"解决 —— **做不到**，
因为方块模型是烘焙好的，运行时换不了。正确做法是 `multipart`：
**每个方向一个独立的边框模型**，按连接状态决定渲不渲染。

### ② 空腔 vs 实心

水族箱内部如果是**真水**，那它的方块本身就不能是完整立方体（否则水被挤掉）。
需要 `noOcclusion()` + 自定义碰撞箱（只挡边框那一圈，或者干脆不挡）。

但**不挡**的话玩家会掉进去。所以：碰撞箱 = 完整立方体，但**渲染**只有边框。
（玻璃方块就是这么干的：`isViewBlocking → false` + 完整碰撞箱。）

### ③ 鱼类实体的呼吸

真鱼在水里 `handleAirSupply` 正常；一旦玩家把箱子拆了，鱼会**搁浅扑腾**
—— 这其实是好效果，但如果是"拆一块就整组失效"，会一次掉出一堆鱼。
需要在破坏方块时把箱内实体**放出来**（掉在原地）而不是杀掉。

### ④ 体积门槛的形状

用户说"格数恰好是正方体构成所需"。8 和 27 是 2³/3³，但 **2 不是任何正方体**。
所以有两种读法：
- **读法一（推荐）**：门槛就是**连通格数**，2 = 1×1×2
- **读法二**：门槛是"能内切一个 N³ 正方体"

两者对 8/27 结果相同，只有 2 有歧义。**默认按读法一实现**，如果用户要读法二，
小型的门槛会变成 1（1×1×1）。

## 6. 与现有系统的接口

- **鱼的物品**：`FishItem` + `FishData` 组件（已有）。放进水族箱 = 消费一个物品、生成一个 `ModFish` 实体
- **鱼的实体**：`ModFish` + `ModEntities.FISHES`（S1 已完成 ✅）。实体靠 `speciesId()` 决定贴图
- **鱼的体型**：`FishSpecies` 的 `kgMin/kgMax` → 分小/中/大三档，对应 2/8/27
- **图鉴**：放生/养鱼**不影响**图鉴（图鉴记的是"钓到过"，不是"养着"）

## 8. 补充定案（2026-07-01 用户答复）

### 8.1 方块自身是水，**外壳硬、内部空**

用户原话："方块自身是水，连接成的方块内部像没有方块一样方便自由移动，
但方块外壳像石头一样硬。"

**这直接决定了碰撞怎么实现** —— 不是"整块有碰撞"（那是玻璃），
而是"**只有暴露的面有薄壁**"：

```java
@Override
protected VoxelShape getCollisionShape(BlockState state, BlockGetter level,
                                       BlockPos pos, CollisionContext ctx) {
    // ⚠ 用 **blockstate 里的连接布尔**，不查世界 —— 这个方法是碰撞检测每帧都会调的，
    //   里面再 getBlockState 六次会很痛。连接状态本来就已经在 state 里了。
    VoxelShape shape = Shapes.empty();
    if (!state.getValue(NORTH)) shape = Shapes.join(shape, WALL_NORTH, BooleanOp.OR);
    if (!state.getValue(SOUTH)) shape = Shapes.join(shape, WALL_SOUTH, BooleanOp.OR);
    if (!state.getValue(EAST))  shape = Shapes.join(shape, WALL_EAST,  BooleanOp.OR);
    if (!state.getValue(WEST))  shape = Shapes.join(shape, WALL_WEST,  BooleanOp.OR);
    if (!state.getValue(UP))    shape = Shapes.join(shape, WALL_UP,    BooleanOp.OR);
    if (!state.getValue(DOWN))  shape = Shapes.join(shape, WALL_DOWN,  BooleanOp.OR);
    return shape;
}
```

壁厚建议 **1/8 格（2 像素）**：太薄会穿模，太厚会挤压鱼的活动空间。

**效果**：
- 2×2×2 的缸 → 8 个方块各贡献"朝外的薄壁"，内部是一个接近 2×2×2 的空腔
- 鱼在空腔里自由游（`WaterBoundPathNavigation` 不会被卡）
- 玩家从外面撞是硬的，进不去
- **拆掉一块就破了个洞** —— 正好配合"破坏时把鱼放出来"

### 8.2 每条鱼占用的体积 = 它的门槛

即 **27 格的箱子能养 1 条大型鱼，或者 13 条小型鱼**（`27 / 2 = 13`，向下取整）。

### 8.3 放生台：做

不再列为可选项，进入 A5。

### 8.4 还没答的两条

- **小型鱼的 2 格**是 1×1×2 长方体还是内切 1×1×1？（8/27 无歧义，只有 2 有）
- 水族箱**能不能被活塞推动 / 被爆炸破坏**？
  - 建议：**禁止活塞推动**（多方块结构一推就散架，而且连接状态会错乱）
  - 爆炸：允许破坏，但要走"把箱内鱼放出来"的那条路径

## 9. 施工记录（2026-10-01，A2–A5 全部落地）

### 9.1 没有用方块实体 —— 与本文件 §3.1 的初版方案不同

§3.1 写的是"`AquariumBlockEntity` 存箱内实体 UUID 列表"。真动手时发现一个绕不开的问题：
**3×3×3 的缸有 27 个方块实体，哪一个说了算？** 引入"控制器 + 从属"之后，还要处理
控制器被拆、控制器所在区块没加载而另一块加载了、多人同时放鱼……每一种都是一类难查的 bug。

最后改成**不存状态、现算**（`block/AquariumTank.java`）：

| 需要什么 | 怎么得到 |
|---|---|
| 体积 | 从被右击的那一格出发的 BFS 连通分量，**只在右键时算**，上限 512 格 |
| 缸里有哪些鱼 | 问世界要包围盒里的 `ModFish`，再筛"确实落在体积里"（L 形缸靠这一步才准） |
| 鱼的个体数据 | 存在**鱼实体自己身上**（`ModFish.fishData`，用 `FishData.CODEC` 落盘） |

于是唯一的事实来源是"世界 + 实体"，两者的存盘与同步由引擎保证，
没有任何跨方块的一致性问题。`AquariumBlock` 因此仍是普通 `Block`，**没有方块实体**。

### 9.2 体型分档用这条鱼自己的体长，门槛 30 / 80 cm

§6 原写"按 kgMin/kgMax 分档"，实际用个体体长：

| 体长 | 占格 | 形状 |
|---|---|---|
| < 30 cm | 2 | 1×1×2 |
| 30 – 80 cm | 8 | 2×2×2 |
| ≥ 80 cm | 27 | 3×3×3 |

30 这个数**不是新拍的**：外形管线里 `shape.style` 的分界也是 30 cm（小于 30 走鳕鱼模板），
所以"小鱼"在容量系统和外形系统里是同一批鱼。用个体体长而非物种区间，
效果是"同物种里的大个体要多占地方"，比"按物种一刀切"更好理解。

### 9.3 §7 开放项的最终口径

| # | 问题 | 口径 |
|---|---|---|
| 1 | 小型鱼的 2 格 | 按 §5④ **读法一**：连通格数 2，即 1×1×2 |
| 2 | 箱内真水？ | **真水**。`getFluidState` 返回水源；`pickupBlock` 返回 EMPTY，桶舀不走 |
| 3 | 每条鱼占多少 | 就占它自己的门槛（§8.2）；容量 = 总格数 − Σ 各鱼门槛 |
| 4 | 放生台 | **做**（§8.3），`ReleasePlatformBlock` |
| 5 | 活塞 / 爆炸 | 活塞**推不动**（`getPistonPushReaction → BLOCK`）；爆炸允许，走 `onRemove` 放鱼 |

没有个体数据的鱼（野生鱼自己游进缸）按中型 8 格算 —— 极少数情况，
按中位数比按最小算保守：宁可少放一条，也不要让缸超载。

### 9.4 交互口径

| 操作 | 行为 |
|---|---|
| 手持鱼右键缸 | 容量够就放入（消耗 1 个物品），不够则**不消耗**并提示"共 N 格、已占 M 格、这条还要 K 格" |
| 空手右键缸 | 取出**离玩家最近**的那一条，个体数据原样还原（还是原来那条 42.3cm/1.2kg） |
| 拆掉任意一块 | 缸里所有鱼**解除圈养**，在原地搁浅扑腾 —— 绝不杀（§5③） |
| 被圈养的鱼出界 | 每 10 刻确认自己站的那格还是水族箱，不是就拉回去（兜底，不是主逻辑） |

### 9.5 踩到的坑：3D 方块物品必须挂 `parent`

自定义模型里写了 `elements`、又没写 `parent` 时，方块拿在手上**一点缩放都没有** ——
表现是"手上一块占满屏幕的巨物"（用户截图就是这个）。原版方块物品全部靠
`minecraft:block/block` 提供 GUI / 手持 / 掉落 的位移与缩放，所以正确做法是照原版挂上它。

⚠ 这个坑**和是否手写数值无关**：手抄一遍原版的变换几乎一定会抄错。
实际去 1.21.1 客户端 jar 里把 `assets/minecraft/models/block/block.json` 挖出来看，
第一人称其实是 `rotation [0,45,0] / translation [0,0,0] / scale 0.40`，
fixed 是 `0.5` —— 和"凭印象写"的版本差得很远。

`tools/check-aquarium-tank.js` 的 A 组现在会遍历 `models/item/` 的 parent 链，
"有 elements 却没有任何 display 变换"直接报错，所以这个 bug 不会再有第二次。
