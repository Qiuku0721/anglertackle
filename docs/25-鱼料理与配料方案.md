## 1. 设计目标

| # | 目标 | 含义 |
|---|---|---|
| 1 | **三档鱼肉统一所有鱼** | 28 条鱼只产出 **3 种**食材物品；贴图只需 3 张（而不是 28×N 张） |
| 2 | **数据跟着走** | 鱼块里刻着"哪条鱼、什么品质、多重"，tooltip 一眼看得到 |
| 3 | **档位决定料理上限** | 普通鱼块做家常菜、优质鱼肉做讲究菜、顶级鱼排做刺身/蒲烧 |
| 4 | **主料永远只有鱼** | 不搭配任何其他食材也能做出来；调料是**可选升级** |
| 5 | 只用 **3 个**新调料 | 盐 / 酱油 / 芥末；其余"葱姜蒜油糖"全借原版物 |
| 6 | 每个数字都能被检查器守住 | 不靠"感觉好吃" |

**明确不做**：❌ 多食材大菜（红烧/酸菜鱼那种）；❌ 食物腐败；❌ 生吃淡水鱼的负面效果。

## 2. 核心：三档鱼块（鱼类食材预处理）

### 2.1 三档的定义

| 档位 | 物品 | id | 由什么鱼切出 | 贴图 |
|---|---|---|---|---|
| 一档 | **普通鱼块** | `fish_chunk` | 品质 **白 / 绿** 的鱼 | 1 张（三档共用同一套风格） |
| 二档 | **优质鱼肉** | `fine_fish_meat` | 品质 **蓝 / 紫** 的鱼 | 1 张 |
| 三档 | **顶级鱼排** | `supreme_fish_steak` | 品质 **金 / 红** 的鱼（**观赏鱼除外**） | 1 张 |

> **理由（现实依据）**：鱼肉本来就按颜色分**白肉 / 粉肉 / 红肉**三类 ——
> 白肉鱼（鳕、鲈、鲫）细腻清淡、粉肉鱼（鲑、鳟、鲷）居中、红肉鱼（金枪、鲣）味重适合生食。
> 三档正好对上，不需要向玩家解释为什么这么分。

### 2.2 tooltip 与数据组件

```
普通鱼块
鲫鱼 · 白
—————————
可做：清烤 / 鱼汤 / 炸鱼块
```

- 物品名固定（`普通鱼块`），**第二行**显示来源：`<鱼的中文名> · <品质中文名>`
  （如 `鲫鱼 · 白`、`蓝鳍金枪鱼 · 金`）
- 第三行起显示"这一档能做哪些料理"（由档位查表，不写死文案）
- 数据组件 `fish_material`：`{ fish_id, tier(0~5), weight_kg, ornamental(boolean) }`
  —— 重量保留是为了后续显示与统计，**档位已经决定了一切**，重量不再影响料理

⚠ **堆叠规则**：MC 按组件判堆叠，所以**只有同一条鱼、同一品质的鱼块能叠**（16/组）。
钓到 20 条鲫鱼 = 20 组鱼块。这是"数据跟着走"的必然代价，见 §11 待拍板 #3。

### 2.3 数量：按重量，上限 12

| 档位 | 每几 kg 出 1 块 | 保底 | 上限 | 实例 |
|---|---|---|---|---|
| 普通鱼块 | 0.25 kg | **1 块** | **12 块** | 鲫鱼 1.2kg → 4 块；横纹鱼 0.03kg → 1 块（保底） |
| 优质鱼肉 | 1 kg | 1 块 | 12 块 | 翘嘴 0.6kg → 1 块；青鱼 35kg → 12 块（触顶） |
| 顶级鱼排 | 3 kg | 1 块 | 12 块 | 孔雀鱼 0.006kg → 1 块；金枪鱼 180kg → 12 块（触顶） |

**公式**：`份数 = clamp(floor(重量 / 系数), 1, 12)`

- **保底 1**：不然 3 克的横纹鱼会切出 0 块（东西直接消失，玩家会以为 bug）
- **上限 12**（用户指定）：金枪鱼 180kg 按 3kg/块本该 60 块，封在 12
- 三档系数不同是**故意的**：小鱼多切几块、大鱼少切几块，让"一条 180kg 的金枪鱼"
  不至于一次塞满背包，也让小鱼有存在感

## 3. 调料清单（3 新增 + 5 借用）

### 3.1 新增

**✅ 已实现**（2026-10-03，贴图见 §8.5；配方在
`src/main/resources/data/anglertackle/recipe/`，由 `tools/check-kitchen-items.js` 逐条守）：

| 调料 | id | 获取链（全用原版材料） |
|---|---|---|
| **盐** | `salt` | 工作台无序：**水桶 ×1 + 干海带 ×1** → **盐 ×2**（空桶自动返还） |
| **酱油** | `soy_sauce` | 工作台无序：**小麦 ×2 + 干海带 ×1 + 糖 ×1** → 1 |
| **芥末** | `mustard` | 工作台无序：**仙人掌 ×1 + 糖 ×1 + 盐 ×1** → 1 |
| **鱼油** | `fish_oil` | 鱼块**榨油**（多脂鱼 1 块 / 普通鱼 2 块 → 1 瓶，见 §13.4） |
| **鱼刀** | `fish_knife` | 工作台无序：**铁锭 ×1 + 任意木头按钮 ×1 + 木棍 ×1**（用户 2026-10-03 指定） |

> ⚠️ **盐从"熔炉烧水桶"改成"工作台·水桶 + 干海带"了**（2026-10-03）。
> 原因就是用户提醒的那条规则的**另一面**：**熔炉不返还容器**
> （原版 `AbstractFurnaceBlockEntity` 只会 `shrink(1)`，没有 `getRemainingItems` 那一套），
> 烧一次水桶就**永久少 3 个铁锭**。改到工作台以后，水桶走原版的
> `craftingRemainingItem`（原版蛋糕用奶桶也是这个机制），**不需要我们写一行代码**就返还空桶。
> 于是：**所有用到容器的配方都在工作台**，这条现在对"盐"也成立了。
>
> ⚠️ 芥末是三者里最勉强的（原版没有山葵，用仙人掌当"辛"的替身）——
> 但用户 2026-10-03 已定"芥末等东西按你配方"，所以照此实现。

### 3.2 借用（一个中间物都不多加）

| 借用的原版物 | 当什么用 |
|---|---|
| 干海带 | 鲜味 / 包裹（幽庵烧、刺身垫底）**+ 熬盐、酿酱油的主料** |
| 糖 | 甜味 / 上色（蒲烧） |
| 小麦 | 酱油的主料、鱼丸的黏合剂、油炸的挂糊 |
| 甘蔗 | 姜的替身（清蒸、慢炖去腥） |
| 仙人掌 | 芥末的"辛" |
| ~~向日葵 + 玻璃瓶~~ | ❌ **作废** —— 植物油已被**鱼油**取代（用户 2026-10-03 定） |

## 4. 从鱼块到料理（两级结构）

**这是用户设计的精髓**：第一级"切块"把 28 条鱼收敛成 3 种食材；
第二级"烹饪"由**鱼块档位 + 鱼的数据**决定能做什么。

```
整条鱼 ──工作台切块──▶ 鱼块（3 档，带鱼的数据）
                          │
                          ├─ 烤：熔炉 / 烟熏炉 / 营火（+ 可选调料）
                          ├─ 生食：刺身（需要酱油 + 鱼刀）
                          ├─ 清蒸：蒸锅位？→ 见 §12 待拍板 #5
                          └─ 汤/炸：见下
```

### 4.1 三档能做的料理（映射表）

| 料理 | 需要的档位 | 额外材料 | 说明 |
|---|---|---|---|
| **清烤 / 香烤 / 蒲烧**（烤鱼，3 档做法） | 普通鱼块起 | 火 + 可选调料 | 最基础，任何档都能做 |
| **鱼汤** | 普通鱼块起 | 水桶 + 盐 | 家常 |
| **炸鱼块** | 普通鱼块起 | 植物油 + 小麦 | |
| **香煎鱼排** | 优质鱼肉起 | 植物油 + 盐 | |
| **清蒸鱼** | 优质鱼肉起 | 水 + 姜（甘蔗）+ 酱油 | |
| **刺身** | **顶级鱼排** + **海鱼** | 酱油 + 鱼刀（芥末可选） | 见 §7 |
| **蒲烧（高级）** | 顶级鱼排 | 酱油 + 糖 | 甜咸上色 |

> ⚠ 注意：**刺身同时受"档位"和"水体"两个条件约束**（顶级鱼排 ∩ 海鱼）。
> 淡水鱼即使到了金红档也做不了刺身（现实依据），但可以做蒲烧。

### 4.2 调料的作用（可选升级，不阻断）

| 调料 | 效果 | 是否必需 |
|---|---|---|
| 盐 | 饱食度 +20% | 否 |
| 酱油 | 再 +20%（与盐合计 +40%） | 否 |
| 植物油 | 额外给"饱和"效果 | 否 |
| 干海带 | 与酱油同用 → 走"幽庵烧"路线（只在命名与图鉴上体现） | 否 |
| 芥末 | 刺身效果时长 +50% | 否 |

## 5. 数值表（档位 → 料理）

> **2026-10-03 用户定案（原话）**："根据鱼品质做饱食度区分，即使同一道菜只要制作的鱼档次不同
> 回复的饱食度就不同。即使一样的鱼品质不同饱食度回复也不同，根据品质每差一级饱和度与饱食度
> 可以差**半格**（需要注意这个"格"的说法可能与数值表不大相似，比如原版是 10 格血的目标在
> 显示中是 20 滴血）。每个档次再差半格（如优质鱼肉与顶级鱼排），但无论如何加工成的烹饪品
> **至少比熟鱼块高半格**饱食度与饱和度。"

**单位**：**1 格 = 一个完整的鸡腿图标 = 2 点饱食度**；**半格 = 1 点**。
玩家看到的是图标，代码里存的是点数（源：`fishing/FoodValues.java`）。

| 档位 | 熟鱼块（饥饿 / 饱和） | 菜（饥饿 / 饱和） |
|---|---|---|
| 0 白 | 3 / 3.0 | **4 / 4.0** |
| 1 绿 | 4 / 4.0 | 5 / 5.0 |
| 2 蓝 | 5 / 5.0 | **6 / 6.0** |
| 3 紫 | 6 / 6.0 | 7 / 7.0 |
| 4 金 | 7 / 7.0 | **8 / 8.0** |
| 5 红 | 8 / 8.0 | 9 / 9.0 |

三条性质（`tools/check-food-values.js` 会逐条复算）：

1. **每差一级差半格**：相邻档位差 1 点；
2. **每个材料档次再差半格**：普通(0,1) / 优质(2,3) / 顶级(4,5) 三段**交界处**也差 1 点（1→2、3→4），
   不会出现两个档次数值撞在一起；
3. **菜至少比熟块高半格**：同档下菜恰好 = 熟块 + 1 点。

> 加粗那三个数就是**旧稿的三段锚点**（4 / 6 / 8）—— 定案与旧稿不冲突，
> 只是把"三段"细化成了"六个档位"。
> 饱和度与饱食度**同值**（`saturationModifier = 0.5`，最终饱和度 = nutrition × 0.5 × 2）。

**菜的数值只跟材料档位走，不跟菜型走** —— 玩家只要记住六档，不用记十几道菜各自的数值。

**菜型只决定"额外效果"**（⚠ **完整策划见 `docs/28-菜型效果策划.md`**；代码里还没实现，见 docs/27 §5）：

| 菜型 | 额外效果（**待实现**） |
|---|---|
| **刺身** | 速度 + 水下呼吸（按档位分级：优质 速度 I 20s；顶级 速度 II 30s + 水下呼吸 30s） |
| **清蒸** | 生命恢复 5s（清淡养生） |
| **汤 / 奶白汤 / 慢炖** | 饱腹 10s（喝汤暖胃） |
| **熏鱼** | 无效果，但**堆叠上限 64**（保存性好，适合带出门） |
| 其余（烤 / 煎 / 炸 / 红烧 / 炭烤 / 鱼丸 / 整条油炸） | 无 |

> 为什么不做"每道菜一套数值"：那会变成 40+ 道 × 6 档 = 240 多组数字，
> 每加一道菜都要重新配平，而且玩家完全记不住。**档位定数值、菜型定效果**之后，
> 加菜只是加一个效果标签，不动平衡。
>
> 参考原版：熟鳕鱼 5 / 6.0、生鳕鱼 2 / 0.4、熟牛肉 8 / 12.8 ——
> 我们的菜从 4 / 4.0 到 9 / 9.0，把这三样夹在中间。

## 6. 观赏鱼：**不进入料理系统**（用户 2026-10-03 定案）

> ⚠️ **勘误**：本节第一版把用户那句"观赏鱼不做料理方面改动"理解成了
> "不给观赏鱼做特殊处理、金红档全部可做鱼排" —— **完全反了**。
> 用户随即指出："**因为你的材料提到了观赏鱼做鱼排，这不符合我的策划**"。
>
> 正确含义：**观赏鱼不参与料理系统** —— 不能切鱼块、不能做任何菜。
> 它仍然是完整的鱼获（能卖钱、进图鉴、放水族箱），只是**跟厨房无关**。

### 6.1 两类鱼的分工

| | **食用鱼** | **观赏鱼** |
|---|---|---|
| 能否切鱼块 | ✅ 能（按品质切成三档） | ❌ **不能** |
| 能否做菜 | ✅ 能 | ❌ **不能** |
| 卖钱 | ✅（已有商店） | ✅（多半更值钱，因为是金红档） |
| 图鉴收集 | ✅ | ✅ |
| 水族箱展示 | ✅ | ✅ **（这才是它的主场）** |
| 现实依据 | 各地主要食用鱼种 | 水族贸易的主要品种 |

> 这个划分还顺带解释了**为什么观赏鱼都在金红档**：稀有度本来就该对应"稀有用途"，
> 而不是"更好吃"。钓到孔雀鱼拿去做鱼排这件事，从设计上就不该发生。

### 6.2 观赏鱼清单（用户 2026-10-03 定案）

依据"现实中是否以**水族观赏**为主要身份"判断，并经用户逐条确认：

| 鱼 | 中文名 | 现实身份 | 定案 |
|---|---|---|---|
| `guppy` | 孔雀鱼 | 全球最普及的小型观赏鱼 | **观赏鱼** |
| `african_butterflyfish` | 齿蝶鱼 | 蝴蝶鱼科，海水观赏鱼代表 | **观赏鱼** |
| `jewel_cichlid` | 红宝石鱼 | 非洲慈鲷，著名观赏鱼 | **观赏鱼** |
| `elephantnose` | 长吻象鼻鱼 | 象鼻鱼，水族箱常见 | **观赏鱼** |
| `cave_blindfish` | 盲鱼 | 洞穴盲鱼，无食用价值 | **观赏鱼**（用户定） |
| ~~`platinum_arowana`~~ | ~~铂金银龙鱼~~ | 龙鱼：高端观赏，但东南亚确实食用 | ✅ **食用鱼**（用户定） |

> 洞穴本来就是"鱼最少的极端环境"，而金泥鳅正是为它配的（§13.5 第 13 行）。

## 7. 水体规则：只有海鱼能做刺身

按 `FishWaters` 已有标记过滤（`M_OCEAN = 1<<3`、`M_DEEP = 1<<4`，常量定义在 `WaterBody`），**这张表是从源码抽出来的，不是手抄**：

**学到的 12 条**（前 9 条来自量 57 张物品显示图，后 3 条来自游戏内实拍）：

| # | 画法 | 反例（我第一版就是这么错的） |
|---|---|---|
| ① | **填满画布**：内容框 13~16px、不透明 90~200（参考实测 73~206） | 盘菜主体太小，四周空一圈 |

## 9. 实现方案

产物要"动态"（继承鱼的 id / 品质 / 重量），而原版配方系统**不支持动态产物**，必须写自定义配方。

| | **方案 A**（按档位分物品） | **方案 B**（单物品 + 全动态组件） |
|---|---|---|
| 鱼块物品数 | **3 个**（就是本文档的设计） | 1 个（档位也进组件） |
| 料理物品数 | 4 个（3 烤 + 1 刺身） | 1 个（做法也进组件） |
| 贴图 | 7 张 | 7 张（都一样，因为档位要靠贴图区分视觉） |
| 优点 | 玩家一眼看懂档位；JEI 里能看到 3 档 | 物品少 |
| 缺点 | 物品多 3 个 | 组件分支多，tooltip 与图鉴逻辑更绕 |

**我推荐方案 A**（即用户描述的设计）：鱼块本来就该是"三种看得见的东西"，
塞进一个物品再靠 tooltip 区分反而更难懂。而且 **3 个物品的贴图成本已经很低了**。

### 9.1 落点

> 用户 2026-10-03 的要求：
> **"每个鱼材料可以根据自身刻录的数据做成不同菜，搜索各种食用鱼的做法，决定最终配方成菜。"**

### 13.1 现实依据（不是编的）

设计依据是《生命时报》的《每种鱼都有最佳做法》
（[中国农业科学院转载](http://cast.caas.cn/kj/kjyjk/154347.html)），
它给出的"做法 → 适合的鱼"我直接采用：

| 现实做法 | 原文依据 | 映射成游戏规则 |
|---|---|---|
| **清蒸** | "高端鱼最适合清蒸，如鳜鱼、鲥鱼、鲈鱼……肉质细嫩，保持原汁原味" | 优质鱼肉 + **白肉** |
| **红烧** | "大部分鱼可以红烧……**鲤鱼、白鲢、花鲢、草鱼**红烧后风味更好" | 优质鱼肉（不限肉色） |
| **做汤** | "以**大黄鱼、鳜鱼、鲫鱼**味道最佳……肉嫩、质细、出汤率高" | 普通鱼块 + 水 |
| **慢炖** | "**黄鳝、黑鱼、鲫鱼、鳕鱼**味道鲜美、肉相对紧实……**泥鳅**可能带寄生虫，炖着吃更安全" | 普通鱼块 + 水 + 姜（**白肉**） |
| **烧烤** | "**脂肪较多**的鱼适合烤着吃，如鳗鱼、秋刀鱼，可产生特有的香气及风味" | 顶级鱼排 + **多脂鱼** |
| **油煎** | "很多鱼烹饪预处理时都会用到油煎……煎前抹盐可防破皮" | 优质鱼肉 + **鱼油** + 盐 |
| **生食** | "生吃**最好选海水鱼**，寄生虫较少……最好选**金枪鱼、真鲷、三文鱼**" | 顶级鱼排 ∩ **海鱼**（§7 已定） |

> ⚠ 顺带印证了两条既有规则：**淡水鱼不做刺身**（寄生虫）、
> **泥鳅这类底栖鱼炖着吃更安全**（所以金泥鳅的看家菜是"慢炖"）。

### 13.4 鱼油（用户 2026-10-03 指定）

> 用户原话：**"可以在工作台通过鱼材料加工成鱼油，2 鱼块加工一个。
> 对于鱼块数据中如存在油脂含量更多的鱼数据，则可以允许一块鱼材料做一鱼油。"**

| 产出 | 消耗 | 条件 |
|---|---|---|
| **鱼油 ×1** | 鱼块 ×2 | 任意鱼（`oil = lean`） |
| **鱼油 ×1** | 鱼块 ×**1** | **多脂鱼**（`oil = oily`）—— §13.2 里那 5 条 |

**用途**：煎 / 炸 / 奶白汤的必需材料；也可直接吃（回少量饱食度）。

> 这条规则顺带解释了"顶级鱼为什么值钱"：金枪鱼、鲑鱼、幼鲨都是多脂鱼 →
> 同一批鱼块能榨出**双倍**的油；而它们本身又是刺身原料。
> **顶级鱼同时是食材和油源**，这个双重身份是设计出来的，不是巧合。

### 13.5 逐鱼详细菜谱（**每种鱼 ≤ 2 道**，用户 2026-10-03 定）

> 用户原话：**"根据现有策划出菜谱，要具体详细。每种可以先做两种及以下。"**
>
> 所以下表**不是**"从一张通用菜单里随便挑"，而是**给 42 条食用鱼各指定 1~2 道**——
> 每条鱼有它的看家做法（依据见 §13.1），玩家钓到什么鱼就知道该做什么菜。
> （第一批 23 条 = 2026-10-03；第二批 19 条 = 2026-10-10 按**食用描述分级**补的全，
> 剩下的 5 条是不可食用，见 §13.5.3。加菜只是加一行，不动平衡。）

**材料记法**：`生块` = 整鱼切出的三档材料（普通鱼块 / 优质鱼肉 / 顶级鱼排）；
`熟块` = 生块经**熔炉**加热（= 清烤，可直接吃）；`整鱼` = 不切块直接用。
**方式**列写的就是设备（详见 §14 的三级流程）。数值统一按档位（§5），下表只写配方与效果。

| # | 鱼 | 材料 | **菜 1**（方式） | 配方 | **菜 2**（方式） | 配方 |
|---|---|---|---|---|---|---|
| 1 | 鲫鱼 | 普通鱼块 | **鲫鱼汤**（工作台） | 熟块×1 + 水桶 | **奶白鲫鱼汤**（工作台） | 熟块×1 + 水桶 + 鱼油 |
| 2 | 罗非鱼 | 普通鱼块 | **清烤罗非鱼**（**熔炉**） | 生块 → 熟块（直接吃） | **香煎罗非鱼**（工作台） | 熟块×1 + 鱼油 + 盐 |

## 14. 烹饪方式与配方结构（用户 2026-10-03 要求）

> 用户原话：**"要给烹饪方式。比如加工成熟鱼块是需要熔炉，包含鱼数据的熟鱼块又需要怎样
> 转化为对应的菜，注意同种类鱼不同菜不能撞配料，不同鱼因为鱼材料包含的数据不同所以允许撞配方。"**

### 14.1 三级流程（每级用不同设备）

```
【第 1 级 · 预处理】工作台
   整鱼 ──────────────▶ 生鱼块（三档，带 fish_id / 品质 / 重量）
   生鱼块 ×2（多脂鱼 ×1）──▶ 鱼油
                          │
【第 2 级 · 基础加热】熔炉 / 烟熏炉 / 营火   ← **三种设备产出三样东西**
   生鱼块 ──熔炉──▶ 熟鱼块    （= 清烤，可直接吃）
   生鱼块 ──烟熏炉──▶ 熏鱼块  （保存性好，堆叠 64）
   生鱼块 ──营火──▶ 炭烤鱼块  （炭火风味）
                          │
【第 3 级 · 调味成菜】工作台
   熟鱼块 + 配料 ─────▶ 具体菜（红烧 / 清蒸 / 香煎 / 汤 / 炖 / 鱼丸…）
   生鱼块 + 酱油 + 鱼刀 ─▶ 刺身（**唯一走生料的菜**）
```

**为什么第 2 级要让三个设备产出不同**：MC 原版只有这三种加热设备，如果它们都产出"熟鱼块"，
那设备就没有意义了。三分之后 —— **熔炉=基础熟食、烟熏炉=耐存干粮、营火=风味烧烤** ——
玩家在野外（营火）和在家（熔炉）能做的菜天生不同。

### 14.2 设备分工总表

| 设备 | 负责的菜 | 说明 |
|---|---|---|
| **工作台** | 切块 · 榨油 · 鱼丸 · 刺身 · 全部第 3 级调味菜 | 唯一做"组合"的地方 |
| **熔炉** | 熟鱼块（清烤） | 最基础的加热 |
| **烟熏炉** | 熏鱼块（熏鱼） | 堆叠 64，适合带出门 |
| **营火** | 炭烤鱼块（炭烤） | 可野外现场做 |

### 14.3 配方不撞的三条规则

用户提的两条约束，落到实现上是三条规则：

| # | 规则 | 为什么 |
|---|---|---|
| **①** | **产出物品按"菜型"注册，不按鱼** —— 例如 `braised_fish` 只有**一个**物品，靠数据组件记住"这是哪条鱼做的" | 否则 23 条鱼 × 8 道菜 = 184 个物品 |
| **②** | **不同鱼的同名菜共用同一条配方**（材料 = 熟鱼块 + 酱油 + 糖 → `braised_fish`，`fish_id` 从材料继承） | 这正是用户说的"不同鱼**允许**撞配方"：鱼块里的数据已经把鱼区分开了，配方不需要再分 |
| **③** | **同一条鱼的两道菜，配料必须不同** | 否则同一条鱼的两个配方材料**完全相同**，MC 无法判断该出哪道菜（后注册的会覆盖前者） |

**规则 ③ 的验证**（我逐条核对 §13.5 的表，全部通过）：

| 鱼 | 菜 1 的配方 | 菜 2 的配方 | 差异点 |
|---|---|---|---|
| 鲫鱼 | 熟块 + 水桶 | 熟块 + 水桶 + **鱼油** | 多一样鱼油 |
| 罗非鱼 | （第 2 级：熔炉，无第 3 级配方） | 熟块 + 鱼油 + 盐 | 分属不同级 |
| 草鱼 | 熟块 + 酱油 + 糖 | **熟块×2** + 小麦 | 数量 + 材料都不同 |
| 青鱼 / 镜鲤 / 翘嘴 | （第 2 级：烟熏炉） | 熟块 + 酱油 + 糖 | 分属不同级 |
| 梭鲈 / 条纹鲈 | 熟块 + ****水桶** + 甘蔗** + 酱油 | 熟块 + **鱼油 + 盐** | 完全不同 |
| 狗鱼 | **熟块×2** + 小麦 | 熟块 + 鱼油 + 盐 | 数量 + 材料 |
| 鲇鱼 / 金泥鳅 | 熟块 + 水桶 + **甘蔗** | 熟块 + 鱼油 + **小麦** | 完全不同 |
| 蓝宝石雷龙鱼 | 熟块 + 水桶 + 甘蔗 | （第 2 级：熔炉） | 分属不同级 |
| 鲻鱼 | 熟块 + **鱼油 + 盐** | 熟块 + **水桶** | 完全不同 |
| 大眼海鲢 / 鲑鱼 / 金枪鱼 | **生块** + 酱油 + 鱼刀 | 熟块 + 火/酱油 | 生熟材料不同 |
| 幼鲨 / 褐鳟 | 熟块 + **鱼油 + 盐** | （第 2 级：营火） | 分属不同级 |
| 银龙 | 熟块 + ****水桶** + 甘蔗** + 酱油 | 熟块 + **酱油 + 糖** | 完全不同 |

> **"分属不同级"也算不撞**：第 2 级的配方在**熔炉/烟熏炉/营火**的配方空间里，
> 第 3 级在工作台的配方空间里，两者根本不会互相覆盖。
> 所以一条鱼完全可以"熔炉清烤 + 工作台香煎"两道菜并存。

### 14.5 熟鱼块的"转化"（回答用户的问题）

用户问："包含鱼数据的熟鱼块又需要怎样转化为对应的菜" ——

**答案：熟鱼块就是"第 3 级的通用材料"，它的鱼数据一路继承下去。**

```
鲫鱼（白·绿）
  └─切块→ 普通鱼块{fish=crucian_carp, tier=0}
        └─熔炉→ 熟鱼块{fish=crucian_carp, tier=0}     ← 此时可直接吃（= 清烤鲫鱼）
              ├─+水桶──────→ 鲫鱼汤{fish=crucian_carp}
              └─+水桶+鱼油──→ 奶白鲫鱼汤{fish=crucian_carp}
```

- **数据继承链**：整鱼 → 生块 → 熟块 → 菜，`fish_id` 与 `tier` 全程不变
- **名字动态拼**：`熟鱼块` 的 tooltip 写"鲫鱼 · 白"；做成的菜叫"鲫鱼汤"（**菜名 = 鱼名 + 菜型名**）
- **同一条鱼能做几道菜，由 §13.5 的表决定**：不在表里的组合，配方匹配不上（材料对但鱼不对 → 拒绝）

### 14.6 特殊材料的返还与消耗（用户 2026-10-03 提醒）

> 用户原话：**"加额外物品的菜需要考虑影响，比如做汤，水桶参与制作理应返还水桶。"**

⚠️ **这条是我方案里的一个真漏洞**：原版工作台合成有一条"剩余物"机制
（`Recipe#getRemainingItems`），水桶会**自动**返还空桶 —— 但那只对**原版标准配方**成立。
我们的切块 / 榨油 / 做菜全是**自定义配方类**（因为要读鱼块里的数据），
**不覆写 `getRemainingItems` 就什么都不会返还** —— 玩家做个汤丢一个桶。

#### 14.6.1 材料分类与处理规则

| 材料 | 类型 | 合成后怎么处理 | 实现方式 |
|---|---|---|---|
| **水桶** | 容器 | ✅ **返还空桶** | `getRemainingItems` 返回 `Items.BUCKET` |
| **鱼刀** | 工具（有耐久） | ✅ **返还，并扣 1 点耐久** | 返回一个 damage+1 的鱼刀副本 |
| 盐 / 酱油 / 芥末 | 消耗品 | 消耗 | 默认 |
| 鱼油 | 消耗品 | 消耗 | 默认 |
| 小麦 / 糖 / 甘蔗 / 干海带 | 消耗品 | 消耗 | 默认 |
| 生块 / 熟块 / 整鱼 | 主料 | 消耗 | 默认 |

#### 14.6.2 逐个配方核对（哪些需要返还）

| 配方 | 用到容器/工具 | 返还 |
|---|---|---|
| 鱼汤 | **水桶** | 空桶 ×1 |
| 奶白鱼汤 | **水桶** | 空桶 ×1 |
| 慢炖鱼（鲇鱼炖 / 泥鳅炖 / 慢炖雷龙） | **水桶** | 空桶 ×1 |
| 清蒸鱼（翘嘴 / 梭鲈 / 条纹鲈 / 银龙） | **水桶** | 空桶 ×1 |
| 刺身（海鲢 / 鲑鱼 / 金枪鱼） | **鱼刀** | 鱼刀（耐久 −1） |
| 其余（红烧 / 香煎 / 油炸 / 鱼丸 / 熏 / 炭烤 / 切块 / 榨油 / 整鱼油炸） | 无 | — |

> 覆盖 **10 道菜**；**1 条配方用鱼刀**（刺身），覆盖 **3 道菜**。

> 所以**所有用水的菜必须在工作台做**，这正是 §14.1 把第 3 级放在工作台的原因之一。

#### 14.6.3 鱼刀的耐久

| 项 | 值 |

| 用完 | 变"破损鱼刀"？→ ⏳ 沿用现有配件"见底不提供加成"的思路，**直接消失**更简单 |
| 修复 | 铁锭在铁砧修（原版工具通用做法） |

>
> ✅ **已落地**：耐久写在 `item/FishKnifeItem.java` 的 `DURABILITY = 64`，

### 14.8 原版配方书（用户 2026-10-03："内容写进原版配方书"）

**原版机制（1.21.1 源码，不是猜的）**：`ClientRecipeBook#categorizeAndGroupRecipes` 的第一句是

```java
if (!recipe.isSpecial() && !recipe.isIncomplete()) { …收进配方书… }
```

而 `Recipe#isIncomplete()` 是"材料表为空 / 有一条材料一个物品都没有"。再加上
`Recipe#getResultItem()` 默认是 `ItemStack.EMPTY`（那一格会是空的），
以及"配方书只显示**已解锁**的配方，解锁唯一途径是带 `rewards.recipes` 的进度" ——
所以一条配方要出现在配方书里，**四件事缺一不可**：

| # | 条件 | 我们的做法 |
|---|---|---|
| 1 | 不是 special | `CuttingRecipe` / `OilPressingRecipe` / `DishRecipe` 都覆写 `isSpecial() → false` |
| 2 | 材料表非空且每条材料都有物品 | 覆写 `getIngredients()`，**条数与真实消耗一致** |
| 3 | 有产物图标 | 覆写 `getResultItem()` 给代表产物（**带鱼种组件**，名字才是"红烧草鱼"） |
| 4 | 有解锁进度 | `tools/gen-recipe-advancements.js` 生成；菜配方的解锁材料就是**那条鱼** |

**共 33 条**（切块 1 + 榨油 1 + 菜配方 **31** = 菜型 × 鱼种，见 §14.4）：

| 配方 | 配方书里的材料 | 配方书里的产物 |
|---|---|---|
| 切块 | `#anglertackle:fishes`（一条整鱼） | 普通生鱼块 ×1 |
| 榨油 | 生鱼块 ×2（普通鱼的量；三档都认） | 鱼油 ×1 |
| **每个菜型 × 每条鱼各一条** | **那条鱼真能切出来的块**（按它的档位表，见下）+ 该菜型的配料 | **红烧草鱼 / 红烧青鱼 / 鲫鱼汤…**（名字带鱼种） |

> ⚠ **展示的鱼块必须按鱼的档位表算**（用户 2026-10-03 第二次抓到的 bug）：
> "刺身需要大西洋鲑的**普通鱼块**，但显然普通鱼块不可能被大西洋鲑做出来" ——
> 第一版把展示档位写死成 `tier 0`（普通鱼块），而鲑鱼档位表是 `{4,5}`，只会出顶级鱼排。
> 现在按 `FishSpecies.tiers()` 去重后逐个给：跨档的鱼（鲻鱼 `{1,2}`、狗鱼 `{3,4}`、
> 巨骨舌鱼 `{3,4,5}`）会显示成"普通块 / 优质肉"这样的**多个变体**，全都真能切出来。
>
> 同时这也是 §13.5 "材料"列的口径：**那一列 = 该鱼档位表最高档对应的那一档**
> （鲫鱼 `{0,1}`→普通鱼块、草鱼 `{1,2}`→优质鱼肉、鲑鱼 `{4,5}`→顶级鱼排），
> 检查器逐行比对，改鱼的档位表不改文档就会红。

> 配方书 / JEI 里显示成"红烧鱼 ← 熟块 + 酱油 + 糖"，**看上去哪条鱼都能做** ——
> 而真实规则是 §13.5 的逐鱼表。用户当场反馈：

**已知取舍（都不是 bug，是界面表达不了）**：

| 症状 | 真因 | 修法 |
|---|---|---|
| JEI 里**三条营火配方**（`*_to_charred_fish`）查不到；日志里 `ClassCastException: ChunkCampfireRecipe cannot be cast to CampfireCookingRecipe` | JEI 的营火分类里有一句写死的强转 `(CampfireCookingRecipe) recipe`；我们的营火配方原来继承的是自己的 `DataCookingRecipe`（熔炉/烟熏炉用的是 `AbstractCookingRecipe`，没有这个强转，所以只有营火炸） | `ChunkCampfireRecipe` 改成继承**原版** `CampfireCookingRecipe`；数据继承那段抽成 `DataCookingRecipe.inheritChunkData()` 共用 |
| 摆对了材料也合不出来（"即使显示能做也弄不了"） | **创造模式 / JEI 里直接拿到的鱼块与整鱼没有 `FISH_CHUNK` / `FISH_DATA` 组件** —— 而匹配要求"这是哪条鱼"。没有数据 = 任何菜都匹配不上 | 鱼块注册时给默认 `FISH_CHUNK`（普通→鲫鱼、优质→草鱼、顶级→大西洋鲑，取该鱼最高档 + 体重中值）；整鱼给默认 `FISH_DATA`（自己的鱼种 + 档位表中档 + 体重中值）。真实钓鱼/切块的栈会被写上真实数据，覆盖默认值 |

> 默认值只影响"没有真实数据"的栈（创造模式、JEI、结构战利品）。两条断言守着：
> `check-cooking.js` 的 **D2**（营火必须继承原版类）与 **D3**（鱼块/整鱼必须带默认组件），
> 负例 `cook-campfire-not-vanilla` / `cook-no-default-chunk-data` / `cook-no-default-fish-data`。
>
> ⚠ 默认数据**必须是常数**：注册期去查 `FishSpecies` 会触发 `FightProfile` 的静态初始化
> 去读配置，而**物品注册发生在配置加载之前** → `Cannot get config value before config is loaded`，
> 模组直接装不进去（1.1.11 真的这么崩过一次，是下面那台体检服务器抓出来的）。
> 常数与鱼种数据（档位表 / 规格区间）的一致性由 D3 逐条核对。

#### 14.8.3 主料按**格**数，不按个数数（用户："塞多个相同物品就合不了 / 没有批量合成"）

原版每次合成的扣除方式是 `ResultSlot#onTake` 里那句：

```java
for (每个合成格) { if (!slot.isEmpty()) slot.removeItem(1); }   // 每个非空格子各扣 1 个
```

所以**匹配必须按格算**：

| 摆法 | 应当是 | 说明 |
|---|---|---|
| 一格放一叠熟块（3 个）做「红烧鱼」（要 1 块） | ✅ 匹配 | 扣掉 1 个后还剩 2 个 → **按住 Shift 可以连续合成（批量）** |
| 一格里放 2 个熟块做「鱼丸」（要 2 块） | ❌ 不匹配 | 否则合成只从这一格扣 1 个，等于**白送**一份 |
| 两个格子各放熟块做「鱼丸」 | ✅ 匹配 | 与配方书 / JEI 显示的两条主料一致 |

第一版按**个数**数（`baseCount += stack.getCount()`），于是第二种摆法反而"能合"（白送），
而第一种被拒 —— 用户实测到的就是第一种。

守它的有两处：`check-dish-recipes.js` 的 **H**（源码里必须是 `baseSlots++`，负例 `dish-count-by-stack`），
以及**配方体检**里那条"每格放一叠也必须匹配"（`RecipeAudit` 用 1 个/格与 3 个/格各跑一遍）。

#### 14.8.2 配方体检：把"显示的材料"真的摆进合成格（用户："这都出问题了那肯定还有更多"）

JS 检查器读源码与 JSON，**查不出"界面显示的材料与实际匹配脱节"**。所以加了一台
体检服务器：`debug/RecipeAudit.java`，判据是

> `Recipe#getIngredients()`（配方书 / JEI 显示的材料）摆进合成格后，`matches` 必须为真、
> `assemble` 必须非空（切块与菜还必须继承 `FISH_CHUNK`）。

跑法：`ATL_AUDIT=true gradlew runServer`（体检完自动关服；平时不设这个变量它什么都不做）。
⚠ 第一次跑会弹 Windows 防火墙（专用服务器监听 25565）——**拦掉即可**，那是本地开发服务器。

它第一次跑就抓到两个"构建全绿、单人游戏看不出来"的真 bug：模组装不进专用服务器
（common 类里引用客户端 `Screen`）、以及 1.1.11 的注册期读配置崩溃。
当前 55 条配方全部通过。
