## 1. 定位与边界（先把"不是什么"划清）

**任务 = 老柯每天/每周给玩家的"具体目标"，完成后给奖励。** 它把"随机钓鱼"变成  
"**有目标的钓鱼**" —— 不新增进度真源，只是给已有的上鱼事件**加一层目标判断**。

| 系统     | 是什么         | 与任务的分工                                 |
| ------ | ----------- | -------------------------------------- |
| **图鉴** | 你**收集过**什么  | 任务可要求"钓到某鱼"，但进度只读上鱼事件，不另存一份            |
| **联赛** | **周期内比排名**  | PvP 排名；任务是与老柯的**单人委托**（PvE）            |
| **比赛** | **一场活动的名次** | 有开赛/结算；任务是**常态化**的日/周节奏                |
| **称号** | **长期成就外化**  | 任务完成数 / 活跃度可成为称号来源，判定仍只在 `Titles`      |
| **商店** | 用鱼币买东西      | 任务是**产鱼币**的新渠道（另一条是卖鱼）—— 数值与商店经济对齐（§8） |

⚠ **三条不新造**（用户第 10 条："代码之间都有可抄之处，别整花活"）：

1. **不新造通信通道** —— 委托与奖励**全部走邮件**（`MailService` / `MailEntry`）✓；
2. **不新造"上鱼"入口** —— 进度只在 `LeaderboardHooks.onCatch` 那一处挂钩 ✓；
3. **不新造 NPC** —— 老柯就是 `FishermanEntity`（`docs/13`），只给他加一套"派活"的话术与列表 ✓。

## 2. 三个周期（**同时可做 N 个，池子更大**）

| 周期              | 刷新口径             | **同时可做** | **池子条目数** | 定位                      |
| --------------- | ---------------- | -------- | --------- | ----------------------- |
| **每日委托**        | 每 1 游戏日（天明刷新，§3） | **5 个**  | **≥ 8**   | **轻松可完成**（用户："每日就是要轻松"） |
| **周常委托**        | 每 7 游戏日          | **5 个**  | **≥ 8**   | **有一定挑战性**，但不出高难（§4.2）  |
| **主线任务**（原"常驻"） | 长期               | —        | —         | **本版不做**（用户第 6 条，§14）   |

- **"5 个"是同时可接可做的数量**，"**≥ 8**"是**设计出来的总条目数** ——  
  两者是两件事：玩家每天只能接 5 个，但池子有 ≥8 种，**抽出来才有随机感** ✓（用户 16:19 澄清原话）。
- **不限"种类必须互不相同"**：同一天抽到的 5 条**允许是同一目标类型**（例如两条都是"钓到 N 条鱼"）  
  —— 用户第 1 条："限制种类的 3 条非常难以达成" ✓。

## 3. ★ 刷新口径（**本版推翻上一版，按用户第 2 条重写**）

### 3.1 结论：按**游戏内时刻**刷新，**天明开新的一天**

```
日序号 day  = floor( getDayTime() / 24000 )     // ServerLevel（主世界）
周序号 week = floor( day / 7 )
1 游戏日 = 24000 刻 ≈ 20 分钟（游戏内 dayTime 0 刻 = 06:00 天明）
```

- **`day` 变化的那一刻刷新**（游戏内 06:00 天明）⇒ 玩家感知是"**天亮了，老柯派新活**" ✓；
- **全局统一**：`dayTime` 是**世界时钟**，多人服里所有玩家共享同一个 ⇒ 全服同一天、同时刷新 ✓；
- **无人在线时服务器不 tick ⇒ `dayTime` 不推进 ⇒ 不刷**（合理：没人玩就没有"新的一天"）✓。

### 3.2 为什么**不用** `getGameTime()`（上一版就是错在这）

`getGameTime()` 是**纯 tick 计数**（每刻 +1），与世界昼夜**无关** ⇒ 它的"一天"边界会落在  
**游戏内随便一个时刻**（经常是半夜）。症状就是用户说的"**一天睡觉一天不睡就乱套了**"：  
玩家看到"天还黑着，任务刷新了"，或"睡了一觉醒来，任务没刷新" —— 感知完全错位 ✗。

⇒ **改用 `getDayTime()` 的日序号**：它**跟着游戏内昼夜走**，睡觉跳过夜晚＝**自然进入新的一天** ✓。

### 3.3 睡觉 / `/time set` 会不会被刷？

| 行为                 | 对 `dayTime` 的影响          | 会不会被刷                                       |
| ------------------ | ------------------------ | ------------------------------------------- |
| 睡觉跳过夜晚             | 一次性推进到次日清晨 ⇒ `day` +1    | **不会**：原版**一晚只能睡一次** ⇒ 一夜最多前进一天，本来就该是新的一天 ✓ |
| `/time set`（OP 指令） | 改的是当天时刻，**原版保留天数不改日序号**  | **不设防**：这是 OP 权限，和它能做的其它事一样 ✓               |
| 关掉游戏               | 服务器不 tick ⇒ `dayTime` 不动 | **不会**：不该把离线时间算成"新的一天" ✓                    |

### 3.4 日界推进怎么触发（实现口径）

- 主世界 `LevelTickEvent.Post` 里记 `lastDaySeen`，`floor(getDayTime()/24000)` 变化时跑一次  
  "**新的一天**"（幂等：`lastDaySeen` 挡住重复执行）✓；
- **离线补发**：`PlayerLoggedInEvent` 比对玩家的 `lastDailyDay` 与当前 `day`，落后了**只补当天那一份**  
  （不补错过的每一天 —— 补一叠等于鼓励离线挂机 ✗）；
- 日界推进**只投递委托信**，不做别的（"一件事一个地方"）✓。

### 3.5 与联赛计时口径的区别（别照抄）

`docs/37` §3.4 的联赛用**每人独立时间轴**（签收起算），因为排名赛要**公平起跑线**；  
**任务不是排名** ⇒ 用**全局统一日界**（简单、可预期、全服一致）✓。  
一句话：**联赛按人算时间，任务按世界算时间。**

## 5. 数据模型（新附件 + 数据驱动定义）

### 5.1 任务定义：模板 + 参数（**不写死未来内容**）

照 `docs/39` §5"生成式称号"的教训 —— 任务**用"模板 + 参数"**，不为每条任务写一个类：

```java
// quest/QuestDef.java
record QuestDef(
    String id,          // 'daily_any_5' / 'weekly_tier_gold' …
    Period period,      // DAILY / WEEKLY
    Goal goal,          // 见 §4 的"目标类型"
    String[] args,      // 参数（只放 id 与数字）
    Reward reward,      // 二选一：鱼币 或 物品（§8）
    int minLevel,       // 抽池的等级门槛
    int weight)         // 抽中权重

enum Goal { GET_COUNT, GET_TIER_COUNT, GET_SPECIES, GET_SPECIES_SET,
            GET_WEIGHT_SUM, GET_BIGGEST, GET_LONGEST, GET_ROD_TYPE, GET_VARIETY }
enum Reward { COINS, ITEM }   // 用户第 3 条：给饵料就不给鱼币 ⇒ 每个任务只给一种
```

### 5.2 玩家数据：**一个新附件**（不塞进 `PlayerFishingData`）

照 `FishermanProgress` / `MailBox` 的成例 —— 任务数据与鱼币/图鉴**没有共同生命周期**，单开一个：

```java
// player/QuestData.java   （玩家附件，copyOnDeath，optionalFieldOf 默认值 ⇒ 老存档零迁移）
record QuestData(
    long lastDailyDay,               // 上次发到"每日委托"的游戏日序号（§3 的 day）
    long lastWeeklyWeek,             // 上次发到"周常"的游戏周序号（§3 的 week）
    Map<String, Row> active,         // 已接取的委托：id → 进度行
    long activityWeek,               // 活跃度所属周序号
    int activity,                    // 本周活跃度（上限 100，§7）
    int claimedTiers,                // 已领过的活跃度档位（位掩码，25/50/75/100）
    int totalCompleted               // 累计完成数（称号/统计用）
) {
    record Row(int progress, boolean claimed) {}   // progress=当前值; claimed=已领奖/已结算
}
```

- **老存档零迁移**：新附件读不到就是 `EMPTY`（`lastDailyDay=0` ⇒ 登录当天立刻补发当天委托 ✓）；
- **服务端权威**：进度只在服务端写；客户端只能发"**接取 / 领奖**"两个动作（同邮箱"读/领"的纪律）；
- **幂等**：`claimed` 位 + `lastDailyDay`/`lastWeeklyWeek`/`claimedTiers` 天然挡住"重复领""同天重复刷新" ✓。

### 5.3 邮件作为通道（**新增两个白名单动作**）

复用 `mail/MailActions.java` 的白名单（服务端只认表内 id；客户端不能自定义、不能"替谁执行"）：

| action id      | 服务端做什么                                               |
| -------------- | ---------------------------------------------------- |
| `quest_accept` | 校验（今天没接过 / 5 条没满 / 等级够）⇒ 记入 `QuestData.active`，回一条提示 |
| `quest_claim`  | 校验（该任务已完成、未领）⇒ 跑完成流程（记 `totalCompleted`、加活跃度、视情况授称号） |

**四类信的模板**（语言键中英成对，照 `check-lang`）：

| 模板                      | 附件               | 动作按钮                   |
| ----------------------- | ---------------- | ---------------------- |
| 每日委托信 `quest_daily`     | 无（只是清单）          | 【接下委托】= `quest_accept` |
| 周常委托信 `quest_weekly`    | 无                | 【接下委托】= `quest_accept` |
| 委托奖励信 `quest_reward`    | **鱼币 或 物品（二选一）** | 无（普通【领取】）              |
| 活跃度奖励信 `quest_activity` | 该档奖励（§7）         | 无                      |

> ⚠ **邮箱满 ⇒ 委托推迟，绝不静默丢**（抄 `MailService.deliver` 三条政策）：  
> 投递失败返回 `BOX_FULL` ⇒ **不写 `lastDailyDay`**，下次登录/下个 tick 再试 ⇒ 委托不会永久丢失 ✓。

## 6. 流程（状态机）

```
 ┌────────── 每日天明（getDayTime 的 day 变化）/ 每周（week 变化）──────────┐
 │  服务端给每个在线玩家投递《今日/本周委托》信（5 条，带【接下委托】按钮）    │
 └────────────────────────────┬───────────────────────────────────────────┘
                              │ 玩家点【接下委托】
                              ▼
            QuestService.accept()  ⇒ QuestData.active 记 5 条
                              │ 上鱼
                              ▼
  LeaderboardHooks.onCatch → try{ QuestService.onCatch(player, c) } catch{忽略}
                              │ 进度推进；某条达标
                              ▼
    服务端投递《委托完成》奖励信（鱼币 或 物品，二选一，带【领取】）
                              │ 玩家点【领取】
                              ▼
 MailService.claim → 入包 + MailActions.quest_claim → 记 completed、**加活跃度**、视情况授称号
```

**边界（逐条给处理）**：

| # | 情形          | 处理                                                |
| - | ----------- | ------------------------------------------------- |
| 1 | 当天没上线       | 次日登录**只补当天那一份** ✓                                 |
| 2 | 接取了没完成，跨日了  | 跨日时 `active` 里未完成的**清掉**（每日过期作废），周常按周清 ✓          |
| 3 | 完成了没点领取，跨日了 | **奖励信已在邮箱**（保管期走 `MailService.keepFor`，奖励类给长保管期）✓ |
| 4 | 邮箱满         | 推迟投递 + **不置位**（§5.3）✓                             |
| 5 | 日界那一刻正在上鱼   | 用**结算时刻**的 day 判定（`Catch` 快照里带 day 参考，**不重算两遍**）✓ |
| 6 | 睡觉跳过夜晚      | 自然地进入"新的一天"（§3.3）✓                                |
| 7 | 关服/回档/重进    | 幂等位挡住重复发奖 ✓                                       |
| 8 | 活跃度到档       | 见 §7（每档每周只发一次）✓                                   |

## 11. 玩法设想（这些模块要做到什么玩法的实现 ★ 用户点名）

### 11.1 核心：把"随机钓鱼"变成"有目标的钓鱼"

现在的循环是"抛竿→上鱼→卖鱼"。任务加了一层**目标**：  
**天亮看老柯要什么 → 有目的地下竿 → 交付 → 领钱 →（明天再来）**。  
玩家从"我该去哪钓"变成"我**今天**要钓到什么" —— 从"沙盒"到"节奏"的关键一步。

### 11.2 每日：给短会话一个"理由"（**轻松**）

- 一个游戏日 ≈ 一次游玩 ⇒ **一上线就有 5 个明确小目标**，解决"上来不知道干嘛"；
- **期限感**（"今天剩 8 分钟"）制造温和紧迫，但**跨日只是消失，不扣分** ⇒ 不逼肝 ✓；
- **门槛低**（每日池偏"钓 N 条"/低档）⇒ 是"新手链路"（`docs/13`）的延续 ✓。

### 11.3 周常：给"回访"一个"理由"（**有挑战**）

- 周常需要几天投入（累计量 / 集齐鱼种 / 冲重量）⇒ 制造"**明天还得来**"的钩子；
- 与**联赛**错峰：联赛比排名、周常完成某件事 ⇒ 叠加时是"**名次 + 目标**"双动力，且**互不干扰** ✓；
- **难度上限压在金色**（不出红鱼），保证"等级低、没钻石竿"的玩家也够得着 ✓。

### 11.4 活跃度：给"周"一个进度的抓手

- 简单、**可预期**、**有阶段感**（25/50/75/100 四个台阶）⇒ 玩家能"看着进度条往上走"；
- **不是逼肝**：满档只需要约 4 天全勤 + 全部周常（§7.1）✓；
- 与**称号**联动：累计完成数 / 连续满档 ⇒ 生成式称号（"日课不辍""周常全勤"）✓。

### 11.5 老柯：从"商店"变成"老板"

- 老柯现在只"收货/卖货"；任务让他**主动派活** ⇒ NPC 有了**人格与议程**（`docs/13` 的人设）；
- 与**等级/评定**打通：高等级才有更高价值的委托 ⇒ 给"升级"一个除商店解锁外的第二理由 ✓。

### 11.6 与其它系统的联动（**复用，不并列**）

| 联动                        | 玩法                                   |
| ------------------------- | ------------------------------------ |
| **图鉴**                    | 委托可指定"没点亮的鱼" ⇒ 任务变成**图鉴的引导**         |
| **称号**（`docs/38`）         | 完成数 / 活跃度满档 ⇒ 生成式称号，授称号复用 `Titles` ✓ |
| **联赛/比赛**（`docs/37`/`35`） | 委托可要求"本期联赛里钓到 X" ⇒ 任务成为**联赛的引导层**    |
| **时间/天气/月相**（`docs/24`）   | 条件委托（"雨天/夜钓/满月"）⇒ 让环境系统**有存在感**      |
| **料理**（`docs/25`）         | 委托要"交一条做料理的鱼" ⇒ 把烹饪线拉进日常             |
| **移动终端**（§10）             | 一个入口看全部 ⇒ 玩家**不用记"哪个功能在哪个物品上"** ✓    |

### 11.7 ⚠ 反玩法（明确不做 ✗）

| 不做           | 为什么                             |
| ------------ | ------------------------------- |
| 挂机/在线时长可完成   | 任务必须靠**上鱼事件**推进 ✗               |
| 每日强迫（漏一天就落后） | 基础奖励与"连续"脱钩；活跃度也**不用满勤**（§7.1）✗ |
| 接了就发的"参加奖"   | `docs/37` §5.3 的教训（催生小号/挂机刷）✗   |
| 为任务新造通信/进度系统 | 违反 §1 的"三条不新造" ✗                |
| **红鱼级高难周常**  | 用户第 4c 条明令禁止 ✗                  |
