## 1. 为什么需要邮件箱（而不是继续各自弹提示）

现在模组"告诉玩家一件事"的方式是**四套并存的**：

| 现状 | 问题 |
|---|---|
| `player.displayClientMessage(...)`（聊天栏/动作栏） | 玩家没看就**永久错过**；不在线就**根本收不到** |
| `CodexRewards` 直接把鱼币塞进钱包 | 钱多了但**不知道为什么多**（玩家会以为算错了）|
| `ItemHandlerHelper.giveItemToPlayer` / `player.getInventory().add` + `player.drop(...)` 兜底 | 背包满时**掉在脚下**（`FirstJoinEvents` 的教程书、`AnvilEvents` 的旧配件都是这么写的）—— **不会凭空消失** ✓，但**会散落**：可能掉进岩浆、被掉落物清理规则清掉、或被别人捡走 ✗ |
| 手册（指南书）里的静态章节 | 只能写"永久规则"，写不了"你这一封信" |

⇒ 邮件箱一次性解决这四件事：**离线也能收到、有记录可回看、附件不会丢、能带一个动作按钮**。

## 2. 数据模型

### 2.1 存哪：**新开一个玩家附件**（不塞进 `PlayerFishingData`）

| 方案 | 评价 |
|---|---|
| 塞进 `PlayerFishingData` 加一个 `List<MailEntry>` 字段 | ✗ 那个 record 现在有 **5 处构造点**（`withCoins/addCoins/withGuideGiven/recordCatch/markClaimed`）+ `EMPTY` + Codec，每加一个字段都要全改一遍；而邮件是**不断增删的表**，每次上鱼重建整张表不划算 |
| **新附件 `PLAYER_MAILS`**（`MailBox` record + 自己的 Codec + `copyOnDeath`） | ✅ 推荐：与鱼币/图鉴互不影响；`copyOnDeath` ⇒ 死一次不会把邮件清空；老存档没有这个附件 ⇒ 默认空表 ✓ **零迁移** |

`MailBox` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `mails` | `List<MailEntry>` | 按**收到时间倒序**（最新在最上面；界面直接照序画） |
| `nextId` | `int` | 递增序号（邮件 id = 玩家的 `序号`，够用且短；不用 UUID 是为了界面上可读、日志里可查） |

⚠ **不存"未读数"** —— 未读与待领都是**从列表数出来的派生值**（`mails.count(!read)`）。
单独存一个计数器迟早和真实状态不一致（本仓库"两套刻度"那两次事故就是同一类：两个真源、不崩不报错、只是数不对）。

`MailEntry` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `int` | 收件人自己的序号（界面/网络包只用它） |
| `template` | `String` | **模板 id**（如 `league_invite` / `codex_milestone` / `admin`）——文案在**语言文件**里 ✅ 见 §2.3 |
| `args` | `List<String>` | 模板参数（鱼名、名次、期号…）—— 服务端**不拼中文**，只传参数 |
| `sentAt` | `long` | 收到的**现实时刻**（毫秒）—— 界面要显示"3 天前"，用现实时刻最直观 |
| `read` | `boolean` | 读过没有（**与"领没领"是两件事** ⚠ 见 §3） |
| `claimed` | `boolean` | 附件领过没有（没有附件的邮件恒为 true） |
| `coins` | `long` | 附件：鱼币（0 = 没有） |
| `items` | `List<ItemStack>` | 附件：物品（可为空；**最多 4 格**，多了界面放不下也没必要） |
| `action` | `String` | 可选的**动作按钮**（如 `league_join`；空 = 没有按钮）—— 见 §4.2 |

### 2.2 附件里的物品

- 用 `ItemStack.CODEC` 直接存 NBT ⇒ 附魔/名称/自定义组件都保留 ✓；
- ⚠ **邮件里的物品是"冻结"的**：不参与耐久扣除、不参与堆叠变化（它不在任何人的背包里）；
- ⚠ 领取时**先试着进背包**（`player.getInventory().add`），**进不去就留在邮件里**并把邮件标成"背包已满"——
  绝不掉地上、绝不静默销毁 ✓（这一条守的是 `AnvilEvents` 那个老问题）。

### 2.3 文案与多语言（关键纪律）

服务端**没有语言表**（这是排行榜当初只能显示 `greenland_shark` 的原因）。
所以：**服务端只发 `template + args`，客户端本地化**。

| 语言键 | 例 |
|---|---|
| `mail.anglertackle.league_invite.title` | `%s 联赛邀请` |
| `mail.anglertackle.league_invite.body` | `第 %s 期%s联赛已开始，%s 后结算。点击下方按钮签收奖励并参赛。` |
| `mail.anglertackle.league_invite.button` | `签收` |
| `mail.anglertackle.league_result.title` / `.body` | 《第 %s 期%s联赛成绩单》：你的名次 %s，冠军 %s（%s） |
| `mail.anglertackle.codex_milestone.*` / `.level_gate.*` / `.restock.*` / `.admin.*` | 见 §4 清单 |

⚠ **文案里不许写死数字**（名次、数量、时间都由参数传）——
本仓库在手册数字上已经踩过好几次"改配置不改文案"。

### 2.4 配置项（`[mail]` 组，全部可热改）

| 键 | 默认 | 含义 |
|---|---|---|
| `keepDays` | `30` | 邮件保管期（**现实天**）；过期只作废附件、正文保留 |
| `maxMails` | `200` | 邮箱条数上限；到顶**拒绝投递**（WARN 日志 + 提示），绝不静默丢件 |
| `bodyMaxChars` | `500` | 服主手写正文的长度上限（编辑器侧拒绝 + 渲染侧再截断） |
| `unreadLoginNotice` | `true` | 进世界时是否给一次"你有未读邮件"的动作栏提示（**只一次**） |

> 其余数字（未读数 / 待领数 / 每页行数）**不配置**：它们要么是派生值、要么由 `UiLayout` 按窗口现算 ✓

## 3. 生命周期与状态机（最容易做错的一处）

```
        收到（服务端写入）
              │
        ┌─────▼─────┐   点开看一眼     ┌──────────┐  点【领取】  ┌───────────┐
        │  未读      │ ───────────────▶│  已读     │ ──────────▶│  已领取    │
        │ UNREAD    │                 │ READ     │            │ CLAIMED   │
        └───────────┘                 └──────────┘            └───────────┘
              │                             │                       │
              └──────── 超过保管期（默认 30 现实天）───────────────┘
                              ▼
                      已过期（附件作废，正文保留为"记录"）
```

**三条硬纪律**：

1. **"已读" ≠ "已领"** ⚠ —— 把"点开就自动领"当省事方案，会让"玩家点开看了一眼、背包满、物品留在哪？"无解；
   必须两个独立位。这也是**签收按钮要单独存在**的原因（用户需求原文："点击邮件之中的签收按钮"）。
2. **领取是服务端动作**：客户端只能发"我要领第 N 封"，能不能领由服务端判定
   （邮件在不在、领没领过、背包满不满）⇒ 与排行榜"服务端纯读"、玩家设置"只改自己"同一套纪律。
3. **过期只清附件、不清正文**：30 天没领的物品作废（界面在过期前 3 天标红提醒），
   但"这封信说过什么"留在记录里 —— 否则玩家会觉得"我的邮件被人删了"。

## 4. 邮件能用在哪儿（用户点名要的部分）

### 4.1 应用清单

| # | 用途 | 触发时机（谁写） | 附件 | 例子（**可实现的例子**） |
|---|---|---|---|---|
| 1 | **联赛邀请**（本轮主用例，见 `docs/37`） | 跨期那一刻，服务端给 `level ≥ 21` 的玩家各写一封 | 小额鱼币 + 1 份饵料 + **动作按钮【签收】** | 《第 3 期小型联赛邀请》→ 点签收：领 50 币 + 活虾×2，同时报名 |
| 2 | **联赛/比赛成绩单** | 结算那一刻，给每个参赛者 | 名次奖励（第 1 名大额） | 《小型联赛（第 3 期）成绩单》：你第 2 名，冠军 老白 4.82kg 大西洋鲑，奖励已附 |
| 3 | **图鉴里程碑奖励**（改造现有 `CodexRewards`） | 点亮数跨过 2/4/6… 时 | 50 币 | 现在直接进钱包 ⇒ 改成"发信"，玩家**知道**这 50 币是哪来的；⚠ 老玩家已领过的不重复发（`claimedMilestones` 位掩码不变 ✓） |
| 4 | **等级评定通过 / 升级通知**（`AnglerLeveling.GATE_LEVELS`） | 通过评定②那一刻 | 无（或小额饵料） | 《恭喜通过评定②：绿梭鲈》→ 正文写"下一段等级 21–30 的商店档位已解锁" |
| 5 | **商店补货提醒** | 玩家**登录时**检查一次自己的 `FishermanProgress.Stock.restockAt`（存的是 `Level.getGameTime()`，即"游戏刻"⇒ 只在服务器运行时推进），到点了就补一封 | 无 | 《老柯的货补上了》：你上次没抢到的「高质吸引」附魔书又有货了 ⚠ 不要每 tick 检查（那是白跑）|
| 6 | **老柯来信（NPC 剧情/引导）** | 关键节点：首次进服、首次钓到金档、首次断线 10 次… | 有时带小礼 | 《老柯：小子，来我这儿一趟》→ 与现有 `talked` 标记衔接：读过这封信后，右键老柯多一句台词 |
| 7 | **新手礼包**（改造 `FirstJoinEvents`） | 首次进游戏 | 教程书 + 木竿 + 饵 | 现在直接塞背包（"背包满就掉地上"）⇒ 改成邮件，玩家点【领取】才入包 ✓ |
| 8 | **离线奖励保管** | 结算/发奖时玩家不在线 | 全额奖励 | 玩家离线三天回来 ⇒ 奖励在邮箱里等着（保管期 30 天）✓ |
| 9 | **服主公告 / 手动发信** | `/atl mail send <玩家> <标题> <正文>`（**需要 OP**） | 可选 | 服主开活动："今晚 8 点钓鱼比赛，前 3 名额外奖励" |
| 10 | **退件兜底**（改造 `AnvilEvents` / `GrindstoneEvents`） | 背包满时本该掉地上的配件 | 那件物品 | 现在"配件掉在脚下"⇒ 改成寄一封《你的配件》，永不丢失 ✓ |

### 4.2 "动作按钮"是什么（联赛能用、别的也能用）

`MailEntry.action` 是一个**服务端认识的动作 id**（不是客户端随便执行的东西）：

| action id | 服务端做什么 | 谁能用 |
|---|---|---|
| `league_join` | 校验资格 + 本期在跑 + 未签收 ⇒ 记入 `joined` 表、发签收奖励、标记已签收 | 收到该邀请的人 |
| `league_claim` | 领成绩单奖励（等价于普通【领取】） | 收件人 |
| `none` | 只有【领取】按钮 | 所有带附件的邮件 |

⚠ **服务端只认白名单 id**；客户端**不能**自己定义动作、也不能指定"替谁执行"
（与玩家设置那条"提交包不带 UUID"完全同一条纪律）。

### 4.3 兼容既有设计的**约束**（用户点名的"需要兼容"）

| 已有设计 | 邮件系统必须怎么兼容 |
|---|---|
| 玩家附件 + `copyOnDeath` + `optionalFieldOf` 默认值 | 新附件照抄这套（死一次不清空、老存档零迁移）✓ |
| 服务端权威、客户端只显示 | 邮件**全部**服务端读写；客户端只发"读/领/删"三个动作 ✓ |
| 语言键中英成对（`check-lang`） | 每个模板的 `title/body/button` 都要中英齐 ✓ |
| 界面走 `UiLayout`（面板按窗口 clamp、行数现算、文字截断） | 邮件界面**必须**用同一套（否则小窗口会切内容）✓ |
| 品质色只有一个真源 `Quality` | 邮件里的鱼名/品质色都走它，不自己写颜色表 ✓ |
| 数值全部走调参器（可热改） | 保管期、每页条数、签收奖励额全进配置 ✓ |
| 每个改动配断言 + 负例 | §6 给清单 ✓ |

## 5. 界面设计（"清爽且有设计"）

> 本节的设计不是凭空想的：**先查了 8 个真实案例**（子代理只做检索、未改任何文件），
> 再按"钓鱼模组 = 单向发奖/公告信箱"这个定位裁剪。案例与出处见 §5.1，
> 提炼出的规则见 §5.2，最后给出**可直接用的图像生成提示词**（§5.6，用户点名要的那份）。

### 5.1 参考案例（有出处）

| 案例 | 可借鉴的点 | 出处 |
|---|---|---|
| **FTB Quests**（NeoForge 同代） | 奖励领取型界面的最佳参照：**列表不删**、状态用 `!` **分层传递**（章节/任务/物品栏图标各带 `!`）、**主操作固定在右上角**（Claim all）、"多选一"奖励回详情页手动点 | https://docs.feed-the-beast.com/mod-docs/mods/suite/Quests/Player/Questbook/Navigating/ |
| **MailboxGUI**（Spigot 邮箱插件） | 成熟邮箱的必备两件事：**只读查看**（不领取就能看内容）与**过期是独立状态**（不是直接消失） | https://www.spigotmc.org/resources/134394/ |
| **Mighty Mail**（MC 实体信箱模组） | 未读用**箱子上方一面红旗**表示；投递队列有**硬上限**（默认 18） | https://www.pwrdown.com/minecraft/minecraft-guides/minecraft-mighty-mail-mod-guide-tutorial/ |
| **《动物森友会》** | "一件事只有一个入口"；**用强约束代替选项**（寄信有每日上限、未来信只能留一封） | https://nookipedia.com/wiki/Letter |
| **《魔兽世界》** | **附件 = 一排格子、动作 = 一排按钮**（读信区因此极干净）；正文上限 **500 字符**；邮件保留 **30 天**；邮箱最多显示 **100 条**（3A 也选硬截断）；历史上"读过的信 3 天就过期"**被官方改掉了**（说明那设计是坏的） | https://warcraft.wiki.gg/wiki/Mail |
| **《FF14》莫古力邮差** | 官方把邮箱定位成**单向发奖/公告渠道**（不是社交私信）⇒ 界面只需"发件人 + 标题 + 附件" | https://support.na.square-enix.com/faqarticle.php?id=5382&kid=78603 |
| **《原神》** | 把"过期不可找回"写进公开 FAQ ⇒ **过期规则必须在界面里可见**（剩余时间），否则玩家认定是丢东西 | https://support.hoyoverse.com/hc/en-us/articles/50913709855769 |
| **《死亡搁浅》**（反例 ⚠） | 在列表里"滚过去"会让感叹号消失，**但那封信并没变成已读** ⇒ **别让"看到"自动等于"已读"**，否则未读数会莫名归零 | https://stratege.ru/ps5/games/death_stranding_directors_cut/trophies/spisok |

**定位结论**：本模组的邮箱 = **单向发奖 / 通知信箱**（不是玩家间通信），
所以**不做**写信、回信、好友私信 ✗ —— 界面只承担"看信 + 领东西 + 按一个动作"。

### 5.2 从案例里提炼的规则（本界面照此执行）

| # | 规则 | 依据 |
|---|---|---|
| 1 | 列表**固定行高**，一行只有**三个信息槽**：左（标记）、中（标题 + 发件人小灰字）、右（相对时间 / "待领取"） | 综合 FTB / Mighty Mail / WoW |
| 2 | **未读 = 左侧 2~3px 窄条 + 标题亮色；已读 = 标题降一档灰** —— **不整行变色**（会与品质色打架） | 同上 |
| 3 | **"未读"与"待领取"是两件事**：未读用**冷色**小点，**待领取用金色标记**（复用"金=值钱"的既有语义）—— 玩家真正关心的是"有没有奖励没拿" | 子代理推断（钓鱼模组定位） |
| 4 | **划过不算已读**（只有真正打开详情才置已读），**未读数是派生值**（由列表数出来，不单独存计数器） | 《死亡搁浅》反例 + 本仓库"两套刻度"事故教训 |
| 5 | **主操作唯一且位置固定**（右下角）：【签收】/【领取】/灰掉的【已领取】；破坏性操作永远靠远、灰色、二次确认 | FTB 的 Claim all 在固定角 |
| 6 | **附件 = 格子，动作 = 按钮**：附件区用 18×18 格排（对齐背包格），悬停出 tooltip | WoW 的分工 |
| 7 | **分页 > 滚动**：MC 的 `Screen` 本身不支持滚动，自研 `UiLayout` 也没有滚轮事件 ⇒ 一页 N 行 + 翻页箭头成本最低、手感最像原版 | 原版列表惯例 + FabricMC 教程 |
| 8 | **相对时间**（"3 小时前"/"昨天"）比 `2026-02-14 21:03` 省一半宽度 | 子代理推断 |
| 9 | **过期用"剩余 X 天"文字**（临近 24h 转红），不用进度条 | 《原神》FAQ 的教训 |
| 10 | **一个主按钮 + 一屏不堆操作**；第一版**不做【一键全领】**（奖励混在一起，玩家分不清哪封给了什么）；真要做时必须**带数字确认**（"确认领取 7 封的全部奖励？"） | 子代理建议 + 本仓库"不许静默"的文化 |

### 5.3 线框（设计尺寸 470×224，与既有界面同一档；窗口小时由 `UiLayout` 折）

```
┌─ 邮箱 ───────────────────────────────────────────── 未读 2/7 ─┐
```

- **列表**：每行两行字（标题 + 发件人），行高 **24**（`UiLayout.rows` 现算每页行数）；

- **详情**：发件人 + 时间（一行灰字）→ 分隔线 → 正文（自动折行，超出截断）

  **不画空列表** ✗（空列表和"加载失败"长得一模一样，本仓库在图鉴上踩过这个坑）。
- **未读角标**：邮箱物品 tooltip 常驻"未读 2 · 待领 1"；进世界时若未读 > 0 给**一次**动作栏提示（不反复弹 ✗）。

**交互细则**

| 场景 | 行为 |
|---|---|
| **鼠标划过列表行** | **什么都不发生** ⚠（《死亡搁浅》的反例：划过就消感叹号，但信并没已读 ⇒ 未读数会莫名归零）|
| 点列表行（打开详情） | 选中 + 标为已读（**不自动领取** ⚠ §3 纪律 1）|
| 点【领取】 | 先试进背包；进不去的**留在邮件里**，按钮变"背包已满"并灰掉（腾出空位再点）✓ 不掉地、不销毁 |
| 点【签收】（联赛） | 一次动作完成"领奖励 + 报名"，成功后就地刷新：按钮 → "已签收 ✓" |
| 批量 | 只给【全部已读】；**第一版不做【一键全领】** ✗（奖励混在一起分不清哪封给了什么）；将来要做必须**带数字确认** |
| 删除 | 单封可删（**已领取的才能删**；未领取的需二次确认）—— **第二阶段**再做 |
| 键盘 | `Esc` 关闭；`↑/↓` 在列表里移动选择（可选，列表控件自带键盘导航与朗读）|
| 过期提醒 | 未领取邮件在**列表右槽**显示"剩 X 天"，≤24h 转红；详情里写"附件将在 X 天后作废"（正文永久保留）|

### 5.4 像素规格（和既有界面对齐，**不照抄原版 176×166**）

⚠ 原版容器 GUI 的贴图标准尺寸是 **176×166**，但**本仓库的 5 个界面都不是容器贴图**：
它们用自研 `UiLayout` 现算面板（图鉴 570×224、指南 400×224、改装 420×216、商店 340×210，`MARGIN=16`）。
而且 **176 宽根本放不下"列表 + 详情"并排**（要 ~300 以上）——
所以邮件界面沿用本仓库这一套，**不引入原版贴图** ✓

| 项 | 取值 | 理由 |
|---|---|---|
| 设计尺寸 | **470×224**（列表 200 + 间隙 10 + 详情 244 + 边距） | 与既有界面同一档；`UiLayout.panelW/H` 按窗口 clamp |
| 最小可读尺寸 | `MIN_W 260 / MIN_H 160` | 与既有界面同一档（`check-ui-fit` 会用四种窗口尺寸验） |
| 列表面板 | 宽 200，行高 24，每页行数 = `UiLayout.rows(panelH, LIST_Y, FOOTER, 24)` | 不写死行数（写死就会在小窗口切行）|
| 详情正文 | 行高 12，最多 10 行（超出"…"），宽 = 详情栏宽 − 12 | 用 `MultiLineLabel` 思路自动折行；`UiLayout.fitText` 兜底 |
| 附件格子 | **18×18**（背包格尺寸），最多 4 格 | 与背包视觉一致（WoW 的分工：附件是格子不是按钮）|
| 按钮 | 高 **18**（与既有 5 个界面一致；原版惯例是 20，**内部一致优先**） | 既有代码一律 `.bounds(..., 18)` |
| 边框 | 外 1px 深 + 内 1px 亮（经典斜面）；列表行**不加投影**，投影只给面板整体 | 像素风规矩（子代理规范 §3）|
| 配色 | **复用既有常量**：`C_PANEL 0xFF243028` / `C_LINE 0xFF5A6A60` / `C_TITLE 0xFFFFD050` / `C_LABEL 0xFF8FCBF5` / `C_TEXT 0xFFE8E8E8` / `C_DIM 0xFFB0B0B0` / `C_HINT 0xFF909090`；品质色一律走 `Quality` | 见 `CodexScreen` 顶部常量；**不许另起一套色板** ✗ |

### 5.5 硬上限与截断（案例逼出来的两个数字）

| 项 | 取值 | 超限时怎么办 |
|---|---|---|
| 邮件条数上限 `maxMails` | **200** 封（可调） | **拒绝投递**：服务端日志 WARN + 给收件人一条聊天提示"邮箱已满"；**绝不静默丢件** ✗（WoW 100 / Mighty Mail 18 都有硬上限） |
| 服主正文长度 `bodyMaxChars` | **500** 字符（与 WoW 同量级） | `/atl mail send` 直接拒绝并告诉服主"太长了"；**渲染侧再截断一次**（两道都要，只做一道会溢出面板） |
| 已读邮件清理 | 超过保管期（默认 30 现实天）**且已领取**的自动清理 | 未领取的**永不自动删**（WoW 曾经"读过 3 天就删"，被官方改掉了 —— 说明那是坏设计）|

## 6. 检查器与负例（交付时必须一起给）

| 断言 | 反例（必须红） |
|---|---|
| 文案只来自 `template + args`（服务端不拼中文） | 在服务端 `Component.literal("第 3 期…")` 里拼中文 |
| 每个模板的 `title/body/button` 中英齐全 | 删掉一个模板的英文键 |
| "已读"与"已领"是**两个独立位** | 把 `read = true` 当成 `claimed = true` |
| 领取只在服务端、且只作用于**发起者自己** | 动作包里加 `targetUuid` |
| 背包满时物品**留在邮件里**（不掉地、不销毁） | 直接 `player.getInventory().add` 而不管返回值（⇒ 掉在脚下散落） |
| 附件过期只清附件、正文保留 | 过期时整封删掉 |
| 老存档零迁移（`optionalFieldOf(默认空表)`） | 用 `fieldOf` |
| 邮件不设条数上限、但已读超期会清理（且清理不动未领） | 无上限地永久堆积 / 把未领的也清掉 |
| **未读数是派生值**（由列表数出来） | 另存一个 `unreadCount` 计数器（迟早不一致） |
| 列表到上限（`maxMails`）时**拒绝投递并提示**、写服务端 WARN | 静默丢件 / 悄悄挤掉最旧的一封 |
| 服主正文超 `bodyMaxChars` 时**拒绝发送**；渲染侧**再截断一次** | 只做一道（会溢出面板 / 或写进去就再没提示）|
| **鼠标划过列表行不改变已读状态** | 在 row hover 里 `read = true`（《死亡搁浅》反例）|
| 界面用 `UiLayout`（四种窗口尺寸都装得下） | 面板尺寸写死常量 |
| 未读提示**只提示一次** | 每 tick 弹动作栏 |

## 8. 反例（明确不做 ✗）

- **不做**【一键全领】：奖励混在一起，玩家分不清哪封给了什么，也没法"先看再领"；
- **不做**邮件里的"回信/聊天"（那是聊天栏的事）；
- **不做**跨存档/跨服的邮件（邮件属于玩家在该存档的附件 ✓ 与鱼币/图鉴同一生命周期）；
- **不做**"服务端拼中文"（会绕开语言表 ⇒ 英文客户端看到中文 ✗）；
- **不做**"读信即领奖"（§3 纪律 1）。
