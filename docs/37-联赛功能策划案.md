## 1. 定位

### 1.1 联赛 ≠ 比赛（先把边界划清，免得做重）

| | **比赛**（docs/35，M2） | **联赛**（本文件） |
|---|---|---|
| 时长 | 一场 **30 分钟** | 一期 **30/120/360 游戏日** 或 **7/30/90 现实天** |
| 参加 | **全员自动**（钓到就算） | **邀请制**：够格者收到邮件，**点签收才算入场** |
| 节奏 | 当场结算、当场广播 | 周期结算、公示、下一期重新邀请 |
| 共用 | 记分口径（上鱼那一帧的服务端数据）、公示方式、奖励幂等、**邮件箱** | 同左 |

> **共用一套记分与结算**是硬约束：绝不为联赛另写一份"怎么算成绩"。
> 否则两份口径迟早分叉（本仓库在"档位 0 起算 / 1 起算"上已经栽过两次）。

## 2. 三个级别（小型 / 中型 / 大型）= **推送间隔**

**资格相同**（都是 Lv.21+），区别在**多久推一次邀请**与**奖励倍率**；
**每一期怎么跑**由下面这条新规则统一决定（用户 2026-10-11 定案，见 §3.4）。

| 级别 | **推送间隔**（默认，现实口径）| **推送间隔**（游戏口径）| 典型用途 | 奖励倍率 |
|---|---|---|---|---|
| **小型联赛** | 每 **7 天** 推一次 | 每 **30 游戏日** | 熟人服、每周一轮 | ×1 |
| **中型联赛** | 每 **30 天** 推一次 | 每 **120 游戏日** | 常规服务器 | 币/经验 **×2** |
| **大型联赛** | 每 **90 天** 推一次 | 每 **360 游戏日** | 长期服/赛季制 | 币/经验 **×4**、原版物资 **×1.5** |

> ⚠ **换算必须写进服主文档**：**1 游戏日 = 24000 tick = 20 分钟**（原版一天）⇒
> 30/120/360 游戏日 = **10 / 40 / 120 小时**；而**游戏口径只在这些小时里服务器真的在跑时才推进** ——
> 每天只开 2 小时的服，"大型联赛"的推送间隔实际是 **60 个现实日**。

### 2.1 ⚠ **据调研改**：同一时刻**只开一级**（默认），不做三级并开

- 调研实证（arXiv 临界质量 + "**离场级联**"）：**分级就是分割人口**；人少→排队久→体验差→更少人上线，
  一旦进入级联，**外部干预收效甚微**。本模组还要把稀疏人口切成三份 ✗。
- ⇒ 默认 **`allowConcurrent = false`**：三级按**轮转**进行（小 → 中 → 大 → 小…，或服主指定下一期开哪级），
  **同一时刻只有一级在跑、只有一种邀请**。服主想并开可以打开（代价写进配置注释）。
- 分级用**绝对门槛**式描述（学星露谷鱿鱼节），**绝不用"前 N%"**（10 人服里"前 10%"毫无意义）✓
- **不做硬升降级**（学皇室战争：赛季末软重置而不是逐级降）；本模组连"段位"都没有，只按期公示名次 ✓

**赛制（计分口径）**：默认 **最重一尾**（与 `Leaderboard.Board.HEAVIEST` 同源）；服主可切
`heaviest / total_weight / high_tier_count / codex`。

⚠ **据调研改（防刷分）**：**排除 `fastest_catch`（最短上鱼时间）与 `streak`（连击）** ——
调研结论直说这两项"极易被脚本刷"；只作排行榜展示，**不进联赛计分**。
一期只用一个口径，开期时钉死（中途改口径 = 榜单错乱 ✗）。

## 3. 计时：两种口径与它们的坑

用户要求"**根据管理需求可以自行切换计时方式**"⇒ 配置项 `leagueClockMode = game_days | real_days`。

### 3.1 只用**单调递增**的计数器（这是本节最重要的一条）

| MC 里有两套时间 | 会不会被改写 | 能不能用来算周期 |
|---|---|---|
| **累计刻 `totalTime`**（`ServerLevel.getGameTime()`） | 只增不减 ✓ | ✅ **只用它** |
| **世界时刻 `dayTime`**（`getDayTime()`） | **睡觉直接把时钟推到天明**；`/time set` 可任意改；`/gamerule advance_time false` 能冻结 | ❌ **绝不用**（按它算，睡一觉赛季就跳完了 ✗） |

（MC 官方 Wiki 的 Daylight cycle 条目把这两套时间写得很清楚；调研也把"睡觉跳夜"列为第 1 号坑。）

### 3.2 七个坑与逐条处理

| # | 坑 | 处理 |
|---|---|---|
| 1 | 睡觉跳夜 | 用 `getGameTime()`（累计刻）⇒ **天然不受影响** ✓ |
| 2 | `/time set` / 命令方块改时钟 | 同上 ✓；配置注释里写明"**作弊改时不影响联赛进度**" |
| 3 | 单人存档开菜单**暂停时钟** | 游戏口径按**实际流逝的游戏刻**算 ⇒ 暂停即暂停（符合直觉）✓ |
| 4 | **服务器重启 / 回档** | ⚠ **回档会让计数倒退** ⇒ 锚点取 **`max(存档里的锚点, 本次读到的累计刻)`** 钳制；发奖流水另有幂等键（§5）⇒ 回档也不会重复发奖 ✓ **据调研补** |
| 5 | 换存档/新周目 | 累计刻从 0 开始 ⇒ 存档里存**本档自己的纪元起点**，不从 0 直接算 ✓ |
| 6 | 时区（现实口径） | **按服务器本地时刻定义边界**（学 LoL 的"各服本地 12:00:00"）：每期从"首日 **本地 12:00**"起算，界面/邮件里公示**精确到分钟的结算时刻** ✓ **据调研改** |
| 7 | 系统时钟被改 | 用 UTC 毫秒差 + **负数增量夹到 0**（否则改一次时钟能瞬间跨期 ✗） |

### 3.3 实现口径（写死，别漂移）

- 世界级 SavedData `anglertackle_league`：
  `mode（game_days / real_days）/ pushAnchorWallMillis / pushAnchorGameTime / lastSeenGameTime /
  periodDays（推送间隔）/ ruleId / seasonId / allowConcurrent /
  hardDeadlineTick（本期硬截止）/ joined: Map<UUID, {windowEndTick, 成绩}> / settled: 发奖流水键集合`；
- 每 **20 tick** 检查一次（与 `BarrelFermenting` 同一个节流习惯，**不每 tick 算**）；
- **两个判定**（对应 §3.4 的两个时钟）：
  1. **推送**：`now - pushAnchor >= 推送间隔` ⇒ 结算上一期（若还未结算）+ 推新一期 + `pushAnchor += 间隔`；
  2. **硬截止**：`now >= hardDeadlineTick` ⇒ **强行结算**并**同时推送下一期邀请**（用户要的是"推送→5 游戏日→结算"的节奏）；
  ⚠ 两条都**只播一次**（用 `seasonId` 与 `hardDeadlineTick` 的去重键推进）；
- ⚠ 结算与推送都在**同一段代码**里先后完成，用 `seasonId` 推进 ⇒ **两期不可能重叠** ✓；
- ⚠ 锚点推进用 `+= 间隔`（**不是 `= now`**：用 `= now` 会把停机期间的时间吞掉，节奏越跑越偏）；
- ⚠ **回档**：锚点与硬截止都取 `max(存档值, 当前值)` 钳制（否则回档后重复结算 ✗）。

> ⚠ **实现时的一处偏差（2026-10-12 落地时定的，用户"继续推进，默认你的数值"）**：
> 上面第 2 条原文是"硬截止 ⇒ **强行结算并同时推送下一期**"。照字面做的话，一期只跑 5 游戏日
> （≈100 分钟运行时间），于是**每 100 分钟就会开一期新的** —— 三级间隔 7/30/90 天会被压成同一个节奏，
> "大联赛"与小联赛再无区别 ✗。
> ⇒ 落地时把两条的效果**拆开**：**硬截止负责"结算"**（用户原话"无论有没有打满，结算时也强行截止" ✓），
> **推送间隔负责"开期"**（7/30/90 天）。停机很久再回来时两条可能同时到点 ⇒ 先结算、再开新期，
> **一期都不会丢** ✓。守着这条的是 `tools/check-league.js`（"硬截止强行结算"+"结算与开期在同一段代码里"）。

## 3.4 ★ 一期的时间轴（**用户 2026-10-11 定案，整套计时按这条**）

用户原话：

> "联赛**由参与之时开始计时，每人独立**，但**联赛推送后无论玩家签不签收都是在推送后 5 个游戏日后结算**。
> **每人参赛后计入的参与时间是 30 分钟。无论有没有打满，联赛结算时也强行截止。**"

⇒ 一期里有**两个时钟**，一个是全局的、一个是每人各自的：

```
推送邀请 T0（服务端统一时刻）
  │
  │  全局硬截止 = T0 + 5 游戏日 = 120000 tick ≈ 运行 100 分钟
  │  （到点**不管谁打没打满，一律结算** ✓ 用户原话"强行截止"）
  │
  ├── 玩家 A 第 3 分钟签收 ──▶ 他的窗口 = [签收, 签收 + 30 分钟游戏时间]
  ├── 玩家 B 第 90 分钟签收 ─▶ 他的窗口只有 10 分钟（被硬截止截断）✓ "无论有没有打满"
  └── 玩家 C 从不签收 ──────▶ 没有窗口、不计分，但**他照样会收到结算公示**（未参赛）
```

| 数字 | 值 | 换算 |
|---|---|---|
| **全局硬截止** | 推送后 **5 游戏日** | 120000 tick ≈ **运行 100 分钟**（1 小时 40 分）|
| **每人窗口** | 签收后 **30 分钟**（游戏时间）| 36000 tick |
| 窗口终点 | `min(签收刻 + 36000, 硬截止刻)` | 两个都取，谁先到算谁 ✓ |

**只计分不惩罚**：窗口走完了也别拦着他继续钓鱼 —— 只是**本期联赛不再计分**（其他玩法完全不受影响）✓；
界面/邮件里写清"本期参与时间已用完"。

⚠ **两处口径我按最直白的读法实现，见 §9 待确认**：
1. **30 分钟从"签收那一刻"起算**（而不是"只在实际钓鱼时消耗"）；
   —— 若你要后者（只在有钓鱼会话时才走表），规则改成"累计钓鱼 30 分钟"，我照改；
2. **两个时间都用游戏刻**（`getGameTime()`）⇒ 服务器停机期间两边都停 ✓（与"5 游戏日"这个口径一致）。

## 4. 邀请 → 签收 → 参赛

```
推送那一刻 T0（服务端）
   ├─ 结算上一期（若到点）：按 ruleId 取名次 → 写发奖流水 → 线入账/离线寄邮件 → 公示
   ├─ 生成本期邀请：遍历够格（level ≥ 21）的在线 + 离线玩家
   │     └─ 每人一封《XX联赛邀请》，附件 = 签收奖励，按钮 = 【签收】，正文写清
   │        "本期参与时间 30 分钟 / 本期在 5 游戏日后统一结算"
   └─ seasonId + 1；hardDeadline = now + 5 × 24000 tick

玩家点【签收】（服务端校验）
   ├─ 校验：邮件是自己的 / 未签收 / **本期还没到硬截止** / level ≥ 21
   ├─ 领奖励：鱼币 / 物品入账（已有的 addCoins / giveItemToPlayer）
   ├─ 报名：joined 表写 {uuid → 窗口终点 = min(now + 36000, hardDeadline)}
   └─ 邮件状态改"已签收"，界面实时刷新

上鱼那一帧（计分）
   ├─ 只对"已签收且 now ≤ 该玩家的窗口终点"的鱼计分 ✓（每人独立，A 的窗口不影响 B）
   └─ 窗口用完或已过硬截止 ⇒ 本期不再计分（不报错、不提示刷屏，界面里能看到剩余时间）

硬截止（T0 + 5 游戏日）
   └─ **强行结算**：写成绩快照 → 排名 → 发奖（幂等流水）→ 全服公示 → 每人一封《成绩单》
```

### 4.1 为什么"点一下签收"是对的（有出处）

子代理找到了**禀赋进度效应**（Nunes & Drèze 2006）的洗车卡实验：**同样要集 8 次**，
"先送 2 次、需集 10 次"那组完成率 **34%**，"不送、需集 8 次"那组只有 **19%** ——
**先给一点进度，完成率高出 15 个百分点**；机制是"让任务看起来已经开始了"。
⇒ 用户定的"**点签收即领奖励 + 参赛**"正好落在这条上 ✓（也叫承诺一致性/登门槛效应）。

> ⚠ 而"签收即开始走 30 分钟窗口"进一步放大了这条：**签收这个动作有真实代价（时间开始流逝）**，
> 所以它不是"白拿一份礼" ✗ —— 这正好把 §4.2 里"只领奖不参赛"的风险压下去 ✓

### 4.2 ⚠ **据调研改**：防"只领奖不参赛"的三件套

1. **签收奖励小且非稀缺**，**主奖励绑名次**；签收即开始计时（上一条）⇒ 白拿的收益很小；
2. **奖励分级**：只签收得 A；**签收且在本期上过鱼**再得 B 档（一封"参战确认"小信 + 少量鱼币）；
3. **把"签收后未参赛率"做成可观测指标**（写进 `/atl league stats` 与日志）——
   调研提醒这正是"参与度虚高但留存差"的早期信号。

> 反面参照（有出处）：动森奖杯按**累计分**发、兑换**不消耗累计分**，结构上不可能"拿了就跑"——
> 说明"把奖励和长期累计绑起来"是更稳的做法（本模组的长期线候选，见 §5.3）。

### 4.3 防挂机/小号（据调研）

- 计分**只用抗刷指标**（最重一尾 / 总重量 / 金红尾数 / 图鉴完成度），排除"最短上鱼/连击"（§2）；
- 采 WoW 的"**门槛 + 有效成绩下限**"双条件：本期**至少上鱼 1 尾**才进榜、才有名次奖励
  （类似 WoW 角斗士要"赢满 150 场"）；
- **不给参赛奖**（只有名次奖 + 签收小奖）⇒ 小号没有收益 ✓；
- 与排行榜同一口径：按 UUID 计，不额外反小号 ✓。

### 5.2 ⚠ **据调研改**：发奖的幂等与"结算边界"

- **幂等用唯一键流水**：`seasonId + UUID + tier` 作为主键写进 SavedData 的发奖集合；

- ⚠ **结算边界必须显式定义**（FF14 出过官方事故：重置前入本、重置后通关 ⇒ 丢新一周奖励）：
  **本模组的规则 = "以上鱼那一帧的服务器时刻归属期号"** ——

#### 5.3.4 并列名次（tie-break）—— **必须自己定，网上没有先例**

调研确认：**没有任何 MC 服务器或排行榜插件公开过并列处理规则**；而**原版**侧边栏从 14w29a（1.8）起是
"分数相同时**按名字字母序**二次排序"（[Minecraft Wiki – Scoreboard](https://minecraft.wiki/w/Scoreboard)）。

⚠ 也就是说：**照抄原版排序 ⇒ 同在奖励边界上的两个人，由"名字拼写"决定谁拿奖**，
而**玩家可以改名** ⇒ 这条 tie-break **可被操纵** ✗。

**本模组的规则（显式、可公示、不可操纵 —— 三级键，逐级比较）**：

1. **主指标**（本期 `rule`：最重一尾 / 总重量 / 金红尾数 / 图鉴完成度）；
2. **达成该成绩的时间**：**先达到者排前**（用上鱼那一帧的 `gameTime`；图鉴榜用首次点亮时间）；
3. **UUID 字典序**兜底（不可改、全局唯一）。

并在 `/atl league` 与成绩单邮件里**把这三级写出来**（"并列时先看谁先钓到"）——
规则写出来，"并列"就从争议变成规则 ✓。

## 6. 配置项（`[league]` 组，全部可热改）

| 键 | 默认 | 含义 |
|---|---|---|
| `useRealDays` | `true` | **用户要的那个旋钮**：`true` = 推送间隔按**现实天**（7/30/90）；`false` = 按**游戏日**（30/120/360）。⚠ 落地时从文档原先写的 `clockMode = real_days\|game_days` **改成了布尔** —— 调参器只认数字与布尔两种字段，加字符串要同时改模板 + schema 生成器 + 两个检查器（那是在用户天天用的调参器上做手术），而这里只有两个取值 |
| `minLevel` | `21` | 邀请资格线（"高于 20" = 过了 Lv.20 评定②）|
| `allowBelowLevel` | `false` | 打开后未达线者也收邀请（**据调研**：硬门槛会让新服长期无人参赛）|
| `smallDays` / `mediumDays` / `largeDays` | `7 / 30 / 90` | 三级的**推送间隔**（按所选口径的"天"）|
| `periodGameDays` | **`5`** | **一期硬截止**：推送后几个**游戏日**结算（用户定案 5 ⇒ 120000 tick ≈ 运行 100 分钟）|
| `playerWindowMinutes` | **`30`** | **每人窗口**：签收后多少**游戏分钟**内计分（30 ⇒ 36000 tick）|
| `periodBoundaryHour` | `12` | 现实口径下每期的起始**服务器本地时刻**（学 LoL 的"本地 12:00"）|
| `ruleMode` | `0` | 计分口径：**0 = 单鱼最重** / 1 = 总重量 / 2 = 金红尾数 / 3 = 图鉴完成度（**不含** fastest_catch / streak）。⚠ 同样是落地时从字符串改成下标 —— 顺序与 `League.Rule` 的枚举逐位绑定，`check-league.js` 双向核对 |
| `minCatchesToRank` | `1` | 有效成绩下限（至少上鱼 N 尾才进榜）|
| `inviteRewardCoins` / `inviteRewardItems` | **见 §5.3.1**（三级各不相同，逐项写死在代码里的**物品 id 表**）| 签收即得 ⚠ 物品那部分**没有做成配置**：它是"哪几件东西"而不是一个数字，做成配置就是一串 id 字符串（同上，调参器不支持）|
| `rewardCoinsParticipant` / `rewardCoinsTop10` | `500 / 2000` | 参与奖 / 第 4~10 名（小型基准）|
| `rewardCoins1st/2nd/3rd` | `10000 / 5000 / 3000` | 前三名（小型基准）|
| `rewardXp1st/2nd/3rd` | `1200 / 600 / 300` | 垂纶经验（小型基准）|
| `scaleMediumCoinsXp` / `scaleLargeCoinsXp` | `2 / 4` | 中型/大型的**币与经验**倍率 |
| `scaleLargeVanillaItems` | `1.5` | 大型的**原版物资**倍率（模组物品不缩放）|
| `rewardMailKeepDays` | **`365`** | **奖励类邮件的保管期**（**据调研改**：30 天会惩罚休假玩家；MC 生态有"14 天清数据"的实测坑）|
| `noticeMailKeepDays` | `30` | 普通通知类邮件的保管期 |
| `inviteOnLogin` | `true` | **登录时补发当前期邀请**（落地时加的，见下方说明）|

> ⚠ **`inviteOnLogin` 是落地时补的一条**（用户"继续推进，默认你的数值"）：§7 原话是"中途加入的玩家本期不再补发邀请"
> （防掐着结算前一天进来捡便宜）。但本模组的**够格名单只存在于玩家附件里**（离线读不到）
> ⇒ 推送那一刻不在线的人**永远收不到邀请**，一个每周只上两天的玩家可能一期都参加不了 ✗。
> 而用户定的"每人窗口 + 硬截止截断"（§3.4）本身就消灭了那个便宜：越晚签收窗口越短（第 90 分钟签收只剩 10 分钟）
> ✓。所以默认**补发**，并留这个开关给想要严格按文档的服主。

## 7. 边界与坑（逐条给处理）

| 坑 | 处理 |
|---|---|
| 单人存档 | **完全可用** ✓（自己跟自己比；小联赛的推送间隔正好当"周常目标"）|
| **签收后不上线** | ⚠ 他的 30 分钟窗口**照走**（按 §3.4 的直白读法）⇒ 上线时可能已经用完。界面/邮件里要写清"窗口自签收起算"；若你觉得太亏，见 §9 待确认 1（改成"只在钓鱼时消耗"）|
| **窗口用完了还想钓** | **不拦** ✓（只是本期不再计分；其他玩法完全不受影响），界面里显示"本期参与时间已用完" |
| **硬截止时正在遛鱼** | 按上鱼那一帧的期号归属：**截止之后才上岸的那条算下一期**（本期的结算已冻结快照）✓ |
| 服务器人少（< 3 人） | 照常开、照常结算（1 人参赛也公示："本期只有 1 位参赛者"）；**不设最少人数门槛** ✗（动森/星露谷/MC 榜都是单人也能拿名次）|
| 人少 + 三级并开 | **默认不并开**（§2.1）；并开时也照常，只是提醒服主"人口被切三份" |
| 中途加入的玩家 | **本期不再补发邀请**（下期开始收）⇒ 避免"掐着结算前一天进来捡便宜" |
| 中途掉到 Lv.20 以下 | **签收时**再校验一次；已签收的成绩**保留**（不能因一次降级抹掉成绩）|
| 服务器重启 | 硬截止、锚点、各人窗口都存盘 ⇒ 继续 ✓；重启期间按口径决定算不算（§3）|
| **回档** | 锚点/硬截止取 `max(存档, 当前)` 钳制 + 发奖流水幂等 ⇒ **不重复发奖、期号不倒流** ✓ |
| 一期里改了 `rule` / 窗口分钟数 | 以**开期时钉死**的口径为准（存进 SavedData），改配置只影响下一期 |
| 邮件箱满（200 封） | 拒绝投递 + WARN + 提示；**联赛邀请与奖励邮件永不因"满"被丢**（优先占用名额）✓ |
| 玩家长期不上线 | 奖励**永久保管在邮件里**（`rewardMailKeepDays=365`），结算**不依赖在线** ✓ |
| 性能 | 两个判定各 20 tick 一次、只比两个 long；成绩更新只在上鱼时 O(1) ✓ |

## 8. 落地顺序与检查器

| 步 | 内容 | 验收 |
|---|---|---|
| **L1** | **邮件箱**（`docs/36`）先落地 | 手动 `/atl mail send` 发一封带奖励的信，能读、能签收 ✓ |
| **L2** | 周期与邀请：`LeagueData` + 两种计时口径 + 跨期发邀请 | 周期临时调成 1 分钟：自动开期、发邀请、剩余时间对得上 |
| **L3** | 签收与记分：签收入场 + 上鱼计分（只算已签收、且 ≥`minCatchesToRank`） | 两人实测：只有签收的人进榜；未签收上鱼不计数 |
| **L4** | 结算与公示：名次、广播、成绩单邮件、幂等流水、离线寄邮件 | **强制结算两次，钱只发一次**；离线玩家奖励进邮箱 |
| **L5** | 手册一章 + 服主文档（两种计时的换算表 + "只在这些小时里推进"）| 手册数字与配置逐条对账（`check-guide-numbers` 同一套）|

**检查器与负例（交付时必须一起给）**

| 断言 | 反例（必须红）|
|---|---|
| 周期只用**累计刻**（`getGameTime()`），全仓不出现 `getDayTime()` | 改用 `getDayTime()`（睡一觉跳完赛季）|
| **每人窗口独立**：计分处读的是"这个玩家自己的 `windowEndTick`"，不是全局时间 | 用全局截止当所有人的窗口（A 的签收时间会影响 B）|
| 窗口终点 = `min(签收刻 + 30 分钟, 硬截止)` **两处都取** | 只算 `签收 + 30 分钟`（可能越过硬截止）|
| **硬截止到点强行结算**（不看有没有人"打满"）| 加一个"打满才结算"的提前返回 |
