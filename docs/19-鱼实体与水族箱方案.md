## 1. 最重要的发现：`AbstractFish` 几乎把活都干完了

从源码 jar 读到（`net/minecraft/world/entity/animal/AbstractFish.java`）：

```java
public abstract class AbstractFish extends WaterAnimal implements Bucketable {
```

它**已经实现**了：

| 方法 | 作用 | 我们要不要重写 |
|---|---|---|
| `mobInteract` | **鱼桶交互**（拿桶右键捞鱼、放鱼） | 不用 |
| `saveToBucketTag` / `loadFromBucketTag` | 鱼的 NBT 进出桶 | 不用（除非存自定义数据） |
| `getPickupSound` | 捞起来的声音 | 想换再换 |
| `registerGoals()` | 默认 AI（`FishSwimGoal` + `PanicGoal`） | 一般不用 |
| `createNavigation` | 鱼的寻路（`WaterBoundPathNavigation`） | 不用 |
| `travel` / `aiStep` | 水里怎么动、搁浅怎么扑腾 | 不用 |
| `canRandomSwim()` | 子类可覆盖，控制"要不要随机游动" | 可能要 |
| `getFlopSound()` | **唯一的 abstract 方法** | 必须实现（一行） |

**结论：注册 21 种鱼不需要写 21 个实体类。**
写**一个** `ModFish extends AbstractFish`，用数据驱动（贴图、体型、水层、尺寸都从
`FishSpecies` 查），然后注册 21 个 `EntityType` 指向同一个类。

这不是偷懒，是原版的设计意图 —— `Cod` / `Salmon` / `TropicalFish` 各自成类是因为
它们**行为不同**（鳕鱼成群、鲑鱼能进河流、热带鱼有变体、河豚会鼓起来）。
我们的 21 种鱼行为如果一致，就没有理由拆成 21 个类。

> ⚠ 反过来说：**如果某些鱼要有个性化行为**（比如鲨鱼会攻击、巨骨舌鱼会跃出水面呼吸），
> 那它们才值得单独成类。这是要定的设计问题，见 §6。

## 2. 模型：4 组体型 + 21 张贴图（S2/S3 已落地）

> **2026-10-01 更新**：S2/S3 已完成，做法与本节最初的设想有出入，以实际为准。
> 完整说明见 `docs/21-鱼的建模与贴图管线.md`，这里只记结论。

最初设想是"一个模型 + 5 个参数（体高/体长/尾型/鳍高/须）"。实际做下来分成两层：

**几何层 —— 4 组可复用体型**（`tools/fish-appearance.json` 的 `bodies`）：

| 组 | 名称 | 体长:体高 | 含 |
|---|---|---|---|
| A | 高背侧扁 | 2.3 : 1 | 罗非鱼、鲫鱼、镜鲤 |
| B | 纺锤形 | 4.0 : 1 | 梭鱼、梭鲈、大西洋鲑、蓝鳍金枪鱼、褐鳟、虎鱼 |
| C | 侧扁·延长型 | 3.5 : 1 | 翘嘴鲌、䱗条、条纹鲈、白金龙鱼、大眼海鲢、花鳅 |
| D | 延长圆筒形 | 6.7 : 1 | 草鱼、青鱼、狗鱼、巨骨舌鱼、蓝宝石雷龙、幼鲨 |

每组 25 个零件，**零件名四组完全一致**（体干/尾柄/头/吻/背鳍×2/第二背鳍/脂鳍/胸鳍×2/
臀鳍/尾鳍×3/鳃裂×5/口须×6）。所以只需要 **4 个 ModelLayer**：用不上的零件在
`setupAnim` 里设 `visible = false` 就行，不必给 21 种鱼各烘一份网格。

**差异层 —— 三轴缩放**（`client/FishVariants.java`）。组内区别（高背/细长/扁平）
全部交给 `poseStack.scale(sx, sy, sz)`，这正是参考资料自己的建议：
"C 组可并入 A 组，用长宽比缩放区分"。缩放基准是鱼的**腹线**而不是模型原点
（`LivingEntityRenderer` 的 `translate(0,-1.501,0)` 在顶点变换里最先作用），
所以大鱼小鱼都贴地，不会浮空也不会陷进地里。

**贴图层 —— 21 张 64×64**，按真实物种资料逐面作画（见 §7 与 `docs/21`）。

> 原版 `CodModel` 是 32×32 且 texOffs **互相重叠**（body 占 u0~17、head 从 u11 开始），
> 头和身抢同一片像素，做不了"头素色、身带花纹"。我们改成按盒子尺寸自动装箱、
> 零重叠，于是"哪块像素属于哪个零件的哪个面"完全是算出来的。

## 3. 水族箱：两条路，我建议 A

### A. 玻璃缸 = 真的鱼实体在里面游（推荐）

- 鱼是**真的 `ModFish` 实体**，AI 照常工作
- 只需要一个"把鱼限制在缸内"的 AI 目标 —— **这个模式我已经在 `FishermanEntity` 上写过**
  （`StrollNearHomeGoal` + `GoHomeGoal`：以"家"为圆心限制活动范围）
- 玩家能看、能用桶捞、能喂
- **不需要方块实体、不需要渲染器**（实体自己会渲染）

代价：鱼是实体，多个水族箱 = 多份 AI 开销。按住 20 条鱼 × 10 个缸可能有点重，
但 `canRandomSwim()` 可以调低它们的活跃度。

### B. 方块实体 + 内部渲染鱼模型

- 参考 `SkullBlockRenderer`：`modelSet.bakeLayer(...)` 拿到实体模型，手动 `render`
- 好处：鱼的姿势完全可控、零 AI 开销
- 代价：要写 `BlockEntityRenderer`、要自己画动画、玩家**不能**和鱼互动

**建议 A**：工作量小一个数量级，而且"活的鱼"体验明显更好。
B 可以作为**标本**的做法（标本本来就该是静止的）。

### 缸体本身怎么做

不做一个"多格大方块"，而是：
- 一个 `aquarium_glass` 方块（透明、防水流出）
- 玩家自己用玻璃围一个池子、灌水、放鱼？
- **或者**：一个 `aquarium` 方块，放下后自动生成 3×3×2 的水空间

前者更 MC、更自由；后者更像"家具"。**待定**（见 §6）。

## 4. 标本（鱼架）：抄 `SkullBlockRenderer`

从源码读到原版的做法：

```java
public static Map<SkullBlock.Type, SkullModelBase> createSkullRenderers(EntityModelSet modelSet) {
    builder.put(SkullBlock.Types.SKELETON, new SkullModel(modelSet.bakeLayer(ModelLayers.SKELETON_SKULL)));
    ...
}
```

**要点：方块实体渲染器通过 `EntityModelSet.bakeLayer(...)` 复用实体模型。**
所以标本不需要另做模型 —— 直接用 `ModFishModel` 的烘焙层，摆一个固定姿势。

标本方块存"鱼种 + 体长/体重"（用 `FishData` 组件），渲染时：
- 按体长缩放
- 摆成"挂在墙上"的姿势（可以用 `setupAnim` 的参数硬编码一个静态姿势）

这样**标本是 3D 的鱼**，比原版物品展示框里的一张平面图好看得多。

## 6. 必须先定的设计问题

### ① 钓上来的鱼，是物品还是实体？

**这是最关键的**。现在钓上来直接给 `ItemStack`（`FishItem` + `FishData` 组件），
整套系统（图鉴、售价、商店卖鱼、战利品表）都建立在"鱼是物品"上。

如果鱼变成实体，这四样全要改。

**我的建议：保持"钓上来是物品"，实体只用于**：
- 水族箱里养的活鱼
- 标本展示

也就是说**实体是"物品的展示形态"**，不是钓获物本身。
这样零破坏，而且符合"钓到的鱼可以放进水族箱"的直觉。

### ② 21 种鱼的实体都要吗？

用户说"给每个鱼加实体"。但如果实体只用于水族箱/标本，那 21 种都要有。
工作量主要在**贴图**（21 张）和**模型参数**（21 组），不在代码。

### ③ 水族箱是一个方块还是玩家自己围的池子？

见 §3。

### ④ 鱼的个性化行为？

- 鲨鱼要不要攻击玩家？
- 巨骨舌鱼要不要跃出水面？
- 虎鱼要不要成群？

如果要，那几种鱼值得单独成类。**默认：全部用同一套 AI**（省事且行为一致）。

### ⑤ 实体和水体的关系

鱼实体在水里会"搁浅扑腾"（`AbstractFish` 自带）。水族箱里的鱼如果缸太小，
可能一直处于搁浅状态。要调 `canRandomSwim()` 或给缸一个最小尺寸限制。
