## 1. 为什么纹理坐标必须"算"而不是"抄"

MC 的 box UV 是**按盒子尺寸自动展开**的。一个 `(dx, dy, dz)` 的盒子在贴图上占

```
宽 = 2*dz + 2*dx        高 = dz + dy
```

的一块矩形，里面 6 个面的位置由 `ModelPart.Cube` 的构造顺序**硬编码**：

```
u0        u0+dz      u0+dz+dx    +dz        +dx
┌──────────┬──────────┐
│  DOWN    │   UP     │                      高 = dz
├──────────┼────┬─────┼────────────┐
│  WEST    │NORTH│EAST │   SOUTH    │         高 = dy
└──────────┴────┴─────┴────────────┘
  宽 = dz    宽 = dx  宽 = dz   宽 = dx
```

（来源：`_fishsrc/net__minecraft__client__model__geom__ModelPart.java` 第 252~344 行。
那个 `[u0, u0+dz] × [v0, v0+dz]` 的左上角是**空的**，原版如此。）

两张面的**朝向**也从同一段代码反推出来，这一点最容易被忽略：

| 面 | 是哪个面 | 矩形横向 | 矩形纵向 |
|---|---|---|---|
| `west` | 鱼的**左侧**（-X） | 局部 z，**头在右、尾在左** | 上=背、下=腹 |
| `east` | 鱼的**右侧**（+X） | 局部 z，**头在左、尾在右**（镜像） | 上=背、下=腹 |
| `north` | 前端（-Z） | x | 上=背、下=腹 |
| `south` | 后端（+Z） | x（反向） | 上=背、下=腹 |
| `up` | 背（-Y） | x | 上=尾、下=头 |
| `down` | 腹（+Y） | x | 上=尾、下=头 |

> west 与 east 是**镜像**的 —— 同一个 z 在两张面上分别落在左右两端。
> 手工画贴图时这里是必错点：画对了左侧，右侧花纹就是反的。
> 所以 `gen-fish-textures.js` 里统一按**鱼体全局坐标 (Z, s)** 作画，
> 由 `walk()` 负责镜像，人不碰这个细节。

**原版 `CodModel` 的 texOffs 是重叠的**：body 的矩形是 u0~17，head 从 u11 开始，
两者抢同一片像素。所以原版贴图里头和身只能同色。
我们要"头部素色 + 身体带花纹 + 头侧画眼睛"，就必须让 UV 零重叠 ——
于是 `fish-model.js` 用**货架装箱**（按高度降序、逐行排）给 25 个零件分配矩形，
装箱结果同时喂给 Java 生成器和贴图生成器，两边不可能对不上。

## 2. 4 组体型，25 个零件

`tools/fish-appearance.json` 的 `bodies` 里，每组只有 8 个标量：
`W`（体宽）`H`（体高）`Lb/Lh/Ln/Lt`（体干/头/吻/尾鳍的 z 向长度）`tailH` `dorsalLong`，
其余全部由 `buildParts()` 推导。已定型的四组：

| 组 | 名称 | W×H | 体干 | 头 | 吻 | 尾 | 体长:体高 |
|---|---|---|---|---|---|---|---|
| A | 高背侧扁 | 2×6 | 8 | 4 | 2 | 4 | 2.33 : 1 |
| B | 纺锤形 | 2×4 | 10 | 4 | 2 | 5 | 4.00 : 1 |
| C | 侧扁·延长型 | 1×4 | 10 | 3 | 1 | 5 | 3.50 : 1 |
| D | 延长圆筒形 | 3×3 | 14 | 4 | 2 | 5 | 6.67 : 1 |

比例来自 `21种鱼外形参考资料.md` 的分组建议（A 组体高约体长的 36%~45%，
C 组约 24%~29%，与上表吻合）。

**零件并集 25 个**（四组同名同序）：

```
体干类：body  peduncle  head  nose
奇鳍类：dorsal  dorsal_long  dorsal2  adipose  anal
尾鳍类：tail_round  tail_fork_up  tail_fork_lo
偶鳍类：pectoral_r  pectoral_l
细节类：gill_1..gill_5   barbel_1..barbel_6
```

其中 `peduncle`（尾柄）是让轮廓不像方盒子的关键 —— 它比体干矮一半、窄四成，
鱼身才有"向后收细"的曲线。`dorsal` 与 `dorsal_long`、`tail_round` 与两片叉尾叶
是**互斥**的，按鱼种开一个关一个，所以并集里同时存在。

**为什么是并集而不是每种鱼一套**：`ModelPart` 有 `visible` 字段。
一个层里放全部零件、`setupAnim` 里按鱼种关掉用不上的，就只要 **4 个 ModelLayer**；
换成"每种鱼一套网格"要 21 次烘焙，而且 texOffs 会有 21 组，改一处就全乱。

## 3. 三轴缩放与"该大的要大"

`FishVariants.java` 给每种鱼三个缩放系数和一个碰撞箱，**全部由真实体长算出**：

```
targetUnits = 2.98 × 体长(cm)^0.48          目标模型长度（1 模型单位 = 1/16 格）
scale       = targetUnits / 该组模型全长      只此一处归一，不再额外压缩
hitW/hitH   = 模型长度/高度 × 系数，夹在 [0.30,1.90] / [0.20,1.00]
```

> **2026-10-01 重做**。上一版是「组内归一 → 0.6 次方 → 夹 [0.78,1.5]」三重压缩，
> 结果 200 cm 的巨骨舌鱼只比 20 cm 的鲫鱼长一倍出头，看着完全不像巨物 ——
> 而**所有检查都是绿的**，因为没人断言过尺寸关系。
> 现在 `check-fish-appearance.js` 把"大小排序"直接写成断言：
> 巨骨舌鱼/蓝鳍金枪鱼 ≥ 2.0 格、花鳅 ≤ 0.7 格、最大与最小相差 ≥ 4 倍。

0.48 次方是刻意的：真实体长差 25 倍，线性映射到模型上会出戏，压成 4.2 倍正好。
系数 2.98 的标定和原版同量级 —— 原版鳕鱼模型 15 单位而真实鳕鱼约 50 cm，
相当于"1 格 ≈ 55 cm 的真鱼"。

实际结果（`node tools/fish-model.js` 会打印全表）：

| 鱼 | 体长 | 模型长度 | 碰撞箱 |
|---|---|---|---|
| 花鳅 | 8 cm | 0.51 格 | 0.40 × 0.20 |
| 䱗条 | 11 cm | 0.59 格 | 0.47 × 0.20 |
| 鲫鱼 | 20 cm | 0.78 格 | 0.63 × 0.35 |
| 梭鲈 / 狗鱼 | 50 cm | 1.22 格 | 0.97 × 0.35 |
| 大西洋鲑 / 草鱼 | 70 cm | 1.43 格 | 1.15 × 0.41 |
| 青鱼 | 90 cm | 1.62 格 | 1.29 × 0.32 |
| 蓝鳍金枪鱼 / 巨骨舌鱼 | 200 cm | **2.37 格** | 1.90 × 0.68 |

- `renderScale` 是组的**形状**微调（A 组 x 乘 1.2 让高背鱼更厚），不参与定尺寸。
- `squat` 单独压 y，做矮身底栖种（花鳅 0.7）。
- 原来的 `scaleHint` 已删除 —— 尺寸由体长决定，再叠一层手调只会让两处打架。

**碰撞箱和模型同源**：`ModEntities` 里手写的 `SIZE_OF` 表已删除，改为
`FishVariants.of(id).hitW()/hitH()`。手写表的坑是"模型放大了判定框没跟着动"，
表现是鱼比自己的判定框大一圈、**用桶捞会捞到空气**。这也是 `FishVariants`
从 `client` 包搬到 `fish` 包的原因 —— 服务端也要读它。

**缩放基准是腹线**：`LivingEntityRenderer.render` 的调用顺序是

```
scale(getScale())  →  setupRotations(...)  →  scale(-1,-1,1)  →  this.scale(...)  →  translate(0,-1.501,0)
```

`PoseStack` 是后乘，顶点变换里**最后调用的最先作用** —— 轮到 `this.scale()` 时，
坐标系原点已经在鱼的腹线（模型 y=24）上了。直接 `pose.scale(...)` 就是
"以腹线为基准缩放"，鱼不会浮空。想在别的基准上缩放必须自己补 `translate`。

## 4. 贴图：逐面作画

`gen-fish-textures.js` 拿到每个零件 6 个面的矩形后，按**面的角色**上色：

| 面 | 画什么 |
|---|---|
| `west` / `east` | 背→体侧→腹三段渐变（背 30% / 侧 45% / 腹 25%，比例取自鲫鱼资料）+ 花纹 + 侧线 |
| `up` | 背色（背脊一行加 10% 高光） |
| `down` | 腹色 |
| `north` / `south` | 体侧色（一般被相邻零件挡住） |
| 鳍的侧面 | 鳍色，每 2px 一条略深的鳍条线，外缘一行压深 |

**花纹只画在体干与尾柄上**，头部保持素色 —— 真鱼是这样，而且头侧面要留给眼睛。

花纹类型（`pattern` 数组，可叠加）与画法：

| 名字 | 效果 | 用在 |
|---|---|---|
| `bars` | 垂直暗带，1px 宽，间隔 `barStep`（默认 3，罗非鱼/花鳅用 2） | 罗非鱼、梭鲈、鲑、花鳅、幼鲨 |
| `stripes` | 水平纵纹，每 3 行一条 | 梭鱼、金枪鱼、条纹鲈、虎鱼 |
| `spots` | 随机斑点（16% 密度） | 褐鳟、狗鱼、雷龙 |
| `speckle` | 更细密的点（14% 密度），用 `mark2` 色 | 褐鳟、雷龙 |
| `plates` | 5×3 菱形鳞片网格 | 镜鲤、草鱼、巨骨舌鱼、白金龙鱼 |

`rearFade` 让花纹向后加重（巨骨舌鱼的后 1/3 锈红就是靠它）。
`patternContrast` 控制叠加强度，越是"辨识靠花纹"的鱼给得越高（条纹鲈 0.95、花鳅 0.92）。

爪子以外的细节：眼睛画在头侧面靠吻端、体高中线略偏上（`bigEye` 加大眼海鲢的眼径），
`cheekSpot` 给罗非鱼加鳃盖上缘的蓝灰斑点。

## 4b. 刷怪蛋：四张表一起生成

21 个鱼刷怪蛋（`<id>_spawn_egg`）是**调试物品**，用来在游戏里一条条对着看，
配色不对/大小不对可以直接报出是哪一条。它们牵扯四张表：

| 表 | 内容 |
|---|---|
| `ModItems.java` | 21 个 `DeferredItem` 字段 + `FISH_SPAWN_EGGS` 映射 |
| 创造页签 | 21 行 `output.accept(XXX_SPAWN_EGG.get())` |
| 语言键 | `item.anglertackle.<id>_spawn_egg`（中英各 21 条） |
| 模型 json | `assets/anglertackle/models/item/<id>_spawn_egg.json` |

手写就是 84 处，漏一处的表现各不相同且**都不报错**（拿不到 / 名字显示成键名 / 紫黑方块），
所以四张表由 `gen-fish-model.js` 一起生成，往 `ModItems.java` 里注入两个带标记的块。

**蛋壳颜色 = 该鱼的背部色 + 花纹色**（没有花纹就用体侧色），和模型贴图同源 ——
改了配色蛋跟着变，不会出现"鱼是蓝的、蛋是绿的"。

`FishSpawnEggItem extends DeferredSpawnEggItem`，只多做一件事：
**在 tooltip 里补一行 `anglertackle:<id>`**。"21 条里第 7 条不对"这种反馈，
没有 id 就只能靠中文名猜，一来一回很费时间。

> 刷怪蛋没有也不需要自己的 png：壳色由构造器参数给出，原版 `ItemColors` 把它叠到
> `minecraft:item/template_spawn_egg` 上。`check-creative-tab.js` 认这个 parent 并跳过。

**上架前删除**：`ModItems.java` 里两个生成块（连同锚注）+ `assets/.../models/item/*_spawn_egg.json`
+ 两个语言文件里的 21 个键。`docs/12` 的打包清单里已登记。

## 5. 怎么改鱼的外形

**改配色/花纹/零件** → `tools/fish-appearance.json`，然后

```
node tools/gen-fish-model.js        # Java：模型 + 变体表 + 层 + 21 个刷怪蛋 + 语言键 + 蛋模型
node tools/gen-fish-textures.js     # 21 张 PNG
node tools/preview-fish.js          # 出 build/fish-preview.png 看效果（统一比例，能直接比大小）
```

`build-deploy.ps1` 的第 2 步会自动跑前两个，所以正常流程只改 JSON。

**改几何算法**（比如加一种鳍、改装箱策略）→ `tools/fish-model.js`。
改完必须重跑上面两条 + `preview-fish.js`。

**加一种鱼** → `fish_research/<id>.json` 先有资料，
然后 `fish-appearance.json` 加一条、`ModEntities.FISH_IDS` 加 id、
`tags/item/fishes.json` 加条目、`ModItems` 加鱼物品。
`ClientSetup` 与 `ModModelLayers` **不用改**（它们遍历表）。
`check-fish-appearance.js` 会断言这三处列表完全一致。

## 6. 离线预览：为什么值得做

鱼只有在游戏里才看得见，而"进游戏看一眼"的代价是
构建 → 部署 → 开新世界 → 找到鱼，一轮十几分钟。
所以有了 `tools/preview-fish.js`：用**同一份** `fish-model.js` 排版和**同一批** PNG，
沿 -X 做正交投影 + z-buffer，把 21 种鱼画成一张 PNG。

它当场就抓到了两个肉眼才发现的问题（都是"检查全绿但不好看"的类型）：

1. **预览器自己的 UV 索引写错了**：`uv = [[d[6],d[5]], ..., [d[4],d[6]], [d[6],d[6]]]`
   里 `d[6]` 是 u2 不是 v2，于是整个身体采样到背面那一块 ——
   画出来的鲫鱼是一整块墨绿。这个 bug 在预览器里，但**同样的索引错误如果发生在
   贴图生成器里，就是"鱼身上出现别的零件的颜色"**，正是最难查的那类。
2. **鱼是个方盒子**：体干从头到尾一样高，没有尾柄收细，也没有吻端收窄。
   加了 `peduncle` 与更小的 `nose` 之后才有鱼的轮廓。

用法：

```
node tools/preview-fish.js                  # 全部 21 种 → build/fish-preview.png（3 列）
node tools/preview-fish.js pike arapaima    # 只画指定几种
$env:PPU=22; node tools/preview-fish.js crucian_carp   # 放大到 22 像素/模型单位
```

配套还有 `gen-fish-textures.js` 输出的 `build/fish-textures-sheet.png`（贴图联络表）。

## 7. 守门的两条断言
`check-fish-appearance.js`：

- **配色溯源**：`fish-appearance.json` 里 151 个颜色，每一个都必须原样出现在
  `fish_research/<id>.json` 的对应字段里。
  这条断言第一次跑就抓出 9 个"看着像、实际是编的"色值
  （例如给翘嘴鲌/青鱼编了虹膜色 —— 资料里根本没记它们的眼色）。
  想改配色就必须先改调研资料，绕不过去。
- 覆盖完整（标签 / `FISH_IDS` / 外形数据三方一致）、组名与零件开关合法、缩放范围合理。

`check-fish-model.js`：

- 生成的三个 Java 文件与数据源**逐字节一致**（直接 `require` 生成器比对，
  不另起进程 —— 沙箱禁止 node 用管道收子进程输出，`execFileSync` 会 EPERM）。
- UV 装箱：4 组 × 25 个零件两两不重叠、都在图集内。
- 贴图 21 张全是 64×64（与 `LayerDefinition.create(mesh, 64, 64)` 一致）。
- **每个可见零件的每个非退化面都必须有像素**：这一条同时能抓到
  "忘画某个零件"和"UV 算错、画到别处去了"。
- 接线：渲染器按组取层、施加 `FishVariants` 缩放；`ClientSetup` 遍历表注册；
  旧的单层常量 `MOD_FISH` 不得残留。

`tools/negtest.ps1` 里为这两个检查器配了 **13 个负例**（2 个对照组 + 11 个改坏），
包括"把鲫鱼背部改成编造的色"、"把图集缩到 32×32"、"把贴图整张涂成全透明"、
"渲染器不再施加缩放"—— 每一处都必须让对应检查器变红。
