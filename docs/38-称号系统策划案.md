## 1. 目标与定位

- **称号 = 玩家可见的成就**，显示在**聊天里自己的名字后面**；
- **★ 必须"别人也看得到"**（用户追加口径）⇒ 三个层面都要做到：
  1. **聊天**：称号由**服务端**广播 ⇒ 全服每个人看到的都是 `玩家[称号]：发言内容` ✓
     （绝不是"只在自己客户端显示"的花架子 ✗）；
  2. **可查询**：`/atl title list <玩家>`（**无权限**）能看**别人**的称号与获得次数；
  3. **界面**（第二阶段）：称号列表里显示"本服还有谁拿到了这个称号"（数据来自服务端，不靠客户端猜）。
- 它必须是**已有进度的自然外化**：图鉴、等级、纪录、联赛、比赛 —— 这些系统都已经在跑，
  称号只是"把它们变成别人看得见的一行字"；
- **绝不新增一套独立的进度系统**（否则又是一份要和图鉴/等级对齐的真源 ✗）。

## 2. 聊天显示：三个方案与代价（**已按用户口径定：优先方案 3，退路方案 2**）

用户要的形态是 **`玩家[称号]：发言内容`**（名字后直接跟称号，然后是冒号与内容）。
Minecraft 的聊天在 1.19+ 是**签名聊天**：玩家发的内容与显示格式由原版 `ChatType` 决定
（默认 `SAY` 渲染成 `<名字> 内容`）。所以"改显示"有三条路：

| 编号 | 方案 | 实际显示 | 代价 | 采用 |
|---|---|---|---|---|
| **方案 1** | 改玩家的显示名（`ServerPlayer.setCustomName`）| `<玩家[称号]> 内容` | 名字会在**聊天、Tab 列表、头顶名牌三处一起变** | ✗ 影响面太大 |
| **方案 2**（**退路**）| 只改消息内容（`ServerChatEvent.setMessage`）| `<玩家> [称号]内容` | 称号跑到内容前面（与"名字后"不符），**但完全保留原版签名聊天** ✓ | ✅ **困难时退这条** |
| **方案 3**（**默认，用户格式**）| 拦截并自行广播（`ServerChatEvent` 里 `setCanceled(true)` + 自己 `broadcastSystemMessage`）| **`玩家[称号]：内容`** ✓ 与用户原话逐字一致 | ⚠ **绕过原版签名聊天**：这条消息变成"系统消息"（不进聊天举报链、其他聊天类模组看不到原始签名、颜色由我们定）| ✅ **默认** |

**实现要点（方案 3）**：

- 监听 `net.neoforged.neoforge.event.ServerChatEvent`（**已确认 NeoForge 21.1.252 里有这个类**）；
- 取 `event.getRawText()`（原文，已过滤过）+ 该玩家当前佩戴的称号 → 组一条
  `Component.literal(name + "[" + title + "]：" + text)`（**称号那一段带它自己的品质色**）；
- `event.setCanceled(true)` 后由 `server.getPlayerList().broadcastSystemMessage(component, false)` 广播；
- **不佩戴称号的玩家**：**照常走原版聊天**（不拦截）⇒ 未使用该功能的人行为逐字不变 ✓（纯加法）；
- 配置 `titleChatMode = full_line（方案 3）| message_only（方案 2）| vanilla`：
  服主若更在意**聊天举报/其他模组兼容**，一条配置即可切换（`vanilla` = 聊天里不显示，称号仍可在查询/界面看到）。

⚠ **已知的、必须写进手册的两条**：
1. 方案 3 下，佩戴称号玩家的聊天**不再是原版签名消息**（截图举报仍有效，但走系统消息）；
2. 因此 `/msg`、`/me`、其他模组的聊天前缀/频道**不会**带称号 —— 只有**普通公开发言**会。

## 2.1 头顶名牌显示称号（**2026-10-13 用户新增**）

> 用户原话：**"需要让玩家在他人显示视角里看到名字后有已经佩戴的称号。"**

**形态**：名牌 = **`名字[称号]`** —— 与聊天**同一套括号、同一个品质色**（用户口径"名字后"）。
截图实况：`baigu` 头顶只有名字（本轮要补的就是那一段）。

**只改名牌这一处 —— 绝不动"显示名"**：
§2 的方案 1（`setCustomName`）被否，理由是"改显示名会把**聊天、Tab、名牌三处一起改**"。
本轮要的恰恰**只有名牌**，所以走客户端渲染事件：**Tab 列表、聊天、其它界面一个字都不变**。

### 怎么实现（每个环节为什么这么选）

| 环节 | 做法 | 理由 |
|---|---|---|
| 数据从哪来 | 服务端广播一张 `UUID → 已佩戴称号 id` 的**整表**（新包 `title_nameplates`） | 客户端**不可能自己知道别人的称号**（称号挂在别人的玩家附件里，只有服务端有）；发整表 = **自愈**：任何一次不一致都会被下一次广播纠正 |
| 什么时候发 | ① 有人**戴上/摘下** ② 有人**进服** ③ 有人**退服** | 三处足以覆盖。`Titles.equip/unequip` 是**唯一**改佩戴的入口（`withEquipped` 全仓只有那两个调用点 ⇒ 不会漏） |
| 客户端怎么画 | `RenderNameTagEvent#setContent`（NeoForge 21.1.252 **已确认有此事件**，只在逻辑客户端触发） | 不碰实体、不写世界数据；原版名牌的**其它**行为（蹲下隐藏、距离判断、遮挡）**原样保留** |
| 认不出的 id | **不画**（`TitleDefs.byId` 与 `validInstance` 都认不出就直接返回） | 与 `TitleSnapshot`/`TitleScreen` 同一条纪律：**绝不把 `%s` 或语言键原样画出来** |
| 出错 | 整个处理器 `try/catch` 吞掉、放行原版名牌 | 名牌画不出来比"称号不显示"严重得多（同 `TitleChatEvents` 第三条纪律） |
| 已失去的称号 | 广播时**只发"现在仍然拥有"的**（`has(id)` 为真） | 与聊天同口径：不显示一个玩家已经不该有的称号 |

### 验收标准（可验证）

| # | 怎么试 | 应该看到 |
|---|---|---|
| A1 | 两个玩家，A 戴上称号 | B 的视角里 A 头顶是 `A名[称号]`（称号是**品质色**） |
| A2 | A 摘掉 | B 视角里那一段**立刻消失**（不必等 A 重进） |
| A3 | A 戴的是生成式实例（如 `S3大型联赛冠军`） | B 看到**带参数的完整名**，不是 `%s` 或语言键 |
| A4 | 没戴称号的玩家 | 名牌**逐字不变**（纯加法） |
| A5 | A 蹲下 / A 走远（>64 格） | 按**原版**规则隐藏 —— 我们不抢这套规则 |
| A6 | B 的 Tab 列表、聊天、其它界面 | **一个字都没变**（本轮不碰） |
| A7 | B 换存档 / 重进 | 不会闪上一个档的称号（客户端缓存在退出世界时清掉） |

### 明确不做（免得以后被"顺手补上"）

- **不动 Tab 列表**：用户只点名名牌。真要加，是同一张表 + 另一个事件（`PlayerEvent.TabListNameFormat`），单独一轮；
- **不动显示名**（会把三处一起改，见 §2 方案 1 的否决理由）；
- **不加任何快捷键**（用户口径：一律鼠标 / 无键）。

## 3. 数据模型（与玩家设置同一条纪律）

新玩家附件 `PLAYER_TITLES`（`TitleBook` record）：**不塞进 `PlayerFishingData`**
（那个 record 有 5 处构造点，且称号是"会增删的集合"，理由同 `docs/36` §2.1）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `owned` | `Set<String>` | 已获得的称号 id（**不存数量**；"第几次获得"另存 `counts`）|
| `counts` | `Map<String,Integer>` | 可重复获得的称号（如联赛冠军）的**次数**，用来显示 `[小型联赛冠军 ×3]` |
| `equipped` | `String` | **当前佩戴**的称号 id；空串 = 不显示 |
| `progress` | `Map<String,Integer>` | **只装"算不出来"的进度**（见下）|

**`progress` 里装什么、不装什么（这条是纪律，不是细节）**：

- **装**：`red_caught`（红档尾数）/ `night`（夜晚尾数）/ `full_moon`（满月尾数）/ `ice`（冰洞尾数）/
  `storm_gold`（雷暴金档，0/1）/ `league_joined`（签收期数）/
  `dishes_made`（菜型位掩码，10 道 ⇒ 低 10 位）/ `dishes_eaten`（同上）/ `palat_seen`（L0~L4 位掩码，低 5 位）
  —— 这些**现有存档里确实没有**（例如图鉴只存"最高档 + 尾数"，没有"按档计数"）；
  **备选池启用时才加**：`chum`（打窝次数）、`line_break`（断线次数）、`first_launch`（首启时刻，给"开服元老"用）；
- **不装**：图鉴完成度、等级、巨物纪录、尺寸评级、联赛名次、三冠 —— 它们**当场从现有数据算**
  （`codexCount()` / `FishermanData.level` / `CodexEntry` / `LeaderboardData`）✓。
  **理由**：再存一份就是"两份真源"，迟早会出现"称号说拿到了、图鉴说没有"✗。

- 规则：**永久拥有、不因赛季/联赛结算失去** ✓（与"绝不动玩家永久数据"一条纪律一致）；
- 老存档零迁移：`optionalFieldOf("owned", Set.of())` / `("equipped", "")` / `("progress", Map.of())` ✓；
- `copyOnDeath()` ⇒ 死一次不会丢称号 ✓。

**网络与指令**

| 交互 | 形式 | 权限 |
|---|---|---|
| 查看**自己** | `/atl title list` | **无权限**（只读自己 ✓）|
| 查看**别人** | `/atl title list <玩家>` | **无权限** ✓（用户口径："不止自己连别人也能看到" —— 看别人不等于改别人）|
| 切换佩戴 | `/atl title use <id>` | **无权限**（只改自己 ✓ 与 `docs/34` 同一条纪律）|
| 服主授予 | `/atl title grant <玩家> <id>` / `/atl title revoke <玩家> <id>` | **需要 OP**（改别人的显示身份 = 影响他人 ✓ 属于"明显影响平衡"）|
| 界面 | 第二阶段：挂在**邮件箱**或图鉴里的一页（称号列表 + 佩戴按钮 + "本服谁拿到了"）| —— |

**授予时机一律走同一处**：`Titles.grant(player, id)` ——
① 幂等（已有则只 `counts+1`，不重复发奖）② **授予时自动发一封邮件**（"你获得了称号：XX"，正文写获得条件）
③ 写一条服务端日志（便于对账）。

| **未佩戴称号的玩家走原版聊天**（事件不被 cancel） | 无条件拦截所有人的聊天 |
| 佩戴称号后**格式与用户口径逐字一致**（`名字[称号]：内容`）| 少了 `[`/`]`/`：`，或顺序颠倒 |
| **别人看得到**（三条一起断言）：① 聊天那条是**服务端广播**（`broadcastSystemMessage`，不是 `player.sendSystemMessage`）② `/atl title list <玩家>` 读的是**目标玩家**的附件（不是调用者的）③ 这条路**没有 OP 门槛** | ① 改成只发给发言者自己 ② 读成调用者自己的 ③ 给 `list` 挂 `hasPermission(2)` |
| 授予是**幂等**的（已有只 +次数，不重复发奖/不重复发邮件）| 每次触发都发一遍奖励 |
| 附件 Codec 用 `optionalFieldOf(默认空)`（老存档零迁移）| 用 `fieldOf` |
| `/atl title use` 只能改**自己**；`grant/revoke` 需要 OP（且**走 `lit()`** —— `AGENTS.md` §六）| `use` 带 `targetUuid`；或 `grant` 无门槛 |
| 称号**不会因赛季/联赛结算被清**（结算代码里不出现 `owned` 的写操作）| 结算时清空称号 |
| 邮件里的"获得称号"文案与条件来自**同一张表**（不另抄一份）| 在邮件模板里手写条件 |
| 🆕 每个新计数**只有一个写入点**（`redCaught` / `nightCatches` / `fullMoonCatches` / `iceCatches` / `stormGold` / `dishesMade` / `dishesEaten` / `palatLevelsEaten` / `leagueJoined`）| 同一个计数在两处各加一次（会双倍） |
| 🆕 新计数的**环境来源与上鱼判定同源**（时段/天气/月相/冰洞都取 `Environment` 与本竿已有的那份，不重新采样）| 称号侧自己再取一次 `level.getDayTime()`（会与鱼获对不上，正是 `AGENTS.md` 时间口径踩过的坑）|
| **可重复称号**只写 `counts`、不动 `owned` 的语义（`owned` 是集合 ⇒ 重复授予不会让它"变大"）| 用 `List` 存 `owned`（重复授予塞两份）|

**为什么第 3 张表（"别人看得到"）必须是三条一起**：单独任何一条都能被"看起来实现了"骗过 ——
只断言广播会漏掉查询，只断言查询会漏掉权限门槛（挂上 OP 之后**本机单人测试永远测不出来**，
见 `AGENTS.md` §六的同一条教训 ✗）。
